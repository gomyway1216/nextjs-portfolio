# 将棋の次に麻雀を作った — 完全情報ゲームと不完全情報ゲームで、設計はここまで変わる

> 個人サイト（meetyudai.com）に、ブラウザで遊べる4人打ちリーチ麻雀を追加した（[/games/mahjong](https://meetyudai.com/games/mahjong)）。人間1人 + AI 3人、東風戦、アリアリ、赤ドラ3枚、一発・裏ドラあり。同じサイトには自作の将棋AIも載っていて、そちらは[作り直しの記録](./blog-shogi-ai-rebuild.md)を長々と書いた。面白かったのは「麻雀を作った」こと自体ではなく、**将棋で正解だった設計判断が、麻雀ではほぼ全部ひっくり返った**ことだった。この記事はその差分の記録。英語版は [blog-mahjong-launch.en.md](./blog-mahjong-launch.en.md)。

---

## TL;DR

- 将棋の強さは**探索の深さ**から来る。だから WASM 移植・SIMD・Lazy SMP・SharedArrayBuffer・COOP/COEP ヘッダが全部必要だった。麻雀ではそれが**1つも要らなかった**。`next.config.ts` は最後まで一度も触っていない
- 代わりに強さの源泉になるのは、**ルールエンジンの正確さ**と**シャンテン/受け入れ計算の速さ**と**押し引きの期待値判断**。素の TypeScript で十分速い：シャンテン **3.2 µs**、受け入れ全34種スキャン **0.097 ms**、AI 1手の意思決定が **0.31〜0.44 ms**
- 最初に凍結したのは牌の表現だった。`kind = tileId >> 2`、王牌のインデックス配置（ドラ表示 `130 - 2i`、裏 `131 - 2i`、嶺上 `135 - n`、`liveEnd = 122 - kanCount`）。**型契約を先に固めたおかげで、山・シャンテン・点数計算を別々のエージェントが並行に実装できた**
- 記事の本題は正しさの担保方法：**わざと遅い総当たり参照実装**とのランダム1万手牌クロスチェック、符×翻の**手打ち支払い表**、**118件の役スナップショット**、そして**ランダム打ちファズ**——1アクションごとに「136枚がちょうど1回ずつ存在するか」「全員の手牌が合法サイズか」「点棒＋供託が100000のままか」を再検査して、**1シードあたり約42万アクションで違反ゼロ**
- ルールの機微はコードコメントに全部書いた。海底と河底が**嶺上ツモに対して非対称**な理由、雀頭を**5ブロック目として扱わない**と `123m456m789m12p34s` をテンパイと誤読する理由、高点法、ダブロンを**頭ハネ順に並べるために `pendingClaims` が要る**理由
- AI は正直に言って**堅実な中級者**であって Mortal 級ではない。シャンテン優先の絞り込み → 受け入れ最大化、現物 > スジ > 壁の安全牌選択、閾値ベースの押し引き。学習ポリシーは今後の課題
- v1 に**入れなかったもの**も明示した：パオ、四風連打、流し満貫、そしてサンマ（108枚・3席・チーなし・北は抜きドラ、という独立マイルストーン）

## 0. なぜ麻雀は将棋ではないのか

将棋AIを強くする作業は、最終的に「1秒間に何ノード読めるか」に収束していった。TypeScript から WebAssembly に移して探索が15倍になり、SIMD128 で評価が6.2倍になり、Lazy SMP でスレッドを増やし、そのために `SharedArrayBuffer` が要るので COOP/COEP ヘッダを足した。評価関数は NNUE に蒸留した。**全部「深く読む」ための投資**だ。

麻雀に同じ発想を持ち込むと、ほぼ何も買えない。

| 観点 | 将棋 | 麻雀 |
|---|---|---|
| 情報 | 完全情報 | **不完全情報**（他家の手牌・山が見えない） |
| プレイヤー | 2人ゼロサム | 4人・確率的（ツモ順） |
| 強さの源泉 | 深い探索（αβ + NNUE） | **正確な局面評価 + 期待値判断** |
| 実装の重心 | 探索速度 → WASM 必須 | **ルール実装と計算の正確さ** → TS で十分 |
| 強さ検証 | 自己対戦 80〜200局で有意 | 分散が非常に大きい → **複製壁 + 1000戦単位** |

理由は単純で、麻雀の「木」は自分の手番の先に**見えない乱数**（次のツモ、他家の手牌）が挟まる。5手先を読んでも、その5手先の分岐確率が分からなければ値が付かない。将棋なら「深さ+1」が素直に棋力になるが、麻雀では深さを1増やしても、増えるのは分散だけだ。

その代わり、麻雀には将棋にない「**閉じた形で正確に計算できるもの**」がたくさんある。今の手牌が何シャンテンか。この牌を切ったとき何種何枚を受け入れるか。この和了形は何符何翻で誰がいくら払うか。この牌は現物か、スジか、壁で否定されているか。これらは全部**探索ではなく計算**で、しかも**間違えると即座に強さが壊れる**。

だから v1 の設計方針は「探索を移植する」ではなく、

1. ルールエンジンを完璧にする（テストベクタで担保）
2. シャンテン数・受け入れ計算を高速に持つ
3. その上に押し引きヒューリスティックを載せる

の順にした。結果として、`next.config.ts` は最後まで一度も編集していない。COOP/COEP も SharedArrayBuffer も Worker のマルチスレッドも要らない。AI worker はあるが、それは**UIをブロックしないため**だけの単純な RPC で、1リクエスト1レスポンス、状態を持たない。

実測値がその判断を裏付けている（すべて手元の Node / ブラウザ実測）。

| 処理 | 目標 | 実測 |
|---|---|---|
| `shanten` 1手牌 | < 0.05 ms | **0.0032 ms（3.2 µs）** |
| `ukeire` 全34種スキャン | < 2 ms | **0.097 ms** |
| AI 1手の意思決定 | < 2 ms | **0.31〜0.44 ms** |

AI の意思決定が 0.44 ms ということは、3人のAIが打つ1巡が 1.5 ms 未満で終わるということだ。ここに WASM を投入する理由はどこにもない。

## 1. 最初に凍結したのは「牌をどう表すか」だった

このプロジェクトで一番効いた判断は、コードを書く前に**型契約を固定した**ことだ。マイルストーン M0 の成果物は `engine/types.ts` と `engine/rules.ts` だけで、実装は1行もない。

牌の表現はこう決めた。

- **牌種 (`TileKind`)**: `0..33`。`0..8` = 萬子1-9、`9..17` = 筒子、`18..26` = 索子、`27..30` = 東南西北、`31..33` = 白發中
- **牌ID (`TileId`)**: `0..135`。各牌種にちょうど4枚あり、**`kind = tileId >> 2`**、コピー番号は `tileId & 3`
- 赤5は各牌種のコピー0、すなわち `16`(5m)・`52`(5p)・`88`(5s)
- 手牌は `Uint8Array(34)` のカウント表現（シャンテン/受け入れが取る形）、河と副露は tileId の列

`kind = tileId >> 2` という1行の契約が、あとの全モジュールを楽にする。シャンテン計算は牌種のヒストグラムしか見ないので赤ドラの存在を知らなくていい。逆に符計算と役判定は物理牌が要るので tileId 列を見る。**同じ牌を2つの粒度で扱いながら、変換が常にシフト1回**という状態が最後まで保たれた。

王牌のインデックス配置も、実装より先に図で凍結した。`wall.ts` の冒頭コメントがそのまま仕様書になっている。

```
index:  0 ............ drawIndex ........ liveEnd | 122 ........... 135
        +---- drawn ----+---- live wall ---+------ dead wall -------+
```

- 生牌は `[drawIndex, liveEnd)`。海底牌は `tiles[liveEnd - 1]`
- 王牌の**スロット** `122..135` は14枚ぶんの固定位置で、**絶対に動かない**
- カンは生牌の末尾を1枚王牌に持っていく＝`liveEnd` をデクリメントする。よって k回カンしたあとは `liveEnd = 122 - k`
- ドラ表示牌 `i` は `130 - 2i`、その裏は `131 - 2i`（`i` は `0..4`）→ 130/131, 128/129, 126/127, 124/125, 122/123
- 嶺上牌 `n`（0始まり）は `tiles[135 - n]` → 135, 134, 133, 132

10個の表示牌スロットと4枚の嶺上牌スロットが**重なりなく14枚を分割する**ことは、コメントではなくテストで固定した。そして決定的に重要なのが最後の一文で、**`wall.tiles` の中身は `buildWall` が返した時点で確定し、以後1枚も移動しない**。動くのは `drawIndex` と `liveEnd` というカーソルだけ。これによって「136枚がちょうど1回ずつ存在する」という不変条件が、配列を舐めるだけで自明に検査可能になった。あとで出てくるファズテストの根拠がここにある。

### 型契約があったから並行実装できた

このプロジェクトは複数のサブエージェントで並行に進めた。M0（型）が終わった時点で、**M2（シャンテン・受け入れ）と M3（役・点数）は互いを一切知らずに同時に着手**できた。両者が触るのは同じ `types.ts` だが、書き込むのは別ファイルで、共有するのは「`TileCounts` は長さ34の `Uint8Array`」「副露は `meldCount` で別途渡す」といった契約だけだからだ。同様に M6（UI）は M4（状態機械）完了後に M5（AI）と並列で走らせた。

UI 側は AI を `AiDriver` という2行のインターフェースの向こうに置いて、本物のAIがマージされるまでは「最初の合法な非リーチ打牌を返すだけ」の仮ドライバで開発した。

```ts
export type AiDriver = (state: RoundState, seat: Seat) => Action | Promise<Action>;
export type AiDriverFactory = (difficulty: MahjongDifficulty) => AiDriver;
```

型が凍結されていなければ、この並行化は「マージのたびに全部壊れる」に化けていたと思う。

## 2. 正しさをどう担保したか（ここが記事の本題）

麻雀の実装が難しいのはアルゴリズムではなく、**間違いに気づけない**ことだ。将棋なら不正な手を指せば盤面が壊れて即バレる。麻雀は、符を10符間違えても、三暗刻の判定を1ケース落としても、局は最後まで進行してしまう。だから検証手段を4つ用意した。

### (a) わざと遅い参照実装との突き合わせ

`engine/shanten.ts` の本番実装は、スーツごとに「`b` ブロック使ったときに作れる最大面子数」というプロファイルを作り、それをメモ化して4段のDPで結合する。速いが、正しさを目で確かめるのは難しい。

そこでテスト側に `shantenReference.ts` を置いた。冒頭コメントがすべてを説明している。

```
Nothing here is memoised, split per suit, or pruned beyond the block budget:
the point is that each function is short enough to be checked by eye, so the
fast DP in `engine/shanten.ts` can be cross-checked against it on tens of
thousands of random hands. Never import this from production code.
```

スーツ分割もDPもメモ化もない、34種を一本の再帰で舐めるだけの実装。遅いが**短くて目で追える**。この2つを **ランダム合法手牌1万件**（13枚/14枚を交互に、`meldCount` を 0..4 で巡回）で突き合わせて**不一致ゼロ**。加えて、実際のブロック（順子・刻子・両面・嵌張・対子・字牌）から組み立てた**構造化手牌2000件**——ランダム手牌よりはるかに分解が密になる——でも一致した。

さらに、シャンテンの**定義そのもの**に錨を打つテストも入れた。`isWinningShape`（4面子1雀頭を再帰で判定するだけの、シャンテン式を一切参照しない実装）を使って、「`standardShanten === 0` ⟺ 和了形まであと1枚」を800手牌で、「最善の1交換でシャンテンはちょうど1しか下がらない（2は下がらない）」を300手牌で検証している。

### (b) 符×翻の支払い表を手で書く

点数計算は「式で導く」ことも「表を引く」こともできる。v1 では**表を手で書いて固定した**。20符〜110符 × 1〜4翻、満貫・跳満・倍満・三倍満・役満まで、親子×ツモ/ロンの全マスをテストに列挙してある。切り上げ満貫を採用していないので、4翻30符は 7700 / 11600 のまま——これも明示的なテストケースにした。

仕様が決めていなかった論点は、`score.ts` の docblock に**決定として書き残した**（あとから「なぜこうなっているのか」を発掘しなくて済むように）。たとえば：

- **門前ロンは +10符**。マイルストーンの指示書には「+2符」と書いてあったが、これは普遍的な +10 の誤記だと判断した。+2 だと門前40符ロン（例：simples の暗刻1つ）が30符になり、門前列が丸ごとずれる
- **連風牌の雀頭は4符**（場風と自風を別々に数える）。連風の**刻子**が役牌2つぶんになるのと揃える。2符説も一般的だが、自分の役牌処理と整合する方を採った
- **ロンで完成した刻子は明刻**。符でも三暗刻/四暗刻でも。ツモか、あるいは既に完成していたシャンポンだけが暗刻になる
- **食い平和は30符に切り上げ**（副露手の符合計がちょうど20になったとき）。門前平和ツモは20符のまま
- **符は10符単位で切り上げ**。これは普遍的な処理で、v1 が採用しない「切り上げ満貫」とは別物

### (c) 118件の役スナップショット

`score.test.ts` に、手牌・副露・和了牌・状況フラグから期待される役リスト・符・翻・点数までを書き下したケースを**118件**並べた。リーチ・一発・門前ツモ・平和の複合から、海底摸月と嶺上開花の区別、槍槓、食い下がりの有無、七対子と二盃口の交差、大三元＋字一色のダブル役満まで。役の**出力順序も固定**してあるので、複合の順番が変わっただけでもテストが落ちる。

役判定と符計算は和了形の**読み方**に依存する。だから `parseWinningHand` は和了形の**あらゆる読み方を全列挙**し、`evaluateHand` がその全部を採点して高点法（役満数 → 翻 → 符 → 点数の順）で最良を選ぶ。

```ts
export function evaluateHand(ctx: WinContext, isDealer?: boolean): HandValue {
  const parses = parseWinningHand(ctx);
  if (parses.length === 0) return emptyValue();
  ...
}
```

なお**ドラ・赤ドラ・裏ドラは役ではない**。`HandValue.han` には足すが `HandValue.yaku` には決して入れない。だから「ドラだけの手」は `hasYaku` を通らず、和了宣言そのものができない。この分離はコードの都合ではなく、麻雀のルールそのものだ。

### (d) ランダム打ちファズ — 1アクションごとに不変条件を検査する

これが一番効いた。`scripts/mahjong-sim-smoke.ts` は、全席が `legalActions` から一様ランダムに選ぶだけの対局を延々と回し、**1アクションごとに**構造不変条件を再検査する。

- 136個の tileId が、山 + 手牌 + 副露 + 河 を通じてちょうど1回ずつ存在するか
- 全員の手牌が合法サイズか（`13 - 3 × 副露数`、ツモ番なら +1）
- **点棒の合計 + 供託 == 4 × 25000**（= 100000）
- エンジンが入力を待っている全席について、合法手リストが空でないか

将棋の perft に相当する健全性検査だ。強さについては何も言わないが、**状態機械の帳簿ミスは数千局以内に必ず出る**。鳴きで牌が複製された、リーチ棒が二重に発生した、カンのあと手牌サイズが1枚ずれた、誰も動けない局面に入った——全部ここで落ちる。

対局は「一様ランダム打ち」と「シャンテン最短の貪欲打ち」を交互に走らせている。前者は変な局面に到達し、後者は実際に手を和了るので、奇妙な隅と点数計算パスの両方が踏まれる。

| シード | 局数 | アクション数 | ツモ / ロン | 流局 | リーチ | カン / 鳴き | 時間 |
|---|---|---|---|---|---|---|---|
| `1` | 5000 | 421,101 | 338 / 860（ダブロン1） | 3802 + 九種九牌1 | 1719 | 644 / 22,770 | 38s |
| `20260826` | 5000 | 419,922 | 323 / 880（ダブロン1） | 3795 + 九種九牌3 | 1722 | 610 / 22,756 | 36s |
| `deadbeef` | 5000 | 420,084 | 327 / 902（ダブロン3） | 3774 | 1776 | 629 / 22,704 | 34s |

例外ゼロ、不変条件違反ゼロ。CI は同じループを2000局ぶん（約13秒）走らせ、5000局はスクリプトから手で回す。

現在、麻雀ツリーのテストは **9ファイル468件**が **3.7秒**で回る。エンジン + AI + UI が約8,600行、テストが約6,700行。

## 3. 読んで面白いルールの機微

実装していて「これは書き残さないと次の人が踏む」と思ったものをいくつか。

### 海底と河底は、嶺上ツモに対して非対称

どちらも「最後の牌で和了る」役なのに、扱いが違う。`actions.ts` のコメントをそのまま引く。

```ts
// Haitei and houtei are deliberately asymmetric. Haitei raoyue is winning
// on *the last tile drawn from the live wall*, so a replacement tile never
// qualifies — that win is rinshan kaihou instead, which is why this checks
// `lastDrawSource === 'wall'`. Houtei raoyui is winning on *the last
// discard of the hand*, and the discard that follows a replacement draw is
// still the last discard once the live wall is empty, so it correctly does
// not exclude rinshan.
haitei: isTsumo && state.lastDrawSource === 'wall' && isExhausted(state.wall),
houtei: !isTsumo && !chankan && isExhausted(state.wall),
```

海底摸月は「**生牌の最後の1枚をツモって和了る**」役なので、嶺上牌でのツモは該当しない（それは嶺上開花だ）。一方で河底撈魚は「**その局の最後の打牌で和了る**」役なので、嶺上ツモの直後の打牌であっても、生牌が尽きていればそれは正しく河底になる。同じ「最後」でも、指しているものが「山の最後」と「河の最後」で違う。

ついでに、槍槓は決して河底にならない（加槓牌は打牌ではない）。この手の条件はすべて `buildWinContext` が局面から導出する。`legalActions`（役があるか判定する側）と `applyAction`（点数を付ける側）が同じ関数を通るので、**両者が「あの牌は海底だったか」で食い違うことが原理的に起きない**。

### 雀頭は「5ブロック目」であって、4ブロック + おまけではない

シャンテン計算で一番踏みやすい罠。標準形の分解は面子 `S` 個・面子候補 `P` 個・任意で雀頭1つを取る。和了形は「4面子1雀頭」= **合計5ブロック**なので：

- 雀頭あり: `meldCount + S + P + 1 <= 5`
- 雀頭なし: `meldCount + S + P <= 4`

どちらも `S + P <= 4 - meldCount` に還元される。つまり**雀頭がないときに5個目のブロックを数えることを拒否する**のがポイントだ。これを怠ると `123m456m789m12p34s` がテンパイと判定される。この手牌はブロックが5つ（順子3つ + 両面2つ）あるが、対子がどこにもないので、どれか1ブロックを雀頭に組み替えないと和了れない。正解は1シャンテンだ。

シャンテン数の式は

```
8 - 2 * (meldCount + S) - P - (head ? 1 : 0)
```

で、全分解の最小値を取る。`B = S + P` と置くと最大化すべき量は `2S + P = S + B` になる。ブロックは絶対にスーツをまたがないので、萬・筒・索・字の4グループを独立に分解して「`b` ブロックで作れる最大面子数」というプロファイルにし、共有ブロック予算の下で4段DPで結合する。プロファイルはスーツのカウント署名でメモ化してある。結果として1手牌のコストは「数回のマップ参照 + 雀頭候補ごとの 4×5×5 DP」——これが 3.2 µs の中身だ。

### 高点法（takame）は「あとで選ぶ」しかない

和了形は複数の読み方を持ちうる。たとえば `11122233344455z` 系の手は「対子7つ（七対子）」とも「刻子と順子の組み合わせ」とも読めるし、平和ツモ20符と別分解30符が競合することもある。役と符は**読み方に依存する**ので、読み方を先に1つ選んでから採点することはできない。全部採点してから最良を選ぶしかない。それが `parseWinningHand` を「全列挙」にしてある理由だ。

### ダブロンには `pendingClaims` が要る

これは状態機械の設計に跳ね返った話。打牌に対する応答は**到着順ではなくランク順**で解決される。ロン > ポン/カン > チー。しかも「上家からしかチーできない」といった方向の制約もある。

さらに厄介なのがダブロンで、本場と供託は**頭ハネ順で最も近い和了者**（放銃者から反時計回りで最初）が総取りする。つまり**全員のロン宣言が出揃うまで、誰が本場を取るか決まらない**。到着順に処理すると、2人目のロンが来た時点で1人目への支払いをやり直す羽目になる。

そこで `RoundState` に1フィールドだけ足した。

```ts
/**
 * Claims cannot be executed the moment they arrive — ron beats pon/kan beats
 * chi, and a double ron needs every ron declared before the payments can be
 * ordered head-bump first — so they are parked here until every seat the
 * engine is waiting on has answered.
 */
pendingClaims: Action[];
```

既存の `pendingResponses: Seat[]`（誰が答えたか）は「何を選んだか」を運べないので、宣言そのものを保留する場所が必要だった。1つロンが出た時点で、ポンとチーしかできない席は待機対象から外れる（どうせ勝てないので）。この設計のおかげで、ダブロンは特別扱いではなく「和了者が2人いる通常の決済」として書ける。

ファズテストの5000局×3シードで、ダブロンは1〜3回しか出ていない。**手で書いたシナリオテストがなければ、まず踏まないパス**だ。

## 4. AI — 正直なスコープ

現在の AI がどのくらい強いかを正直に書いておく。**堅実な中級者**であって、Mortal のような深層学習ベースの強豪ではない。設計は素直だ。

### 攻め

1. 打牌候補をまず**シャンテンだけで絞り込む**（34回の安い評価）
2. 絞り込まれた2〜3手にだけ**受け入れ（ukeire）の全スキャン**を払う
3. 受け入れが同率なら牌価値で順序付け——ドラとの近さ、完成面子は絶対に壊さない、孤立牌にボーナス、誰かがテンパイっぽいときは危険度を減点

この2パス構成は最適化の結果だ。コメントにこう書いてある。

```
Two passes on purpose: shanten alone (34 cheap evaluations) narrows a
fourteen-tile hand to the two or three candidates that matter, and only
those pay for a full `ukeire` scan. Running `bestDiscards` over the whole
hand instead measured 1.2ms per decision, most of it spent on acceptance
counts for tiles the AI would never throw.
```

全牌に受け入れ計算をかける素直な実装は 1.2 ms かかった。切る気のない牌の受け入れを数えていたからだ。2パスにして 0.44 ms（手元の100局ランでは 0.31 ms）。

リーチは門前テンパイなら原則宣言する。見送るのは**3条件が全部揃ったときだけ**——待ちが狭く、打点が安く、かつ1枚のツモで待ちが2枚以上広がる手替わりが残っている。鳴きは「鳴いた後に**開いた手でも成立する役**が実際にあるか」を積極的に検査してから。役牌・喰いタン・染め手・対々和は見るが、鳴きサンショク・鳴きイッツーはモデル化していないので**その鳴きは一切しない**（良い鳴きを見送るコストは、和了れない手を開くコストよりずっと安い）。

### 守り

`ai/safety.ts` は「この牌を場に出したら、誰にどのくらいロンされそうか」だけを答える。人間が使う読みを、人間が使う順に実装した。

1. **現物** — その相手の河にある牌はフリテンで当たらない。加えて、その相手のリーチ後に誰かが切って通った牌も安全。`DiscardEntry` に通し番号がないので「リーチ後かどうか」は巡目構造から再構成しているが、**再構成は保守的**に倒してある：本当は安全な牌を見落とすことはあっても、危険な牌を安全と誤認することはない
2. **スジ** — ここは明示的に「**両面にしか効かない**」と書いた。スジ牌は単騎・シャンポン・嵌張には完全に生きているので、危険度をゼロにするのではなく係数で下げる
3. **壁 / ワンチャンス** — 両面が必要とする牌が4枚見えていれば、その両面は存在しない。スジと同じ「その両面はあり得ない」という主張なので、**掛け算ではなく面ごとに統合**する（上がスジで下が壁の牌は、両スジの牌とちょうど同じ安全度）
4. **字牌は残り枚数で** — 誰も対子にできない字牌はほぼ安全、生牌はそうではない
5. **無スジの中張牌** — 手牌の中で最も危険なもの

脅威の検出は、リーチ宣言（重み1.0）、3副露以上（0.7）、役牌ポン + もう1副露（0.6）、そして見た目の染め手——副露が全部1色で、河に既に5枚以上の他色数牌がある（0.5）。

### 押し引き

v1 は閾値ルールだ。生きた脅威に対して、自分が2シャンテン以上ならベタオリ。テンパイでも**安くて待ちが悪ければ**オリ。それ以外は押す。

閾値はすべて**名前付きの export された定数**にしてある（`FOLD_MIN_SHANTEN` 2、`RIICHI_BAD_WAIT_TILES` 4、`SET_BREAK_PENALTY` 40、…）。これが次のマイルストーンのチューニング面になる。

### 次は A/B ハーネス

M7 で、将棋と同じ規律の自己対戦 A/B ハーネスを作る。麻雀で難しいのは分散で、素の自己対戦は1000戦回しても順位差がノイズに埋もれる。対策は**複製壁**——同一シード（＝同一の山・配牌・ツモ順）で被験AIの座席を4席ローテーションした4ゲームを1セットとし、A/B 両アームが同じシード集合を使う。将棋のペア開局と同じ思想だ。

現時点の M5 のゲート計器（`scripts/mahjong-ai-baseline.ts`、AI 1人 vs ランダム打ち3人）は平均順位1.02を出すが、**この計器では守備は測れない**。ランダム打ちの相手はそもそも和了れないので、オリるのは純損だからだ。実際、守備を完全に無効化した `easy` の方がこの計器ではわずかに**上**に出る。だからこそ M7 で計器を差し替える。**A/B の結果はまだ何も出していない**ので、数字はそちらの記事に譲る。

難易度は3段階で、`easy` は守備を切って上位3候補からランダムに選ぶ、`medium` がフル、`hard` は現時点では `medium` と同一のポリシー定数を持ち、M7 の EV 押し引きが有意に勝ったときだけフラグ1つで切り替わる。**A/B で勝つまで本番の hard に昇格させない**——将棋で確立した昇格規律をそのまま持ち込んだ。

## 5. v1 に意図的に入れなかったもの

「実装漏れ」と「意図的な非対応」を区別できるように、外したものを明記しておく。

- **パオ**（大三元・大四喜の責任払い）
- **四風連打・四家立直・四槓散了** — 途中流局は**九種九牌のみ**
- **流し満貫**、**切り上げ満貫**、**人和**
- **ダブル役満** — 国士13面・四暗刻単騎・純正九蓮も v1 では単倍で扱う（`rules.doubleYakuman` は `false`）
- **食い替えの禁止**、**オーラス和了止め**、**西入（サドンデス延長）**
- **オンライン対戦・牌譜保存**

そして最大のものが**サンマ（三人麻雀）**だ。これは設定フラグではなく**ルール亜種**なので、四麻 v1 を出し切ってから独立したマイルストーンとして着手する。

| 項目 | 四麻 | サンマ |
|---|---|---|
| 牌 | 136枚 | **108枚**（2m〜8m の28枚を除去。1m と 9m は残す） |
| 席 | 4（東南西北） | **3（東南西）** |
| 配牌 | 13×4 = 52 | 13×3 = 39 |
| 王牌 | 14枚、生牌は index 0..121 | 14枚、**生牌は index 0..93** |
| チー | あり | **なし**（ポン・カンのみ） |
| 北 | 客風牌 | **抜きドラ**（手牌から抜いて嶺上牌をツモる。1枚 = ドラ1） |
| ツモ支払い | 子3人で分割 | **2人で分割** |

工数の実体はルールではなくリファクタにある。`Seat = 0 | 1 | 2 | 3` と `[number, number, number, number]` という4要素タプルが `PlayerState`・`RoundResult.scoreDeltas`・`GameState.scores` に焼き込まれていて、これを**可変長（`number[]` + `seatCount`）に広げる**のがマイルストーンの主作業になる。`TILE_COUNT` / `DEAD_WALL_START` も定数からルール由来の `wallLayout(rules)` に変える。

面白いのは、牌の構成を変えるだけで**役が自然に消える**ことだ。萬子が1と9しかないので、萬子の清一色と萬子染めの純チャンは実質不可能になる（国士は 1m/9m が残るので普通に成立する）。

サンマのゲートは四麻と同じ形にしてある：四麻の全テストが緑のまま、サンマでも `mahjong-sim-smoke` の不変条件が5000局でゼロ違反。

## おわりに

将棋の作業で身についたのは、技法ではなく**規律**だった。物差しを先に作る。効かなかった実験も記録する。「測った実装」と「shipした実装」が同一物であることをシード再現で毎回担保する。ゲートを満たすまで昇格させない。

麻雀ではその規律の**適用先**が変わった。将棋では物差しが「自己対戦の勝率」で、投資先が「探索速度」だった。麻雀では物差しが「1アクションごとの不変条件検査」と「遅い参照実装との一致」で、投資先が「ルールの正確さ」になった。COOP/COEP ヘッダを1つも足さずに済んだのは、その差が正しく判断できていたということだと思う。

次は複製壁 A/B ハーネスで、閾値ベースの押し引きを期待値ベースに置き換える。それが有意に勝ったときだけ、`hard` が本当に `medium` より強くなる。
