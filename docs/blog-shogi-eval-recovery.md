# 「千日手」ではなかった — deep16 の実回帰を再現し、将棋AIの学習を作り直す

> 自作将棋AIの評価関数を `runOp1` から `deep16` に替えたあと、実戦で「△8六歩打」を何度も繰り返した。最初は千日手履歴の欠落だと説明したが、棋譜を読み直すと局面は毎回変わっていた。旧・新の重みを同じ局面、同じ探索器で比較すると、旧版が低く見ていた手を新版だけが上位に置き、本番相当の探索でも実際に選んだ。これは「表示上の違和感」ではなく、再現可能な評価回帰だった。本稿は、誤診を訂正し、途中データを残し、次の学習方法を設計し直した実験日誌である。

---

## TL;DR

- 20手目、26手目、32手目の「△8六歩打」は**同じ局面の反復ではない**。先手銀は3八→2七→2六と進み、後手飛車も8四→8五と変化している。したがって今回の主因を「実戦履歴がないため千日手を検出できないこと」とした説明は誤りだった
- 32手目直前を同じWASM探索器で比較すると、`runOp1` は△8六歩打を静的評価 **16位 / 46手（−194cp）**に置き、固定深さ11・12、2000ms・4000msのすべてで△4二銀を選んだ。`deep16` は同じ手を **2位 / 46手（−23cp）**に置き、同じ全条件で**△8六歩打**を選んだ
- 採用時の800ms・40局A/Bは52.5%、95%信頼区間は約37〜68%。これは「退行なし」の証明ではなく、**差を判定できないほど幅が広い結果**だった。しかも今回の手は800msでは現れず、2000ms・4000msで現れた
- 現行パイプラインは、やねうら王の`bestmove`をJSONLへ保存するのに、学習時は`SFEN`と`cp`しか読まない。`pair_acc≈0.90`も同じ親局面の候補手比較ではなく、**無関係な局面同士のランダム比較**である
- まず本番の重みだけを`runOp1`へ戻す。次は強豪棋譜を親局面の供給源にし、実戦手・教師MultiPV・旧版の手・候補版の手・既知の悪手を**同じ親局面のsibling候補**として教師に再評価させる
- 自作AIの到達局面も完全には捨てない。ただし正解の供給源にはせず、「現在のAIがどこで間違えるか」を集めるDAgger型のフィードバックに限定する
- 「評価関数が悪い」問題と「評価値が—／タイマーが止まる」問題は別レーンで扱う。一方を直しても、もう一方が直った証拠にはならない

## 0. この記録で使うラベル

今回もっとも反省すべき点は、仮説を事実のように説明したことだった。そこで以下では、主張を4種類に分ける。

- **確認済み**：棋譜、ソースコード、保存ログ、または同条件の再現で確認したもの
- **否定**：再現や記録によって、主張が成り立たないと確認したもの
- **仮説**：確認済みの事実を説明できるが、原因として単離できていないもの
- **未検証**：次の実験で決めるもの。期待を結論として書かない

重要な限定も先に置く。今回確認できたのは、**報告局面におけるdeep16の明確な局所回帰**である。全局面を平均したEloまでrunOp1より低いかは、まだ確認していない。しかし、採用根拠が弱く、実戦で重大な回帰が再現でき、旧版への切り戻しが可逆なら、安定版へ戻すには十分な理由になる。

## 1. 事件：同じ符号の手を、同じ局面だと思い込んだ

```text
22. △同飛

24. △８四飛

26. △８六歩打

28. △同飛
29. ▲８七歩打
30. △８五飛
31. ▲２六銀
32. △８六歩打
33. ▲同歩
34. △同飛
35. ▲８七歩打
36. △８四飛
37. ▲２五銀
38. △３三角
```

最初の説明はこうだった。「エンジンには実戦の局面履歴が渡っておらず、探索木の千日手判定が毎手リセットされるので、同じ局面へ戻ったことに気づけない」。一般論としては起こり得る。しかし、この棋譜の説明にはなっていなかった。

| △8六歩打の手数 | 先手銀 | 着手直前の後手飛車 | 局面 |
|---:|---|---|---|
| 20手目 | 3八 | 8四 | 1回目 |
| 26手目 | 2七 | 8四 | 2回目 |
| 32手目 | 2六 | 8五 | 3回目 |

**確認済み**：銀が前進し、飛車の位置も変わっている。盤面が同一ではない以上、この3回を「同一局面の反復」として処理することはできない。問題は千日手ではなく、**少しずつ変化する局面で、同じ構想の手を繰り返し高く評価していること**だった。

この違いは決定的だ。履歴を渡す修正は、将来の本当の千日手には役立つ。しかし今回のように盤面が変わり続けるケースでは、履歴を何手渡しても△8六歩打そのものの順位は下がらない。誤った原因に正しい実装を足しても、報告された悪手は直らない。

## 2. 32手目直前を旧・新の評価で固定比較する

次に、UI、定跡、マルチスレッド、対局履歴を外し、32手目直前の盤面だけを固定した。探索器は同じproduction系WASM、変えるのはNNUE重みだけである。全合法手を1手進めた子局面の静的評価ランキングと、時間制限探索の最善手を記録した。

### 結果

| 評価モデル | △8六歩打の静的順位 | 固定深さ11 / 12 | 2000ms探索 | 4000ms探索 |
|---|---:|---|---|---|
| `runOp1` | 16位 / 46手（−194cp） | △4二銀 / △4二銀 | △4二銀 | △4二銀 |
| `deep16` | **2位 / 46手（−23cp）** | **△8六歩打 / △8六歩打** | **△8六歩打** | **△8六歩打** |

**確認済み**：探索コードを変えていないのに、重みの交換だけで手が変わった。`deep16`は△8六歩打を静的な入口ですでに上位へ押し上げ、固定深さ11・12、2000ms、4000msのすべてで選択した。`runOp1`は同じ手を16位まで下げ、全条件で△4二銀を選んだ。

ここでcpの絶対値を「真の形勢」と読むべきではない。重要なのは、同じ候補集合に対する**モデル間の相対順位と、その順位が探索の着手へつながったこと**である。この局面については、「deep16で少し評価が変わった可能性」ではなく、モデル固有の回帰を再現できた。

### 再現コマンドの概要

採用コミット`27041d3`の直前がrunOp1、同コミットがdeep16である。以下は2つの重みを取り出し、既存のspot-checkツールへ31手目までのUSI手順を渡す例だ。

```bash
git show 27041d3^:public/shogi-nnue-weights.bin > /tmp/runOp1.bin
git show 27041d3:public/shogi-nnue-weights.bin  > /tmp/deep16.bin

MOVES="2g2f 8c8d 2f2e 8d8e 6i7h 4a3b 2e2d 2c2d 2h2d P*2c 2d2h 8e8f 8g8f 8b8f P*8g 8f8d 3i3h 3c3d 5i6h P*8f 8g8f 8d8f P*8g 8f8d 3h2g P*8f 8g8f 8d8f P*8g 8f8e 2g2f"

node -r tsx/cjs wasm-spike/probe-nnue-position.ts \
  --weights /tmp/runOp1.bin \
  --weights /tmp/deep16.bin \
  --moves "$MOVES" --ms 2000 --depth 32 --top 46

node -r tsx/cjs wasm-spike/probe-nnue-position.ts \
  --weights /tmp/runOp1.bin \
  --weights /tmp/deep16.bin \
  --moves "$MOVES" --ms 4000 --depth 32 --top 46

node -r tsx/cjs wasm-spike/probe-nnue-position.ts \
  --weights /tmp/runOp1.bin \
  --weights /tmp/deep16.bin \
  --moves "$MOVES" --ms 0 --depth 11 --top 46
```

このツールは定跡と外付け詰みルーチンを通さず、production系のNNUE/WASM探索を直接使う。そのため「どの重みが手を押し上げたか」の単離に向く。時間制限探索の到達深さはマシン負荷で変わるが、`--ms 0 --depth 11`なら時間切れなしの固定深さで同じproduction系経路を通せる。**確認済み**：固定深さ11と12でもrunOp1は`3a4b`、deep16は`P*8f`を選んだ。

この結果をその場限りのログにしないため、本番重みをrunOp1のSHA-256 `e4e738f99fbd8685bcfe2700e4df364af6274e75b44b298432fc313b9a3e28dc`へpinし、固定深さ11で`3a4b`をassertするunit testも追加した。deep16の重みに戻すとこのテストは`P*8f`を選んで失敗する。これで機械速度に依存しない回帰ゲートになった。

## 3. なぜ800ms・40局のA/Bは見逃したのか

deep16採用前に残した集計は次の通りだった。

| 指標 | runOp1 | deep16 |
|---|---:|---:|
| holdout MAE | 476.1cp | 443.2cp |
| holdout `pair_acc` | 0.9001 | 0.9031 |
| 800ms A/B、40局 | — | 52.5% |
| A/Bの95%区間 | — | 約37〜68% |

当時はこれを「典型中盤の較正が少し改善し、A/B互角なので退行なし」と読んだ。前半は限定付きで正しいが、後半は統計の読み方を間違えている。

### 3.1 「有意差なし」は「同等」の証明ではない

**確認済み**：52.5%の周りに約37〜68%という広い区間がある。真の強さがかなり悪い場合も、かなり良い場合も、この40局では排除できない。「差を検出できなかった」のであって、「退行がないと確認した」のではない。

同等性を主張したいなら、事前に許容する退行幅を決め、その幅を排除できる局数を用意する必要がある。単に50%をまたぐ区間を見て「安全」とするのは、採用ゲートにならない。

### 3.2 本番と違う時間帯を測っていた

**確認済み**：今回の報告局面では、800msでは△8六歩打が出ず、2000ms・4000msで出た。評価が同じなら長く読めば必ず良くなる、とは限らない。探索深さが変わると、静的評価が効く葉、枝刈り、候補順、PVが変わり、特定のバイアスが深い時間帯で初めて着手へ現れることがある。

したがって、800msのマッチだけでhard相当の2000ms以上を承認したこと自体がテスト設計の不一致だった。短時間テストは候補のふるい分けには使えても、本番ゲートの代わりにはならない。

### 3.3 平均勝率は「この壊れ方」を直接測らない

**仮説**：40局の開始局面と展開に、今回のような「歩交換を繰り返せるが盤面は少しずつ変わる局面」がほとんど含まれなかった可能性が高い。集計勝率は多くの局面を1つの数字へ潰すため、低頻度でも体感を大きく壊す手を見逃し得る。

今後はA/Bの代わりに局面テストを使うのではなく、役割を分ける。局面テストは既知の回帰を二度と通さない。十分な本番時間A/Bは全体強度を見る。人間とのlive実戦は、機械生成の分布が外した問題を発見する。3つとも必要だ。

## 4. 学習パイプラインを読むと、「強い手を真似ていない」ことがわかった

現在のデータ生成は、弱いラベルを使っているわけではない。局面の採点にはやねうら王を使っている。問題は、**何を生成し、教師から何を受け取り、そのうち何を学習へ渡しているか**だった。

```text
自作AIの低budget自己対戦
        + 既定20%のランダム着手
                 │
                 ▼
             親局面SFEN
                 │
        やねうら王が局面を採点
          cp + bestmove を保存
                 │
                 ▼
       train.py は SFEN + cp だけ読む
                 │
                 ▼
       小型value netが1つの数値を回帰
```

### 4.1 局面分布は自作AIが決めている

`ml/generate-teacher.ts`の既定値は、深さ4・短時間の自作AIで手を選び、`epsilon=0.2`で合法手をランダムに指す。やねうら王が後から正しい評価値を付けても、**どの局面が多く、どの構想が少ないか**は生成側の癖を引き継ぐ。

ランダム局面や悪手後の局面が無価値なわけではない。実戦で崩れた後の回復力には必要である。しかし、それが強い将棋の主分布を置き換えると、強豪が実際に比較する微妙な中盤候補が薄くなる。

### 4.2 `bestmove`を保存して、捨てている

生成JSONLには`{sfen, cp, ply, bestmove, depth}`が入る。しかし`ml/train.py`のローダーは`rec["sfen"]`と`rec["cp"]`だけを読む。**確認済み**：やねうら王が選んだ手は、現在の損失へ一度も入らない。

つまり「強いAIがこの局面で何を指したか」を模倣しているのではない。「強いAIがこの局面全体へ付けた1つの数値」を、`2282 → 256 → 32 → 1`の小型ネットで近似している。価値学習として間違いではないが、作者が期待していた「強い棋譜と同じ手を選べるようにする学習」とは別物だった。

### 4.3 `pair_acc≈0.90`は候補手選択の90%正解ではない

`train.py`はvalidation集合からランダムに2局面を選び、教師cp差が100を超えるペアについて大小関係が合う率を出す。ranking lossを有効にしても、比較対象は同じミニバッチに偶然入った別々の局面である。

**確認済み**：親局面IDも候補手グループも存在しない。したがって0.9031という値は、「局面Aと無関係な局面Bのどちらを教師が高く見るか」を約90%の率で並べられた、という意味に限られる。「32手目で△8六歩打より△4二銀を上に置けた」確率ではない。

ここが今回の指標と実戦の断絶だった。探索が必要とするのは、ある親局面から生じる似た子局面同士の細い差である。現行指標は、まったく違う局面同士の大きな差でも稼げる。

### 4.4 deep16の誤りを何が作ったか

- **確認済み**：deep16は報告局面で△8六歩打の順位をrunOp1より大幅に上げた
- **確認済み**：全体holdout MAEはrunOp1より改善した
- **仮説**：深い再ラベルとデータ混合が全体回帰を改善する一方、この局面周辺の候補順位を壊した
- **仮説**：小型ネットの容量と約443cpのMAEでは、探索で重要な近接候補の差を安定して保持しにくい
- **未検証**：どの学習データ群、損失、または量子化差が△8六歩打の上昇へ最も寄与したか

原因をまだ1つに絞れていないことと、回帰が存在することは両立する。事故の再現は完了した。根本原因のアブレーションは次の仕事である。

## 5. 「強い棋譜を学ぶ」を、この探索器に合う形へ変換する

作者の案は正しい。主な親局面を弱い自作AIではなく、強豪同士が実際に到達した棋譜から取る。たとえば[Floodgateの公開対局アーカイブ](https://wdoor.c.u-tokyo.ac.jp/shogi/x/)には年別の棋譜がある。

ただし、棋譜の実戦手だけをそのまま正解ラベルにすると、1局面につき正例が1つしかない。なぜ他の手が悪いか、2番手との差が何cpかは分からない。さらに、実戦手はその対局の持ち時間で選ばれた手であり、後日の深い教師解析で常に1位とは限らない。

そこで、棋譜は**親局面の質を上げるため**に使い、指し手の教師は各親局面で作り直す。

### sibling候補データ

1つの親局面ごとに、最低でも次を候補集合へ入れる。

- 棋譜で実際に指された手
- やねうら王の最善手とMultiPV上位手
- 安定版runOp1が選ぶ手
- 新しい候補モデルが選ぶ手
- deep16が選ぶ手
- △8六歩打のように実戦で発見した既知の悪手
- 必要に応じ、王手・取り・受けなどの戦術候補

各候補を指した**子局面**を、同じ教師設定で採点する。データは次のような親子構造を持つ。

```json
{
  "parent_id": "game-id:ply-31",
  "parent_sfen": "...",
  "move": "P*8f",
  "child_sfen": "...",
  "sources": ["deep16", "field_failure"],
  "teacher_cp": -412,
  "teacher_rank": 9,
  "teacher_engine": "YaneuraOu+eval-id",
  "teacher_limit": { "depth": 18, "multipv": 12 }
}
```

数値はスキーマ例であり、△8六歩打の教師値ではない。重要なのは`parent_id`で候補を束ねること、手番視点を統一すること、教師の評価ファイルと探索条件を記録することだ。

学習では局面価値の回帰を残しつつ、同じ`parent_id`内でのみpairwiseまたはlistwise ranking lossを掛ける。validationも親単位で分割し、同じ親の兄弟がtrainとvalidationへ漏れないようにする。新しい主要指標は、sibling内のtop-1一致率、教師上位手のrecall、既知の悪手を最善手より下へ置けた率になる。

### DAgger型ループ：自作AIは「問題作成者」にする

強豪棋譜だけに限定すると、AIが一度間違えて棋譜分布から外れた後の局面が足りなくなる。そこで候補モデルにも対局させ、そのモデルが実際に到達した局面を回収する。ただし以前と役割が違う。

```text
候補モデルが到達した局面
        │
        ├─ 安定版／教師と同じ手 → 低優先度
        │
        └─ 手が割れた・評価が急落 → 高優先度でsibling採点
                                      │
                                      ▼
                              集約データへ追加
```

これは[DAgger](https://arxiv.org/abs/1011.0686)の「学習者自身が誘発する状態分布で教師ラベルを集約する」考え方に近い。自作AIの手を正解としてコピーするのではない。自作AIには、自分が失敗する局面を提出させ、答えは強い教師に付けさせる。

## 6. 上書きではなく、安定版・継続学習版・scratch版を並べる

本番ファイルへ直接再学習結果を上書きするのはやめる。成果物は不変の名前とメタデータを持ち、比較に合格したものだけを昇格する。

### 推奨する3本

| 系列 | 初期値 | 目的 |
|---|---|---|
| stable | `runOp1` | 即時の安全な基準、本番ロールバック先 |
| warm-start | `runOp1` | 既存の広い知識を保ち、低い学習率でsiblingデータへ適応 |
| scratch | 乱数初期化 | runOp1の古い癖を引き継いでいない対照実験 |

**確認済み**：現在の`train.py`は毎回`DistillNet(...)`を新規生成し、checkpointを初期値として読む機能がない。したがってwarm-startには、まず明示的な`--init-checkpoint`相当を実装する必要がある。

deep16を初期値にしないのは、今回直したい候補順位がすでに内部化されているからである。もちろんdeep16からでも十分な反例で直る可能性はあるが、安定版から始めるより余分なリスクを負う理由がない。

旧データをすべて捨てる必要もない。終盤、大差局面、悪手後などのカバレッジを保つreplayとして混ぜる。ただし新しいsiblingデータとの比率を固定し、データ群ごとのvalidationを別々に出す。全体平均が改善して実戦分布だけ壊れる事故を、もう一度平均で隠さないためである。

## 7. 回復計画と採用ゲート

### Phase 0 — 安定化

- 本番のNNUE重みだけをdeep16からrunOp1へ戻す
- Improvedの探索器、UI、定跡などは同時に巻き戻さない。変数を1つにする
- deep16のバイナリ、メタデータ、採用時ログは削除せず、回帰資料として保存する
- production重みのSHA-256をrunOp1へpinし、32手目直前を固定深さ11の回帰fixtureにする

### Phase 1 — データ基盤

- 強豪棋譜を取り込み、重複排除した`parent_id`付き親局面を作る
- 棋譜実戦手、MultiPV、runOp1、新候補、既知の失敗手からsibling集合を作る
- 合法手、手番視点、教師バージョン、探索条件を保存する
- 棋譜の利用条件、収集期間、エンジン強度フィルタを確定する

### Phase 2 — 学習

- value regressionとparent内rankingを併用する
- runOp1 warm-start版とscratch版を同一split、同一seed群で学習する
- 旧データreplay比率を変えたアブレーションを行う
- 量子化前後でsibling順位が変わっていないか測る

### Phase 3 — オフライン採用ゲート

| ゲート | 何を見るか |
|---|---|
| データ整合性 | 合法手、視点、重複、親単位のtrain/validation分離 |
| sibling holdout | top-1、教師上位手recall、parent内pair accuracy |
| 既知回帰suite | 32手目で△8六歩打を安定版の良手より下へ置くか |
| 探索suite | 800/2000/4000msと固定深さで悪手を選ばないか |
| 全体value | 従来holdoutのMAE・符号・決着圏を壊していないか |
| 対局 | 本番と同じ経路・持ち時間・十分な局数で区間推定 |

局数は「30局」「40局」の慣習で決めない。許容する退行幅と検出したい改善幅を先に決め、必要なサンプル数を設計する。結果は点推定だけでなく区間で出す。合格条件も実験前に固定する。

### Phase 4 — live

- 重みhash、worker起動、WASMロード、使用スレッド数、fallback理由、深さ、評価値、経過時間を診断ログへ出す
- production URLを実ブラウザで開き、非定跡局面を最後まで指させる
- 評価表示、思考タイマー、選択手、コンソールエラーを同時に記録する
- 段階リリースし、問題時は重みだけ即時にstableへ戻せるようにする

## 8. 評価回帰とlive UI障害を混ぜない

同じ実戦報告の中で、作者は「評価値が`—`のまま」「AIが考えていますのタイマーが0.4秒付近から増えない」「マルチスレッドが動いていないように見える」とも報告した。これらは深刻だが、△8六歩打の評価回帰と同じ原因だと決めてはいけない。

### 現時点の証拠

- **確認済み**：作者のlive環境では、少なくとも報告時に上記3症状が同時に見えた
- **確認済み**：別のproductionブラウザ確認では、非定跡hard探索が約3.5秒、深さ13、評価値−183で完了し、タイマー表示も0.7→3.3秒へ進んだ
- **結論できること**：workerが全ブラウザ・全時点で必ず壊れる、とは言えない
- **仮説**：worker失敗後に同期JSフォールバックへ落ちると、評価値欠落・UIタイマー停止・浅い探索をまとめて説明できる
- **未検証**：作者が失敗を見たそのセッションで、実際にどの経路へfallbackしたか。診断ログがなかったため確定できない

したがって作業を2レーンに分ける。

| レーン | 失敗 | 主な検証 |
|---|---|---|
| 将棋の判断 | deep16が△8六歩打を高く置く | 固定局面、sibling順位、探索、対局 |
| 実行と表示 | 評価値`—`、タイマー停止、worker/fallback | 実ブラウザ、console、telemetry、経路表示 |

runOp1へ戻してもworkerの起動は直らない。workerを直してもdeep16の候補順位は直らない。PRも検証結果も分けることで、「画面が動いたから強くなった」「手が変わったからUIも直った」という誤認を防ぐ。

## 9. 途中時点の証拠台帳

| 主張 | 状態 | 根拠／次の確認 |
|---|---|---|
| 20・26・32手目は千日手ではない | **確認済み** | 銀・飛車位置が異なる |
| deep16が報告局面で△8六歩打を押し上げた | **確認済み** | 静的2/46、固定深さ11/12・2000/4000msで選択 |
| runOp1は同じ局面でその手を抑える | **確認済み** | 静的16/46、固定深さ11/12・2000/4000msは△4二銀 |
| deep16は全体EloでもrunOp1より弱い | **未検証** | 本番条件・十分な局数が必要 |
| 800ms・40局は退行なしを証明した | **否定** | 95%区間が約37〜68%、本番時間不一致 |
| 現学習がbestmoveを利用する | **否定** | JSONLにはあるが`train.py`が読まない |
| `pair_acc≈0.90`が同一局面の手選び精度を表す | **否定** | 無関係なvalidation局面のランダムペア |
| 強豪棋譜+sibling学習が実戦を強くする | **未検証** | 次サイクルでwarm/scratch比較 |
| 自作AI局面はすべて捨てるべき | **否定** | DAgger型の失敗局面収集には必要 |
| liveの全環境でworkerが壊れている | **否定** | 少なくとも1ブラウザでは完走 |
| 報告時のUI障害はfallbackが原因 | **仮説** | 失敗セッションの経路ログが必要 |

### まだ決めていないこと

- どの棋譜群を使うか、利用条件をどう満たすか
- MultiPVを何本、どのdepth/nodesで採点するか
- sibling lossの重みと旧データreplay比率
- warm-startとscratchのどちらが最終的に強いか
- 量子化後のネット容量を維持するか増やすか
- hardの正式な非劣性幅と必要対局数

未決定事項を空欄のまま見せる。ここを「たぶん大丈夫」で埋めたことが、deep16採用時の失敗だった。

## 10. 今回の結論

deep16は、全体holdoutではrunOp1より教師へ近づいた。それでも、作者の実戦で問題になった32手目では、runOp1が避ける△8六歩打を2位へ持ち上げ、本番相当の探索に選ばせた。**近似精度の改善と、必要な候補手順位の改善は同じではない。**

そして、「同じ手が3回」から「千日手」と飛びついた診断も間違っていた。棋譜では銀と飛車が動き、局面は変わっていた。最初にやるべきだったのは一般論を当てはめることではなく、各回の盤面差を表にし、旧・新の重みだけを交換して比較することだった。

ここからの順番は明確になった。

1. 重みだけrunOp1へ戻し、悪化を止める
2. 強豪棋譜から良質な親局面を取る
3. 同一親局面のsibling候補を強い教師で比較する
4. 自作AIは、自分の失敗局面を提出する役に変える
5. warm-start版とscratch版を別成果物として競わせる
6. 固定回帰局面、本番時間A/B、liveブラウザを別々のゲートにする

これは「強い棋譜をコピーすれば終わり」というほど単純ではない。しかし、今までのようにbestmoveを保存して捨て、無関係な局面の`pair_acc`を見て「手選びも良くなった」と期待するより、目的に直接つながっている。

次のモデルを採用するときに必要なのは「52.5%だから退行なし」という物語ではない。△8六歩打をどこへ順位づけたか、同じ親局面の候補をどれだけ正しく並べたか、本番時間で区間が何を排除できたか、そして実ブラウザでどの実行経路が動いたか。その4つを、途中データごと残す。
