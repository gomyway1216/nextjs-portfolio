# 将棋AIの評価関数を立て直せるか――2つの再学習パイロットを、失敗も含めて全部記録する

> 先に結論を書く。今回の2つのパイロットでは、**高段レベルの棋力は証明できなかった**。どちらも事前に決めた静的ゲートで不合格になり、対局試験へ進めていない。したがって「AIが強くなった」「何段になった」「何Elo上がった」とは言えない。本番の評価関数も1バイトも変更していない。

関連する以前の記事は「[ブログの将棋AIが弱すぎたので、AIエージェント群に1日で作り直させた話](./blog-shogi-ai-rebuild.md)」。今回は、その後に「いまの弱い評価関数へ積み増すのか、一から作り直すのか」を改めて検証した記録である。

---

## TL;DR

- 現行と同じ1,185,988バイトのNNUEを、全合法手の教師データで追加学習する「本命パイロット」は、価値誤差を改善した一方、最重要の最善手一致が **63/643 → 61/643** に悪化して棄却した
- 現行NNUEを凍結し、親局面と指し手を明示的に見る70,614バイトの補助ヘッドを足すパイロットは、V9分布では改善したが、全合法手のブラウザ分布では最善手一致が **63/643 → 63/643** のまま。必要な96局面へ届かず棄却した
- どちらも「学習が動かなかった」わけではない。損失や一部指標は改善した。しかし、**改善した代理指標と、必要な指し手選択能力が一致しなかった**
- 実行前に、プロトコルのキー不一致、本番WASMと異なる丸め、別ゲーム間の同一局面漏洩を発見した。これらの修正は棋力を直接上げないが、誤った合格や無駄な学習を防いだ
- 事後にseed、epoch、閾値を足して合格するまで回すことはしない。この2レシピは終了し、本番重みは変更しない
- 次は、同じ小型表現を微調整し続けるのではなく、**十分大きいモデルで全合法手問題を本当に学習できるかを先に診断し、学べると確認できた場合だけ圧縮する**のが筋である

## 1. 今回、何を確かめたかったのか

これまでの学習では、強い教師の評価へ近づいたように見えても、実際の最善手一致や直接対局で伸びないことがあった。そこで今回は、「大量データを入れれば強くなるはず」という期待をそのまま信じず、異なる仮説を持つ2本だけを事前登録した。

### パイロットA：現行NNUEを全合法手データで直接追加学習

現行と同じ `2282 → 256 → 32 → 1` の1バケットboard NNUEを使い、本番チェックポイントから開始する。教師が候補を数手だけ出したデータではなく、各親局面の**全合法手を独立に深さ12で評価したデータ**を与えた。

狙いは単純である。過去のデータが「候補手の一部」しか見ていなかったせいで悪手を区別できないなら、全合法手を見せれば同じ小型評価関数でも立て直せるかもしれない。

ただし、指し手順位だけへ寄せて局面評価を壊さないように、50万局面のvalue replayと2,959局面のvalue preservationも併用した。実験条件と停止条件は [board all-legal warm-start protocol](../ml/protocols/board-all-legal-warmstart-v1-plan.json)、実装は [train_board_all_legal_warmstart.py](../ml/train_board_all_legal_warmstart.py) に固定した。

### パイロットB：現行NNUEを凍結し、root指し手順位だけ補正

もう一つは評価関数本体を書き換えず、

```text
親から見た手の点数 = -現行NNUE(子局面) + residual(親局面, 指し手)
```

とする案である。

過去に失敗したfeature hash型の線形ヘッドとは違い、盤上の駒位置、持ち駒、移動元・移動先、駒種、成り・取り・打ち、両玉との位置関係、近傍駒などを衝突なしで明示的に入力した。35,307パラメータ、量子化後70,614バイトで、用途はrootの指し手順序だけ。葉評価や置換表の値には入れない設計である。

V9の23,807親局面と、全合法手データの1,220親局面を使い、両分布のtune成績の悪い側を優先してepochを選んだ。条件は [listwise policy/value protocol](../ml/protocols/listwise-policy-value-v1-plan.json)、実装は [train_listwise_policy_value.py](../ml/train_listwise_policy_value.py) と [listwise_policy_value.py](../ml/listwise_policy_value.py) に固定した。

## 2. 学習前に見つかった3つの不具合

今回は「学習が完走したか」より先に、「その数字は本番と同じ意味か」「検証データが混ざっていないか」を確認した。この段階で3件止まった。

### 2.1 プロトコルのsemantic overlapキーが実装と一致していなかった

初期のwarm-start計画には、データmanifestが持つsemantic overlapの項目名と、検証器が読む項目名のずれがあった。正しい `training_validation_semantic_union_overlap` に統一し、訓練と検証の親・子局面unionが0件重複であることを実manifestから確認した。

キー名だけの問題に見えるが、ここがずれると「漏洩0を確認したつもりで、別の項目を見ていた」状態になる。棋力を上げる変更ではないが、検証の意味を守るために必要だった。

### 2.2 Python側の量子化スコアが、本番WASMと違っていた

当初のPython評価は `out_q / 8128` という連続値を使っていた。一方、本番WASMは次の整数CPを使う。

```text
cp_int = trunc_toward_zero(out_q * 600 / 8128)
```

ゼロ方向への切り捨てにより同点が増えるため、最善手一致、Recall、pair accuracyが変わる。実際、全合法手643親のpair50 baselineは、連続値では0.6679618だったが、本番と同じ丸めでは**0.6675555**になった。

そこでcandidate、live baseline、export round-tripのすべてを本番と同じ整数変換へ統一し、登録済みbaselineとの照合をoptimizer作成前へ移した。これでbaselineが1項目でもずれれば、学習に入る前に止まる。

### 2.3 ゲームを分けても、同一局面がfit/tuneをまたいだ

residualの最初の起動は、optimizer作成前にsemantic leakageを検出して停止した。ゲームIDを分けただけでは、別ゲームに同じ親局面・子局面が現れたときにfitとtuneへまたがるからである。

修正後は、同じゲーム、または同じ親・子局面IDを1つでも共有する親局面を連結成分としてまとめ、成分全体をfitかtuneのどちらか一方へ決定的に割り当てた。

- V9：1,000成分。fit 19,459親／816ゲーム、tune 4,348親／184ゲーム
- browser：29成分。fit 922親／25ゲーム、tune 298親／13ゲーム
- 両方ともゲーム重複0、semantic position重複0

これは過剰な手続きではない。漏洩したtuneでepochを選べば、未見局面へ一般化したように見える数字を簡単に作れてしまう。

## 3. パイロットAの結果：価値は改善、指し手順位は不合格

使用したデータは次の通り。

| 用途 | 規模 |
|---|---:|
| 全合法手train | 112,011行・1,334親 |
| 全合法手reject validation | 57,658行・643親 |
| value replay | 500,000局面 |
| value preservation | 2,959局面 |

訓練中はvalidationを一度も見ず、事前に決めた第3 epochだけをcandidateにした。MPSでのepoch時間は **25.5209秒 + 11.8870秒 + 10.9467秒 = 48.3547秒**。これはデータ読込・検証などの前処理後に記録された訓練ループ時間であり、作業全体の経過時間ではない。

### 3.2 何が分かったか

「学習率が小さすぎて何も学んでいない」という結果ではない。train lossは0.8154 → 0.7540 → 0.7292と低下し、value loss、MAE、Recall@3、Pair200も改善した。

それでも最善手一致は悪化した。つまり、この小型board表現と今回の複合損失では、局面価値を滑らかに近づけることと、全合法手から最善手を選ぶことが同じ方向へ進まなかった。データを増やした事実だけでは、必要な棋力指標の改善を保証しない。

## 5. 何が役に立ち、何が棋力を上げなかったか

### 役に立ったもの

- 本番WASMと同じ整数丸めでbaselineとcandidateを比較できるようになった
- 親局面＋指し手から宣言された子局面へ本当に遷移することを検証し、データの対応関係を固定した
- reject set、訓練分布、fit/tune間の親・子局面漏洩を0にした
- 分割をゲーム／局面連結成分単位にし、再現可能なSHA-256レシートを残した
- live baselineのずれをoptimizer作成前に検出するようにした
- floatでは良く見えるが、本番量子化後に崩れるcandidateを通さないexport/parityゲートを作った
- 「valueは改善したが最善手選択は改善しない」「V9では改善するが全合法手では改善しない」という、次の設計判断に使える負の結果を得た

これらは重要だが、**それ自体は一手も強くしない**。強くなったことを証明するのは、未見データの合格と、その後の本番条件での直接対局である。

### 棋力を上げなかったもの

- 現行小型NNUEへ、同じ表現のまま全合法手データを追加学習するレシピ
- 現行NNUEへ、今回の73入力・32 hiddenのresidualヘッドを足すレシピ
- train loss、value loss、一部pair指標だけを見て「全体も強くなった」と判断すること
- V9だけの改善を、browser全合法手問題の解決と読み替えること
- 合格するまでseed、epoch、閾値を後付けで増やすこと

## 6. なぜここで止めるのか

両プロトコルには、失敗後に追加seed、追加epoch、学習率変更、損失重み変更、閾値変更、教師追加をしないと先に書いた。結果を見た後で条件を変えると、643親の既知reject setへ人間が過学習するからである。

そのため今回の判断は次の通り。

- board warm-startレシピ：終了。screen56へ進めない
- explicit residualレシピ：終了。WASM統合・対局へ進めない
- 本番 `public/shogi-nnue-weights.bin`：変更しない
- 本番WASM・worker：変更しない
- ライブ重み：実行前後とも1,185,988バイト、SHA-256 `e4e738f99fbd8685bcfe2700e4df364af6274e75b44b298432fc313b9a3e28dc`

これは「AIを強くするのは不可能」という結論ではない。「**この2つの小型レシピでは、必要な改善を確認できなかった**」という限定された結論である。

## 7. 次に進むなら

今回の共通した失敗は、データ読込や量子化ではなく、全合法手から最善手を選ぶ能力がほとんど伸びなかったことだった。次の一手は、同じ小型モデルを微調整し続けることではない。

まず、配布サイズを気にしない十分大きなofflineモデルで、同じ全合法手問題を学習できるかを診断する。

1. 玉位置を含む豊かな局面表現と、親局面＋指し手を直接扱う大きなpolicy/valueモデルを用意する
2. 既存のtrain/tuneだけでcapacity testを行い、browser tuneのTop-1が明確に動くか確認する
3. 大型モデルでも動かなければ、表現ではなく教師深度、ラベル、損失、局面分布を疑う
4. 大型モデルで動くなら、その教師を小型NNUEやpolicy headへ蒸留・量子化する
5. 既に数字を見た643親とは別の、新しいsealed holdoutを一度だけ評価する
6. 静的ゲートを通ったcandidateだけを、本番と同じWASM、持ち時間、色替えopening pairで直接A/Bする

この手順でも高段レベルは保証できない。しかし、今回の数字から最も合理的に言えるのは、「小さい器へ同じ学習を足す」前に、**そもそも十分な器なら問題を学べるのかを確認すべき**ということだ。

今回の2本は採用candidateを生まなかった。ただし、失敗を成功に言い換えず、どこまで改善し、どこで止まったかを数値で固定できた。次の計算資源は、その境界を越えられる仮説だけに使う。

全入力・artifactのSHA-256、分割レシート、学習時間、静的ゲートの機械可読証跡は [shogi-evaluator-recovery-two-pilots-2026-07-26.json](./data/shogi-evaluator-recovery-two-pilots-2026-07-26.json) に固定した。
