# 評価関数を触らずに強くできるか：128 KiB手順並べ替えヘッドの実験

> 評価関数の追加学習が実戦棋力へつながらなかったため、別の仮説を1つだけ試した。深い教師が好む合法手を軽量モデルで先に並べれば、alpha-beta探索が同じ時間で深く読めるかもしれない。64世代の学習は約2分30秒で終わったが、事前に決めた静的基準を通らなかった。探索への組み込み、対局、ライブ変更は行っていない。

## 結論

- ライブAIはこの実験では強くなっていない
- 本番NNUE、TypeScript探索、WASM、`public/shogi-nnue-weights.bin`は変更していない
- 128 KiBへの量子化は成功し、floatからの劣化はほぼゼロだった
- しかし643局面の最善手一致は **71/643 = 11.04%**。必要な **99/643 = 15.40%**へ届かなかった
- 50 cp以上離れた手の順序一致も **66.34%**。必要な **68.96%**を下回った
- 別分布4,798局面では、現行scalar評価に対して最善手一致が **30.39% → 26.84%**、pair一致も **59.38% → 56.87%**へ悪化した
- 同じ特徴・損失のseed追加、epoch延長、探索組み込みはしない

## なぜこの実験をしたか

これまでの学習は、1局面に1つの評価値を返すNNUEを微調整していた。しかし局面評価が少し良くなっても、実戦で選ぶ手が変わらなかったり、直接対局で優位を示せなかった。

alpha-beta探索には別の強化経路がある。良い手を先に読むと、後続の枝を早く捨てられる。評価関数を置き換えなくても、手の順番だけで同じ深さの探索ノードを減らせる可能性がある。今回はこの仮説を、既存評価関数と完全に分離した小さなモデルで試した。

```text
現在局面 + 合法手
        │
        ▼
128 KiBの手順並べ替えヘッド
        │
        ▼
有望そうな順に並べる
        │
        ▼
既存NNUEと既存探索で読む
```

静的指標が通った場合だけ、研究用WASMのrootでON/OFF比較をする計画だった。本番探索を先に変更しなかったのは、学習が弱ければ速度測定や対局が追加の無駄になるためである。

## データとモデル

教師データは各親局面の全合法手をdepth 12で評価したbrowser-confusion集合である。学習側は112,011手・1,334親・38局、検証側は57,658手・643親・15局。さらに別分布として、depth 14で候補を出しdepth 16で再評価した28,518手・4,798親・200局を使った。

学習中の選抜は棋譜単位で分離した1,031親をfit、303親をtuneに使った。公開済み643親と外部4,798親はepoch選抜には使っていない。

モデルは65,536個の符号付きhash bucketを持つ線形ヘッドである。駒、移動元、移動先、駒取り、成り、打ち、玉との相対位置、周辺8マスなどを約30〜46個の特徴へ展開し、後手番は盤と手を180度回転して正規化した。実行時はint16の表引きとint32の加算だけで、出力はちょうど131,072 bytesである。

## 時間

| 工程 | 実測 |
| --- | ---: |
| データ読込 | 6.04秒 |
| 64世代からepoch選抜 | 120.29秒 |
| 選ばれた11世代を全学習データで再学習 | 19.99秒 |
| 合計 | **146.31秒** |

長い生成や複数seedは行っていない。今回は先に短い拒否ゲートを置いたため、約2分30秒で仮説を落とせた。

## 結果

| 指標 | 現行scalar基準 | 手順ヘッド | 合格線 | 判定 |
| --- | ---: | ---: | ---: | --- |
| 643親の最善手一致 | 66 / 643（10.26%） | 71 / 643（11.04%） | 99 / 643（15.40%） | 不合格 |
| 643親の50cp pair一致 | 66.96% | 66.34% | 68.96% | 不合格 |
| int16化によるtop-1損失 | — | 0親 | 最大1親 | 合格 |
| int16化によるpair低下 | — | 0.00277ポイント | 最大0.1ポイント | 合格 |
| artifactサイズ | — | 128 KiB | 最大128 KiB | 合格 |

狭い643親では現行scalarより最善手が5親だけ増えたが、重要なpairの向きは0.62ポイント悪化した。さらに独立した4,798親では、現行scalarより最善手一致が170親減り、pair一致も2.51ポイント悪化した。再学習に使った1,334親ではtop-1が32.76%なのに、643親では11.04%まで落ち、21.72ポイントの汎化差があった。狭いデータへの小さな改善を、汎化した強さとは扱えない。

実行後の独立監査で、最初の集計コードが「予測同点のpairを0.5正解」と数え、比較対象のstrict判定と一致していないことを発見した。元のv1 protocolはhashを含めて変更せず保存した。そのうえで、学習条件と合格線を一切変えず、strict pair・tie-safe top-1・漏洩集計を組み込んだv2をfreshに再実行した。表はv2の結果である。補正前後とも不合格で、結論は変わらなかった。

## 何が原因だったか

容量や量子化が原因ではない。floatとint16は最善手71親で一致し、pair差も実質ゼロだった。失敗は量子化より前に起きている。

この線形特徴は、駒と手の局所的な形は読めても、「この手の後に相手がどう応じ、その先の評価がどう変わるか」を計算しない。打ち手が全候補の55%以上を占めるデータでは、局所特徴だけで多数の似た打ち場所を分けるのも難しい。また、643親の狭い集合で少し上がっても、別分布4,798親で逆転したため、分布依存も強い。

したがって「tableを1 GBへ増やせば解決する」とは言えない。現在の128 KiBで量子化誤差は消えており、同じ情報を大きな表へ入れるだけでは、欠けている先読み情報は増えない。

## 次に残る筋

同じレシピの再試行は終了する。次は、評価関数をまた小幅に微調整するのではなく、既存評価のまま到達深度を増やせる探索側の改善を優先する。候補はWASM内の手生成・合法性判定・探索順序の実測で、必ず固定局面・固定depthのノード数と時間を先に測る。

ここでも静的な速度だけで棋力向上とは呼ばない。速度と手品質の基準を通った変更だけをfreshな直接対局へ進め、そこで優位を示した場合だけライブ候補にする。

生データの件数、hash、全ゲートは [`docs/data/shogi-move-order-head-pilot-v2.json`](data/shogi-move-order-head-pilot-v2.json) に記録した。
