## 1. 症状：同じ「変な手」を何度も指す

きっかけは作者の実戦報告だった。ハードモード（持ち時間約2秒）でこう進む：

```
▲７六歩 △８四歩 ▲２六歩 △８五歩 ▲７七角 △３四歩 ▲６六歩 △８四飛
```

8手目の**△８四飛**。飛車を一段浮かせる「浮き飛車」は、それ自体は立派な戦法だが、**この局面のこのタイミングでは早すぎる**。二段の作者から見て明確に感触が悪い。しかも別の相掛かりの将棋でも、似た筋の緩い手が出る。

まず、この手が本当に悪いのかを客観的に確かめた。プロ級エンジン**やねうら王**（depth24）にこの局面を採点させると：

- 最善は **△３三角**（後手視点 −23cp）
- **△８四飛は −126cp**。最善から**約100cp（歩1枚ぶん）劣り、候補手トップ6にも入らない**

作者の感覚は正しかった。AIは序盤で、計測可能なレベルの劣手を系統的に指していた。

## 2. 容疑者を消していく：推測で直さない

前作で骨身に染みた教訓——**症状から原因を推測すると外す。物証を取れ**——に従って、容疑者を1つずつ潰した。ここで2回、私（調査した本人）は間違えた。その過程も含めて書く。

**容疑者A：定跡ブックが悪い手を持っている？**
このAIには手書きの定跡ブックがあり、収録局面では定跡手を指す。「大きくした定跡に悪い手が混ざったのでは」と最初は疑った。——だが git 履歴を確認すると、**この定跡はやねうら王 depth18 で全手を検証済み（悪手ゼロ）**の方だった。推測は外れ。

**容疑者B：変化（variety）機構が緩い手を選んでいる？**
定跡には「人間らしく手を散らす」ために、最善から一定幅（ハードで140cp）以内の手を許容する仕組みがある。「この許容幅が浅い1手評価と組み合わさって緩い手を通しているのでは」——もっともらしい仮説だが、これも**実測で棄却**された。

**決定打は、実測ハーネス**だった。問題の局面を実際に定跡関数に問い合わせるテストを書いて走らせると：

```
[game A / hard] book returns: NULL (out of book → search)
```

**定跡はそもそも「この局面を知らない」と答えていた（NULL＝定跡外）**。つまり定跡もvariety機構も無罪。△８四飛は、定跡を外れた後の**探索（NNUE評価）が自力で選んだ手**だった。

## 3. 真犯人：NNUEの「序盤バイアス」

なぜNNUEは浮き飛車を選ぶのか。構造的な理由がある。

- **浮き飛車は駒損しない**。1手の駒得・駒損で見れば互角の手
- NNUEは局面を数値にする"目"だが、**学習データの大半は中盤〜終盤**。序盤の「形の良し悪し」——同じ駒割でも、この瞬間の飛車浮きは構想として緩い——という判断は、学習が薄い
- 探索を深くしても、**末端の評価が「ほぼ互角」と言う限り、その先の微差は掘り出せない**

つまりこれは前作の「sigmoid飽和」（終盤の病）と対になる、**序盤の病**だ。飽和は「大差の中の微差が潰れる」問題、こちらは「互角の中の構想の差が見えない」問題。どちらも、**探索ではなく評価（データ）の弱点**である。

## 4. 定跡はどう動いているか（仕組みの話）

対策の前に、定跡がどう引かれているかを正確に書いておく。誤解が多いところだ。

**検索は「局面ハッシュの表引き」**。定跡は「手順のリスト」ではなく、ビルド時に手順を盤上で再生して**局面ハッシュ（Zobristハッシュ）→ 候補手** のハッシュ表に変換してある。実行時は、現在の局面のハッシュで表を引くだけ（O(1)）。

この設計の重要な帰結が2つある：

- **手順前後（トランスポジション）には強い**。違う順序で指しても、**同じ局面に合流すればハッシュが一致してヒットする**。「手順が前後したら定跡が効かなくなる」ことはない
- **本当に知らない局面に来たら、即座に定跡外**。そのときは NULL を返して探索に切り替わる。「全く機能しなくなる」のではなく、AIの生の読みに戻る——ただしそこで §3 の序盤バイアスが顔を出す

つまり定跡の弱点は「引き方」ではなく、**カバーしている局面の数**そのものだ。

## 5. モグラ叩きの実録：1本足したら、1手先に逃げた

真犯人が「定跡の穴」だと分かったので、まず素直に穴を塞いだ。問題の角道相掛かりのライン（▲７六歩△８四歩▲２六歩△８五歩▲７七角△３四歩▲６六歩）に、やねうら王検証済みの **△３三角** を定跡追加。回帰テストも書いて「△８四飛が返らない」ことを機械的に保証した。

数時間後、作者から再報告が来た：

```
8. △３三角  ← 直した手。定跡が効いている
9. ▲２五歩
10. △８四飛  ← また出た
```

**修正は効いていた。しかし1手足りなかった。** 追加したラインは8手目まで。作者が▲２五歩と続けた瞬間、局面はまた定跡外に出て、NNUEが同じ浮き飛車を指した。やねうら王で確認すると、10手目の△８四飛も**−85cp**（最善△６二銀の−27cpから約58cp劣る）で、やはり劣手。

対処として、ラインを**18手目まで**延長し、9手目の別の自然手（▲７八金）への分岐も足した。10手目は△７四歩（エンジン最善）を返すようになり、回帰テストも通った。——だが、ここで認めざるを得なかった：

> **定跡を1本ずつ足すのはモグラ叩きだ。** 塞いだラインの1手先、あるいは隣の変化で、同じバイアスが必ず再発する。カバレッジを「線」でなく「面」にしない限り、この繰り返しは終わらない。

## 6. プロ用エンジンはどうしているか

ここで当然の疑問：**やねうら王のような本物のエンジンは、なぜ序盤で緩い手を指さないのか？**

答えは2段構えだ。

1. **定跡の規模が桁で違う**。公開されている定跡ファイル（やねうら王プロジェクトが配布している「標準定跡」「やねうら大定跡」など）は**数十万〜数百万局面**を収録している。主要な戦型なら序盤20〜30手は定跡内で、そもそも評価関数の出番がない
2. **評価関数も桁違いのデータで学習**しているので、定跡を外れても序盤が破綻しない

うちのAIは、定跡がコード直書きの**数十ライン規模**、NNUEも小型・少データ。**アプローチはプロと同じで、規模だけが小さい**。そして§5の実測が示した通り、この規模差はモグラ叩きでは埋まらない。

もう一つ収穫だったのは、**定跡データが公開資源として存在する**こと。やねうら王プロジェクトの定跡ファイルに加え、**floodgate**（コンピュータ将棋の対局サーバ）の棋譜アーカイブも公開されていて、強豪エンジン同士の序盤を大量に取れる。人力で1ラインずつ書く必要は、最初からなかった。

## 7. 転換：数十ラインから数千〜数万局面へ（進行中）

というわけで、方針を転換した。**定跡を「面」で作る**。

設計はこうだ：

- **データ源**：やねうら王プロジェクトの公開定跡を第一候補として変換（ライセンス確認込み）。不可なら、やねうら王を並列に走らせて自動生成（各局面で depth16〜18・最善から50cp以内の手だけ採用して木を展開）
- **配信方法**：巨大データをコードに直書きせず、**NNUEの重みと同じ「静的ファイル＋起動時fetch」方式**に。目標は gzip後1〜3MB・**5,000〜50,000局面**
- **品質ゲートは不変**：depth18 のサンプル検証で**悪手ゼロ**（最善から100cp超劣る手を入れない）。手書きの検証済みラインは残し、大規模定跡より**優先**して引く
- **フォールバック**：ファイルの取得に失敗しても、従来の手書き定跡だけで動く（劣化なし）
- **ハードは全部使う**：生成・検証は YaneuraOu を複数プロセス並列（10〜12スレッド）で回す

これが入ると、主要戦型は序盤20手前後まで定跡内になり、「緩い手の出番」自体が激減する。モグラ叩き（作者が踏んだ筋を後追いで塞ぐ）から、**最初から面でカバーする**体制への転換だ。

### 7.1 結果：5万局面の定跡が本番に載った

パイプラインは完成し、本番にデプロイされた。結果を数字で書く。

**データ源はやねうら王チームの「新ペタショック定跡」**（世界コンピュータ将棋選手権WCSC35で使われた、233万局面の定跡。**MITライセンスで公開**されており「研究などにご自由にお使いください」と明記——ライセンス確認はこの手の取り込みで最初にやるべき工程だ）。この233万局面から、初期局面に到達可能な序盤（20手以内）を幅優先で辿り、**49,961局面・171,512手**を抽出した。

**配信は静的ファイル844KB（gzip後535KB）**。NNUEの重みと同じく、コードには入れずページ起動時に非同期でfetchする（実測~86ms）。取得に失敗しても手書き定跡だけで従来通り動くので、劣化はゼロ。手書きの検証済みライン（△8四飛の回帰テストの根拠）は**局面単位で常に優先**して引く。

カバレッジはこう変わった：

| | before（手書き） | after（ペタショック取り込み） |
|---|---|---|
| 収録局面 | 数十ライン | **49,961局面** |
| 10手目の局面数 | 数個 | **約1,400** |
| 20手目の局面数 | — | **約5,100** |
| 実測の定跡在局時間 | 数手で外れる | **全難易度で17〜19手目まで定跡内**、変則手順でも13手目まで追随 |

体感も変わる。定跡内の手は**約0.5秒で即応**し（探索なら数秒）、序盤の「緩い手の出番」自体が消えた。

### 7.2 いちばん大事な発見：既製の定跡でも「盲信」はできなかった

ここが今回の山場だった。ペタショック定跡には評価値が付いているので、当初は「付属の評価値でフィルタすれば悪手ゼロにできる」と考えていた。**サンプル検証してみると、それでは足りなかった**——付属評価値だけで通した手のうち**約1.5%が、depth18で測ると最善から100cp超劣る**手だった。定跡の評価値は作られた時点のもので、浅い局面では今のエンジンの判断とズレる。

そこで方針を全数検証に切り替えた。**抽出した171,512手（剪定前176,941手）すべてをやねうら王depth18で採点し直し、最善から90cp超劣る5,429手を剪定**した。M4 Proで**12エンジン並列**（深さは削らず、並列で数を稼ぐ）にして約2.5時間。

さらにその全数検証の途中で、もう一つ罠を踏んだ。並列エンジンで置換表（TT）を共有したまま測ると、**同じ局面のdepth18スコアが実行のたびに最大150cpも揺れる**——これでは「90cp基準の剪定」自体が再現不能になる。対策として**毎探索前にTTを確保し直す決定的プロトコル**（同じ局面なら評価値もノード数も完全一致する測り方）を確立してから測定した。独立シードでの再検証（891局面・3,096手）で**100cp超の劣手は0件**を確認。

> 前作からの教訓「検証そのものが罠だらけ」は、定跡の取り込みでも例外ではなかった。**外部データの品質表示を信じず、自分のゲートで測り直す。測定器（エンジンの設定）の再現性まで疑う。**

## 8. で、どれだけ強くなったのか——正直な測定

5万局面の定跡が入って、めでたしめでたし——で終わらせず、**効果を数字で測った**。同一エンジン同士で、片側だけに大規模定跡を持たせた自己対戦を144局（持ち時間・開局条件を変えた3セット、先後入替、95%信頼区間つき）。

結果は、正直に書くと**「小さめのプラス。統計的には有意でない」**だった。

| 条件（48局ずつ） | 定跡あり側のスコア | Elo差（点推定） |
|---|---|---|
| 2秒/手・ランダム開局 | 54.2% | +29 |
| 2秒/手・定跡内開局 | 57.3% | +51 |
| 1秒/手・定跡内開局 | 51.0% | +7 |
| **合計144局** | **54.2%（95%CI 46.6〜61.7%）** | **+29（CIは0を跨ぐ）** |

点推定は+30〜50 Elo程度のプラスだが、95%信頼区間はゼロを跨ぐ。「+50 Eloを有意に検出するには約400局が要る」という規模の話で、この局数では「大きな効果は否定できる。小さな正の効果はありそう」までしか言えない。

**面白いのは「なぜ小さいか」の分析**のほうだ。ログを掘ると：

1. **自己対戦では、大規模定跡がほとんど発火しない。** 手書きの検証済み定跡が自己対戦の本線を17手までカバーしており、そこを一歩でも外れた局面は**両者とも**定跡外になる。5万局面という規模でも、1局あたりの「外部定跡由来の手」は平均1.3〜1.4手にとどまった。定跡は「相手が定跡形を指してくる間」しか働けない。
2. **「序盤で時間を貯めて中盤で深く読む」効果は、構造的に存在しなかった。** このエンジンの持ち時間は1手単位（ゲームクロックではない）ので、定跡で浮いた時間は繰り越されない。
3. だとすると、大規模定跡の真価は**自己対戦ではなく対人間**に出る。人間は定跡形を指してくるから、定跡の網に長く留まる。実際、作者（二段）の体感では序盤の質は明確に向上している——**「自己対戦の勝率」と「対人間の体感」が乖離する**のは、前作の「近似指標は対局の強さを予言しない」の変奏だ。測る土俵によって、同じ改善が違って見える。

> 教訓の追加：**改善の価値は、測る土俵に依存する。** 自己対戦で小さく見える定跡の効果は、定跡形を指す人間相手には大きく効く。逆もまた然り。「何に対して強くなりたいのか」を先に決めてから測ること。

## 9. 第4サイクル：定跡を30手まで伸ばし、序盤バイアスを「脳」ごと直す

§8の最後で「進行中」と書いた2つ——**定跡の30手深掘り＋変則手カバー（v2）**と、**NNUEの序盤バイアスを根治する再学習**——が両方とも本番に載った。この2つは、§8の「測る土俵によって同じ改善が違って見える」という話の、きれいな裏返しになっている。

### 9.1 定跡v2：5万 → 9.8万局面、そして「線」を「面」にする

まず定跡を作り直した。ねらいは2つ。

1. **深さ**：本線を20手級から**30手級**まで伸ばす（ply20全域＋ply21〜30の主要変化）。
2. **面のカバー**：人間が指してくる「定跡形からの自然な逸脱」に、定跡側の返し手を用意する。§5でやった「モグラ叩き」を、手作業ではなく**網羅生成**でやる。

②の逸脱カバーは、到達頻度の高い局面から1,200個を種にして、各局面で「300cp以内の自然な手のうち、定跡を外れる手」を洗い出し、その**一手先にやねうら王depth18の応手を1つずつ**足していく専用スクリプトを書いた。結果、**49,961 → 97,767局面**（gzip約1MB、2.5MB上限内）。自然な10例の変則手プローブは**6/10 → 10/10**に。

**作り直して初めて見つかった、v1の重大な穴**もあった。▲7六歩に対する△3四歩（最善との差わずか31cp＝ほぼ互角の本命手）が、生成時の「1局面あたり展開5手まで」というキャップに弾かれ、**振り飛車系のサブツリーが丸ごと欠落していた**。浅い手数では展開キャップを8に緩めて解消。「線は正しくても面に穴」という§の教訓が、自分の定跡自身から出てきた形だ。

悪手ゼロの担保は前回と同じ**決定的プロトコル**：全303,321手をdepth18で全数検証し、gap>90cpの手を剪定。再利用した5万局面分は、決定性ゲート（12局面のcp完全一致）を確認してから流用。独立シードでの再検証でもgap>100cpは0件だった。

### 9.2 NNUE追い焚き：△8四飛が「気持ち悪い」のは脳の問題だった

§3で突き止めたとおり、序盤の不自然な手（浮き飛車△8四飛など）の真因は定跡ではなく**評価関数（NNUE）の序盤バイアス**だった。定跡は「定跡形の間」しか効かない。定跡を外れた瞬間に変な手が出るなら、直すべきは**脳そのもの**だ。

そこで、序盤に厚い教師データで**追い焚き（再学習）**した。既存の資産を捨てず、序盤局面を約56万追加：本番の定跡（ペタショック由来）をBFSで展開したノードと、**「定跡を1手出た直後」の局面**（＝まさに変な手が出る場所）を中心に、やねうら王depth12で採点。混合後の学習データは約590万局面。

**採否は、近似指標ではなく実対局で決めた**。ここが§8との対比だ：

| 指標 | 追い焚き前 | 追い焚き後 |
|---|---|---|
| 序盤ホールドアウトのMAE | 214.7 | **175.6（−18%）** |
| 序盤ホールドアウトのpair精度 | 0.897 | **0.931（+3.4pt）** |
| 一般ホールドアウトのpair精度 | 0.9040 | 0.9001（**−0.4pt**、正直に言うと微減） |
| **自己対戦A/B（192局・先後入替）** | — | **61.7%勝ち越し（95%CI 54.7〜68.3%、p≈0.0006）** |

問題の局面での△8四飛は、静的評価の**15位から23位**へ沈み、浮き飛車系の手も一貫して順位を落とした。歩不成のような不自然な手が上位に来る局面も無くなった。

**そして§8といちばん違うのは、今回のA/Bは統計的に有意だった**こと。理由は明快で——**定跡はめったに発火しないが、評価関数は毎手働く**。§8で大規模定跡の自己対戦効果が小さく見えたのは、自己対戦だと両者すぐ定跡を外れて定跡が「出番なし」になるからだった。評価関数の改善にはその逃げ場がない。1局の全手に効くから、192局で下限が50%を明確に上回った。

> 教訓の追加：**「どこで効くか」が有意差を決める。** 全局面に効く変更（評価関数）は自己対戦で素直に有意になり、条件が揃ったときだけ効く変更（定跡）は対人間で真価が出る。同じ「強くする」でも、正しい測り方は改善の性質で変わる。

（両方とも独立検証——A/Bログの再集計、ホールドアウトの再走、ビット一致、テスト全数パス——を通してから本番反映。近似指標のpair精度は*採否の根拠にしていない*。前作の「近似指標は対局の強さを予言しない」を、今回も守った。）

## 10. 実験ノート：効かなかったこと

強くなった話ばかり書くとフェアじゃない。実際の開発は**「効かなかった実験」の方が多い**。第4サイクルの後、さらに強くしようと2本の実験を並行で走らせた。片方は完全な行き止まり、もう片方も雲行きが怪しい。負けの記録こそ役に立つので、正直に残す。

### 10.1 終盤をもっと速く ―― 「もう終わっていた」行き止まり

実戦で終盤に読み抜けがあった（72手目の詰み見落とし）ことから、「終盤の探索が遅くて浅いのでは」と疑った。持ち駒が多い終盤は、打つ手（ドロップ）が爆発的に増える（盤上20手に対しドロップ160〜330手）。ここの手生成を速くすれば深く読める、という筋読みだ。

プロファイルすると、確かに終盤の1ノードのコストの大半は**手生成と合法性チェック**（合わせて約99%、評価はわずか1%）で、その主犯はドロップ手の量的爆発だった。ビットボードで空きマスと合法な打ち場所を一括計算すれば速くなる。

**ところが調べると、その最適化は既に終わっていた。** 少し前のサイクルで、まさに同じビット演算による高速化がJS・WASM両方の探索に入っていた（合法性チェックの省略、ドロップ生成の1パス前計算）。ビット完全一致を保ったまま追加で削れる余地は、もう残っていなかった。

さらに間抜けなことに、**最初の「遅い」という診断そのものが的外れ**だった。あの27〜41µs/ノードという数字は**JSエンジン基準**で測ったもの。本番はWASMエンジン（JS比15〜30倍速）で動いていて、そこで測り直すと終盤の1ノードは約2.76µs、しかもコストの支配項は**手生成ではなくNNUEの葉評価**に入れ替わっていた。要するに「遅い場所」を間違った物差しで見ていた。

> 教訓の追加：**本番で走っている経路そのものを測れ。** 代理のエンジン（測りやすいJS版）で出したプロファイルは、最適化済み・別実装の本番（WASM版）には当てはまらない。「どこが遅いか」は実装が変われば入れ替わる。—— これは前作の「測定器そのものを疑え」の、経路版だ。

収穫がゼロだったわけではない。**本番WASM経路で終盤のスループットと到達深さを正しく測るベンチマーク**を残せたし、「次に終盤を速くするならホットパスは手生成ではなくNNUE評価だ」と数字で分かった。つまり終盤を強くする道も、結局は**評価関数（脳）を良く/速くする**方に戻ってくる。

### 10.2 KP特徴量 ―― 「賢い入力」は勝てなかった

もう1本は、NNUEの**入力の作り方**を変える実験。今の脳は盤面を「どのマスに何の駒があるか」でそのまま入力している。プロの評価関数の定番は**KP（King-Piece）**という、**自玉の位置を基準に駒の配置をエンコード**する方式で、玉の安全度を捉えやすく、一般に大きく強くなると言われる。これを試した（自玉の位置を6バケットに分け、バケットごとに別テーブルを持つ「factored KP」）。

学習は問題なく回り、**ブラウザ推論（WASM）にKP版を載せる配線もできた**（心配していた「推論が対応していない」壁は無かった。バケット別テーブルの選択までWASMで動く）。ここまでは順調。

問題は肝心の強さだ。現本番（board特徴のrunOp1）との自己対戦A/Bで、**KP版は60局で20勝40敗＝勝率33.3%（Wilson 95%信頼区間 23〜46%）**。信頼区間の上端すら50%に届かない ―― つまり**統計的に明確に弱い**。学習時の一致率もKP版0.911 < board版0.916 とわずかに劣っており、実対局でもはっきり負けた。**採用しない。**

> 教訓：**「理論的に賢い入力」が「素朴な入力」に負けることがある。** 第2サイクルでも、凝った損失関数はデータが少ないうちだけ効いて、データが十分になると素朴な回帰に抜かれた。今回のKPも同じで、賢い構造は、それを活かすだけのデータ量・学習量が揃って初めて効くのかもしれない（今回の590万局面・この規模の学習では活かしきれなかった）。KPが「悪い」わけではなく、「今のこの構成では勝てなかった」というだけ。負けは負けとして記録し、素直に board 特徴の現行版を本番に残す。

### 10.3 次に試したこと、その結果

KPが負け、終盤高速化も行き止まりだった後、次のレバーを2つ試した。終盤の一件で分かった「**本番のホットパスはNNUE評価**」という事実が、そのまま方針を指していた。結論を先に書くと、**2つとも本番を動かせなかった。**

**(a) 評価を速くする（SIMD化）→ もう終わっていた。**
WASMのSIMD128命令でNNUE推論をベクトル化すれば、同じ持ち時間で探索が深くなり全局面に効く……と考えて手を付けたら、**これも既に前サイクルで実装・マージ済み**だった（推論のホットパスは全て v128 命令で書かれ、fast経路で約6.2倍高速化済み）。ビット一致（着手・スコア・ノード数まで一致）も速度も独立に再確認できたが、**新規の伸びしろはゼロ**。終盤高速化に続く「掘ったら既に金脈は掘り尽くされていた」パターンだった。

**(b) 自己対戦データで学習 → 近似指標は良くなったが、実対局は互角。**
教師局面を、ランダムなロールアウトではなく**本番エンジンが実際に到達する局面**から採り直した（そのために「探索の葉評価を本番NNUEに差し替えて指し継ぐ」生成ツールを新たに用意した）。23万局面を作り、既存590万と混ぜて再学習。

- **ホールドアウト（近似指標）は改善**：自己対戦分布でMAE −8%・一致率 +0.86pt。「分布のズレを直す」機序自体は働いた。
- **でも実対局A/Bは互角**：候補 vs 現本番、**96局で52.1%（1000msはぴったり50.0%）、95%信頼区間 [42.2, 61.8]** ―― 50%を大きく跨ぐ。**採用基準を満たさず不採用。**

なぜ効かなかったか。到達局面の分布が思ったほどベースとズレておらず（重複除去で落ちたのは3%だけ）、自己対戦の比率も3.7%と少量。**590万局面で飽和気味のモデルを動かすには、勾配として弱すぎた**。序盤追い焚き（第4サイクル）が65万局面・比率11%で61.7%を叩き出したのと対照的だ。効かせるには「100万局面超／もっと深い探索での生成／蒸留を複数回まわす」のいずれかが要る、というのが見立て。

> この章の結論：**いまの本番は“安い改善”を出し切った状態**。KP・自己対戦データという2つの真っ当なアイデアが、どちらも近似指標では改善を見せながら実対局では有意差を出せなかった。そして高速化系はことごとく「既に実装済み」だった。ここから先の一段は、**深いラベルでの再蒸留・詰み専用ソルバー・より大きなネット**といった“数日がかりの投資”の領域に入る。安く拾える所は、正直、もう拾い切った。—— そしてこれは失敗ではなく、**「どこに天井があるか」を実測で確定できた**という前進だ。負けの記録が、次にどこへ張るべきかを教えてくれる。

## 11. 実戦が暴いた真犯人：中盤の評価バイアス（進行中）

§10で「安い改善は出し切った、次は数日がかりの投資」と締めた。その“投資”を始めたら、**1年ものあいだ濡れ衣を着せていたバグ**が1つ晴れ、そして**このAIの最大の弱点を、作者（二段）の実戦がハードな数字で暴いた**。

### 11.1 濡れ衣だった「固まる」バグ ―― 犯人はマルチスレッドではなかった

このAIには**マルチスレッド探索（Lazy SMP＝複数コアで一緒に読む）**を入れた時期があったが、**本番で「AI思考中…」のまま永久に固まる**ため封印していた。原因は「並列探索のデッドロック」だと思われていた。

再調査で、忠実な本番ビルド（headless Chrome）で二分探索したら、真相は真逆だった：
- **並列を完全にオフ（単スレッド）にしても固まった** → 並列は無関係。
- **cross-origin isolation（COEP）を外すと直った** → 犯人はヘッダ。
- 決定的証拠：`net::ERR_BLOCKED_BY_RESPONSE /_next/.../worker-*.js`。

真因は——**COEP `require-corp` 下では、Web Worker のスクリプト本体にも COEP ヘッダが要る**（CORPだけでは不足）。それが無いのでワーカーのスクリプトがブラウザにブロックされ、**AIワーカーがそもそも起動できず、探索が永久に返らなかった**。**単スレッドでも起きる**。修正は `/_next/*` に1行 COEP を足すだけ。

> 教訓：**症状（並列）を殺すと真因（ヘッダ）が隠れる。** 当時の“修正”はCOOP/COEPを丸ごと外し、固まりは消えたが**原因は闇のまま、無実の並列も道連れ**にしていた。そして**「本番でだけ出る」バグは、静的にコードを睨むのではなく、本番と同一環境で再現するしかない**。

### 11.2 並列を戻した ―― 効果は控えめ、そしてその理由

真因を直して並列が初めて本当に動いた（メイン＋ヘルパー）。A/Bは **2000ms（作者が遊ぶhard/master帯）で+59%、1000msではほぼ互角**。「少し深く読める」が、**劇的ではない**。理由は3つ：共有TTをJS経由で触るオーバーヘッド、ブラウザで数スレッドしか使えない、そして——**深さは評価が正しくて初めて価値になる**。間違った評価を深く読んでも、間違った答えを深く確信するだけだ。この3つ目が、次の発見に直結する。

### 11.3 作者の実戦が暴いた真犯人 ―― NNUEは中盤で「勝者を9割方まちがえる」

作者は実戦のたびに「中盤の緩い手」を報告してきた：意味のない角の使い替え、働かない位置への角打ち、自玉でなく相手玉頭に歩を連打、そして受けずに攻めて負ける。これらを**engineで一手ずつ検証**するため、彼の実戦を再現した（同じ地点に複数の駒が動ける曖昧な棋譜は、**バックトラッキングで矛盾しない解釈を探すパーサ**を書いて解決した）。

そして**ブラウザのNNUEの評価を、やねうら王の“真実”と一手ずつ突き合わせて**、決定的な数字が出た。中盤（ply15〜70、決着局面を除く）で：

- **平均の符号付き誤差 −1525cp**（＝中盤で自分＝後手を、実際より約1500cpも良く誤評価）
- **「どちらが勝っているか」の符号が合っている割合＝わずか7.8%**
- 51局面中 **36回が符号反転**（後手良し表示←実際は先手良し）

つまり——**このNNUEは中盤で、どちらが勝っているかを9割方“逆”に判定している**。作者がずっと感じていた「評価バーが互角/先手優勢でも後手勝勢を表示し続ける」は、気のせいでも1局の偶然でもなく、**この深刻な系統バグ**だった。

これが**全ての実戦の負けを説明する**：AIは「自分が勝っている」と誤認しているから、**受けずに緩い攻めを選び、過信して踏み外し、気づかず負ける**。緩い角も、玉頭の歩連打も、粘れない終盤も、根はこの1つ。§9で序盤の「気持ち悪い浮き飛車」を脳の問題と突き止めたのと同じ構図が、**中盤にも、もっと深刻な形で**あった。

> ここが今回いちばんの発見だ。**自己対戦のA/Bも近似指標も見逃していた最大の欠陥を、作者の“実戦”が一発で当てた。** 「近似指標は対局の強さを予言しない／作者の実戦が最終審判」という本連載の背骨が、また証明された。

**対策（進行中）**：評価関数を、より深い（depth16）やねうら王ラベルで、**中盤に集中して**再蒸留する。合否は勝率だけでなく「**この中盤バイアス（−1525cp・符号一致7.8%）が縮んだか**」を数値ゲートにする。作者が持つ複数台のMacを並列に使ってデータを集めている最中だ。正直に言えば、**深いラベルだけで系統バイアスが直る保証はない**（原因がラベルの浅さでなくデータの偏りなら、別の手が要る）。結果が出たら——効いても効かなくても——ここに追記する。

> 教訓（暫定）：**深い探索は、狂った評価を救えない。** マルチスレッドで深く読ませる前に、評価そのものを正すのが順序だ。強豪ソフトの並列が強いのは、土台の評価が正しいから。うちはまず「評価」を揃えにいっている。

### 11.4 結果：深いラベルは中盤バイアスを直さなかった（正直な負け）

再蒸留を完走した。教師データは 590万局面を母体に、**918,566局面を depth16 で深いラベル化**して合成した（既存局面の再採点 59.9万 ＋ 2台目マシンで新規生成した中盤局面 31.9万、ply20-60 中心）。学習（board特徴・sigmoid・20エポック）→量子化→2つのゲートで測定。

結果（真値＝やねうら王 depth16、game3 中盤 ply15-70、n=51）：

| | mean signed | 符号一致率 | A/B（自己対戦40局） | holdout MAE / pair |
|---|---|---|---|---|
| runOp1（現行） | −1524.9 | 7.8% | — | 476.1 / 0.9001 |
| **deep16（候補）** | **−1331.3** | **7.8%** | **52.5%（互角・95%CI[37,68]）** | **443.2 / 0.9031** |

- **中盤の符号一致率は 7.8% → 7.8%。ぴくりとも動かなかった。** 平均誤差は −13%（1525→1331）縮んだが、「どちらが勝っているか」の判定は相変わらず9割方逆のまま。
- A/Bは 52.5% で**互角**（有意差なし）。上がったのは近似指標の holdout だけ（MAE 476→443、pair 0.900→0.903）。
- 事前に決めた合否ゲート（符号一致≥35%・A/B有意）を満たさず、**不採用**。本番には入れていない。

**何がわかったか。** 全体精度（holdout）は上がったのに中盤の符号バイアスは1ミリも動かない ── これは**「中盤バイアスの原因はラベルの浅さではない」**という強い証拠だ。ラベルを深く正確にしても、ネットは同じ局面で同じ誤った符号を出す。犯人はおそらく**学習データの分布**（作者の実戦に出る中盤が、教師の中で「後手良し」に偏って学ばれている）か、あるいは**この指標が game3 という1局・51局面だけの狭い窓**であること。holdout の4000局面では net はよく較正されている（pair 0.90）のに game3 では 7.8% ── 「作者の棋風が生む特定タイプの中盤を、ネットが系統的に誤る」構図が見える。

> この連載の背骨がまた確かめられた。**近似指標（holdout）の改善は、実戦強度も、狙ったバイアスの解消も保証しない。** 「深いラベル」というもっともらしい一手は、（この1局では）空振りに見えた。次に効くのは、たぶん「深さ」ではなく「分布」── 作者が実際に負ける中盤局面を、正しいラベルで厚く学ばせること。そしてバイアス指標も、1局でなく複数の実戦に広げて測り直すこと。空振りも、どこを外したかを数字で残せば、次の狙いになる。

### 11.5 訂正：2局目で測ったら効いていた ── 「1局で結論を出す罠」に、書いた本人が落ちた

| runOp1（現行） | −607.0 | 25.5% | 23 |

**game4 では deep16 ははっきり改善していた。** 符号一致率 25.5%→**43.1%**、平均誤差 −607→−520、逆転 23→16（全局面参照でも 30.3%→48.5%）。§11.4 で見た game3 の「不変」とは正反対だ。

理由は単純で、**game3 は作者が大敗した1局＝評価が絶望的に狂う極端な外れ値**、game4 はより典型的な中盤だった、ということ。再蒸留は**「普通の中盤」の較正はちゃんと良くしていた**のに、私は最悪の1局だけを見て「効かない」と早合点した。

**訂正後の正直な結論**：deep16 は現行に対し、**game4の中盤バイアス改善・game3同等・holdout微改善・A/B互角（退行なし）**。つまり空振りではなく、**「典型局面の中盤較正を少し良くした、退行のない小改善」**。A/B が互角＝自己対戦では強さの差が出ないので、最終判断は作者に委ねた。

**採用（本番反映）**：作者が「退行なしで典型中盤の較正は良くなっている」と判断し、deep16 を本番の評価関数に採用した（ビット一致パリティ 1200/1200・量子化誤差 mean17cp を確認のうえ差し替え）。小改善ではあるが、**game3 で直らない「大敗局の中盤」**は次サイクルの宿題として残る ── そこは深さでなく分布（作者の負け将棋の中盤を厚く学ばせる）で狙う。

> 教訓（今回いちばん痛いやつ）：**「1局で結論を出すな」と説教していた当人が、1局で結論を出した。** 負の結果ほど、採否を決める前にサンプルを広げて測り直せ。game3だけなら「深いラベルは無力」、game4を足すと「典型局面には効く」── 同じ実験でも、窓を1つ増やすだけで物語が変わる。

### 11.6 分布アプローチの打ち止め ── 「もっとデータ」が逆効果だった二連敗

deep16 の宿題は「game3 型（大敗局）の中盤が直らない」。狙いは分布の是正 ── **作者が負ける中盤を厚く学ばせる**。一晩で2つ回した。

**cycle2（ハードサンプル方式）**：deep16 で自己対戦して中盤局面を25万生成し、**deep16 の評価がやねうら王d16と符号逆の局面（＝盲点）を16,326件抽出**、×8オーバーサンプルして再学習。結果：

| | game3 | game4 | holdout | A/B(vs deep16) |
|---|---|---|---|---|
| deep16（現行） | 7.8% | **43.1%** | 443 / .903 | ― |
| cycle2 | 7.8% | **29.4%** ⬇ | 448 / .902 ⬇ | 47.5% ⬇ |

盲点を暗記させたら game3 は不変、**game4 の較正が壊れ**、実戦も弱くなった。古典的な過学習。

**cycle2b（オーバーサンプルなし）**：犯人がオーバーサンプルかを切り分けるため、生成25万を素直な深いラベルとして追加しただけで学習。結果 **game4 43.1%→27.5%・holdout も悪化・A/B 51.2%（互角）**。──**オーバーサンプルは犯人ではなかった。「M4b 生成データを足すこと自体」が評価を悪くした。**

真因はほぼこれ：**deep16 で自己対戦して作った局面は分布が狭く偏る**。多様な教師集合に25万の“偏った自作局面”を混ぜると、汎化（game4・holdout）が薄まる。deep16 の勝ちレシピ（base＋再スコア＋M5の31.9万）は既にギリギリのバランスで、そこに足す方向は下りだった。

> **打ち止めの結論**：深さ（§11.4）でも分布（§11.6）でも、この中盤バイアス ── とりわけ game3 の大敗局 ── は動かなかった。**deep16 は、いまのデータとこの小さなネットにおける局所最適**。次に効くとすれば「深さでも分布でもない別軸」＝**ネットの容量を上げる**（ただしブラウザ速度とのトレードオフ）か、あるいは**この強さを受け入れる**か。データをこねる時間は、ここで一旦終わりだ。
>
> そして救いは、**3連続の空振りで、本番には何も悪いものが入らなかった**こと。中盤バイアス・holdout・A/B の3ゲートが、負けラウンドでこそ働いた。**採否ゲートの元は、勝つ実験ではなく負ける実験で取れる。**

（なお、この章で何度も出た「飛車先歩交換の無限ループ」は評価とは別口の構造バグ＝エンジンに実戦履歴を渡さず千日手回避が効かない件で、別タスクとして根治予定。評価を直しても、これは別に直す必要がある。）

### 11.7 訂正：deep16 は本番から戻した

§11.5ではdeep16を「退行なし」として本番採用した。しかし、その後の実戦で飛車先の歩を繰り返し打つ回帰が見つかり、固定深さ11の本番WASM探索でも再現した。deep16はその局面で `P*8f` を選び、runOp1は `3a4b` を選んだ。そこでdeep16を本番から外し、重みをrunOp1へ戻した。現在の本番評価関数はrunOp1である。

これは§11.5の「A/B互角だから退行なし」という表現が強すぎた、という訂正でもある。限られたA/Bで差を検出できなかったことは、回帰が存在しない証明ではない。典型局面の較正が改善しても、探索で繰り返し選ばれる一つの悪い順位付けが実戦を壊すことがある。**代理指標が改善し、短いA/Bが互角でも、本番候補として安全とは限らなかった。**

### 11.8 一週間の遠回り：安全な基盤は残ったが、棋力はほぼ動かなかった

その後、Floodgateの強い棋譜から教師データを作り直す計画を進めた。ところが実際には、所有権、改ざん検知、鍵、実行元の認証、checkpoint、失敗時の回収、段階ごとのPR境界、独立レビューと自動レビューコメントへの対応を細かく分割した。これらには「途中で壊れたデータを学習しない」「本番重みを誤って上書きしない」という役割があり、再利用できる基盤も残った。一方で、**評価関数のパラメータ、教師ラベル、探索、対局結果はほとんど変えなかった。棋力への直接寄与はほぼゼロだった。**

正直な棚卸しは次のとおり。

| 作業 | 残ったもの | 棋力への直接効果 |
|---|---|---|
| Floodgate 36,168局の取得 | 今後の新規学習に使える強い棋譜 | まだ未学習なので0 |
| やねうら王/Háo教師環境 | 自作評価関数へ新しいラベルを付けられる | 生成・学習して初めて発生 |
| checkpoint・中断回収・再現記録 | 長い生成を壊さず再開できる | 0 |
| 所有権・鍵・改ざん・実行元の境界 | 誤投入や誤本番反映を防ぐ | 0 |
| 多数の細かいPRと非必須レビュー対応 | 実装上の指摘をいくつか修正 | **強くなった証拠は0** |
| 24,000親局面の追加学習候補 | 既存候補上のpair精度は約+0.97pt、top-1は約+1.19pt | ライブとの直接A/B未実施で未証明 |

予定と大きくずれた原因は、棋力を上げる工程よりも、その前の安全条件を際限なく細分化したことにある。安全性が不要だったのではない。**一度だけ必要な最小ゲートを作るべきところを、各境界を別の成果物として完成させること自体が目的化した。** 自動レビューコメントへの対応も棋力を強くした証拠はなく、待ち時間と追加作業を増やした。この優先順位は間違っていた。

しかも、既存の失敗はすでに警告していた。縮約KPは60局で33.3%、自己対戦データ追加は96局で52.1%、depth16再蒸留は40局で52.5%。**データを足す、教師を深くする、モデルを少し賢くする、のどれも単独では強化を保証しなかった。** それにもかかわらず「基盤が完成すれば次は強くなる」と扱い、現在棋力と目標棋力の差、成功条件、打ち切り条件を先に定義しなかった。

今後は順序を逆にする。実験中はPRを作らず、同じデータでscratchとwarm-startを比較し、データ量とモデル容量を一度に変えない。候補は近似指標ではなく現行との直接A/Bで採否を決める。必須CIと実ブラウザ確認は残すが、**非必須の自動レビューコメントを待たず、棋力に関係しない追加境界を増やさない。** 明確に勝った候補だけを1本のPRにまとめ、本番を置き換える。

この一週間を「全部無駄ではなかった」とだけまとめるのは正しくない。強い棋譜、教師、再開可能な生成基盤は残った。しかし、目標が「高段レベルへ強くする」だった以上、**棋力を測らず安全基盤を作り続けた時間の大部分は、目標に対して遠回りだった。** 次の工程では、作業量ではなく直接対局の得点率だけを前進の尺度にする。

### 11.9 直接対局の決着：+1%の近似改善は、実戦では14.1%だった

§11.8で「直接A/B未実施」とした24,000親局面のseed 42候補を、現行runOp1と直接対局させた。本番と同じK=600・出力scale 1/1、1手1秒、同じ6手の序盤を先後交換する32ペア・64局で測った。全6,439着手は合法で、異常終了はなかった。

結果は**候補9勝、現行55勝、引き分け0（候補得点率14.1%）**。23ペアで候補が2連敗、9ペアが1勝1敗、候補の2連勝は0だった。最新checkpointと元のseed 42の量子化重みは完全に同一だったため、どちらも不採用とした。正式A/Bへは進めず、本番runOp1も変更していない。

これは「約+0.97ポイントのpair精度、約+1.19ポイントのtop-1」が小さすぎた、というだけではない。**近似指標の向きと実戦の向きが逆だった。** 新しいデータで追加学習すれば強くなる、という前提そのものが外れていた。ここまでの追加学習を積み増す案は打ち切り、次は同じ新規データに対してscratch（ゼロから）とwarm-start（現行から）だけを公平比較する。

そのための最初の10,000局面は、Floodgateの両対局者レーティング3,000以上から、学習9,000・検証500・封印テスト500に分けて準備した。使用棋譜は262・106・102局で、棋譜の分割間重複も同一意味局面の重複も0である。この準備中、従来のFloodgateレーティング解析が、数字で始まるプレイヤー名をレーティングと誤認するバグも見つかった。末尾の正式レーティング欄を読むよう直してから抽出し直した。封印テストは候補固定までラベル生成も参照もしない。

**pilotの結果**：学習9,000・検証500の全局面をやねうら王/Háo depth12でラベル化し、同じデータからscratchとwarm-startを作った。封印テスト500は未ラベルのままである。

| model | 検証MAE | 検証pair精度 | 現行との直接対局 |
|---|---:|---:|---:|
| runOp1（現行） | 575.6cp | 67.30% | — |
| scratch | 434.0cp | 61.43% | **0勝8敗で打ち切り** |
| warm-start | **408.3cp** | **69.05%** | **4勝12敗（25%）で打ち切り** |

scratchは9,000学習局面に対して約59万parameterのモデルが大きすぎ、2epoch後から検証損失が悪化した。warm-startは近似指標だけなら現行より良く見えたが、8つの色替えペアで4ペアが1勝1敗、4ペアが2連敗、2連勝は0だった。さらに途中まで進んだ5局を含めても6勝15敗だった。全着手は合法で、技術障害ではない。

したがって、**10,000局面で一から作る案も、現行へ追加する案も不採用**。ここでも検証MAE・pair精度と実戦の向きは一致しなかった。少量データで方式だけ決めてから大規模化する、というpilotの目的は達した。少なくともこの規模ではscratchは容量に対してデータ不足、warm-startは新しい分布への追随で現行の実戦的な順位付けを壊す。どちらも本番には入れていない。

**原因監査と大規模scratchへの切り替え**：新しい9,500ラベルは全局面・教師bestmove・棋譜の指し手が合法で、重複と分割漏洩も0だった。連続局面の評価は手番交替に合わせて強く反転し（`corr(cp_t, -cp_t+1)=0.935`）、やねうら王への再照会でも一致した。符号バグや壊れた教師ではない。

実際の問題は、約59万parameterに対して学習9,000局面・262棋譜しかなく、入力特徴の30.5%が一度も現れなかったことだった。warm-startも新validationを改善する一方、旧広域20,000局面のMAEを354→499cp（+41%）へ悪化させていた。狭い新分布への忘却である。

そこで同じ方式を5倍にする中間実験は止め、現行を初期値にしない大規模scratchへ切り替えた。強豪17,356棋譜を走査し、**学習800,000・validation 3,000・封印test 3,000局面**を準備した（使用棋譜14,861・678・669、両方の重複0）。親データは364MBで、教師ラベルを含めると約0.8GBになる。これは「弱い現行へ積み増す」のではなく、強い棋譜の広い分布から自分たちの評価関数を一から作る本命実験である。ただし、強くなる保証ではない。採否は直接対局だけで決める。

### 11.10 800,000局面でも敗北：小さい表現を打ち切り、81玉位置へ

§11.9の800,000局面scratchを最後まで学習した。しかし直接対局は、打ち切りまでに**候補0勝・現行52勝・1分**だった。データを増やして一から学び直しても、現行よりはっきり弱かった。さらに、同一親局面の複数候補手を使うv9データで、子局面の値だけを学ぶscratchは**0勝15敗**、候補手の順位を直接学ぶscratchも**0勝11敗**で早期停止した。後二つは短いscreenの途中結果で、正式な予定局数を完走した数字ではないが、拡大する理由がないほど一方向だった。

ここで、1,185,988バイトのboard-only表現に対する「データ量」「初期値」「値損失」「候補手順位損失」の変更を打ち切った。近似精度の改善だけでなく、学習目的を順位へ変えても実戦では全敗したためである。盤上の駒を自玉の位置と組み合わせて表せない約59万parameterの器が、次のボトルネックと判断した。**同じ器へ局面をさらに流し込む実験はもうしない。**

次の候補は、自玉の正規化81升ごとに駒表を持つHalfKP風モデルである。これは、やねうら王の公開NNUEを流用するのではなく、自分たちのネットを約90.27MiB（94,656,708バイト）へ広げるものだ。いきなりscratchにはせず、現行runOp1を共有表へ完全コピーし、81個の差分をゼロにした。学習前の候補は、全81表が現行と同じなので、現在の評価関数と数学的に同一である。

最初の単一WASM実エンジンゲートは通過した。1,000局面の静的評価は**1,000/1,000一致**、王移動直後を含む固定深さ探索は**6/6で最善手・score・nodes・leavesが完全一致**した。探索速度低下は中央値3.99%、全体3.49%で、事前上限5%以内。WASMメモリは56,623,104から151,322,624バイトへ増え、読み込みは約40msだった。これはSHA-256 `1b95659d54fc897e2ff766583ccc2035a0932929fcb9520800c3a5ca2b1430db`の研究用WASMで、学習前の完全同値liftを一つのinstanceで測った結果である。研究用WASMは本番WASMから分離し、後者は変更していない。

同じ実装を1〜4 private instanceでNode上に再現すると、4 instanceの論理WASMメモリは605,290,496バイト、weightの一時複製は283,970,124バイト、実測ピークRSSは約1.17GBだった。これは資源量の実測であってブラウザ合格ではない。学習後候補の速度と実ブラウザ4 workerは、棋力候補が直接対局を通った場合だけ昇格前に別途確認する。

最初の100万局面pilotは、全parameterを動かす候補、共有層を固定して81差分だけ動かす候補、checkpointの選び方違いを比較した。差分限定は追加screenで**6勝21敗1分**となり打ち切り。全parameter版のうち、検証値損失が最小のepoch 1も**13勝14敗1分**で前進しなかった。一方、検証pair精度が最良だったepoch 6は、500ms/手の二つの独立screenを合計して**28勝25敗3分**、さらに1秒/手で**16勝15敗1分**。全88局では**44勝40敗4分、得点率52.3%**だった。過去候補のような大敗ではないが、これも「強くなった」と呼べる差ではない。

二週間の順序は、(1) 現行完全同値と速度を確認、(2) 100万局面級の小候補を作って直接対局、(3) 明確に勝つ設定だけを590万局面へ拡大、(4) 先後交換の正式A/Bと外部較正、を当初ゲートとした。**保証するのは「学習すれば必ず強くなる」ことではなく、「直接対局で勝っていない重みは絶対に本番へ入れない」ことだ。** 現在の本番は引き続きrunOp1、1,185,988バイト、SHA-256 `e4e738f99fbd8685bcfe2700e4df364af6274e75b44b298432fc313b9a3e28dc`で、まだ変更していない。

100万局面版は52.3%で明確な勝ちではないため、本来の「勝てば拡大」ゲートは通っていない。ただし大幅退行もなく、100万局面では81升の被覆不足とモデル自体の否定を切り分けられない。そこで例外を隠さず、**一回限りの最終被覆試験**として全5,892,140有効局面（不正52行を除外）を14分55秒で学習した。最大RSSは約11.1GB、process内swapは0だった。指し手順位一致は93.38%から93.43%へ上がった一方、MAEは374cpから389cpへ悪化した。

最終epochを現行と500ms/手で直接対局させると、**候補8勝・現行18勝・1分（候補得点率31.5%）**で不合格になった。27局時点で残り1局を候補が勝っても最終得点率は33.9%にしかならないため、最後の1局は止めた。完了した13の先後交換pairでは候補2連勝が1、現行2連勝が5、その他が7。3,181の探索手はすべて合法だった。これで「データを約6倍にすれば81升表現が勝ちへ変わる」という仮説は棄却し、HalfKP81の追加学習、正式A/B、本番昇格を止めた。現行weightは変更していない。

ただし、最終epochだけの敗北が「checkpoint選択の失敗」だった可能性は残る。そこで追加学習はせず、保存済みのepoch 1と2だけを、現行と500ms/手・各56局の同じscreenで監査した。epoch 1は途中の16局で**12勝4敗**と先行したが、完走すると**29勝26敗1分、得点率52.68%**。合格線62 half-pointsに対して59だった。epoch 2は**29勝24敗3分、得点率54.46%**で、61 half-pointsと合格まであと1だった。両方を合わせた13,069探索手はすべて合法である。途中の12勝4敗だけなら強化に見えたが、事前に固定した局数を完走すると合格しなかった。どちらも独立96局確認、正式A/B、本番昇格へは進めず、単一視点HalfKP81の候補群をここで閉じた。

次の公式実験は、公開NNUEの重みを使わず、共有HalfKP特徴変換を両側の玉視点へ適用する**二視点 `[256 us, 256 them] -> 32 -> 32 -> 1`**である。現行評価を最初の256入力へ写し、反対視点をゼロ、追加32層を恒等変換にするexact liftから始めるため、学習前は現行と数学的に同一にできる。ただし、表現を変える根拠があることと棋力向上の証拠は別である。保存済み候補と同じく、直接対局で合格するまでは「強くなった」とは扱わず、本番weightも変えない。

### 11.11 二視点化も敗北した――「標準形に近い」は棋力の証拠ではない

この二視点案は、同じ駒特徴を自分側と相手側の玉から読む形にした。まず現行表現を完全に保存したまま差分だけを学ぶ二つの候補を作った。勝敗を25%混ぜた候補は500ms/手screenで**候補8勝・現行26勝・2分**。36局時点の18 half-pointsに対し、残りを全部取っても58で、合格線62へ届かないため打ち切った。評価値だけを学ぶ候補はさらに悪く、**5勝31敗0分**、10 half-pointsだった。

加えて、学習前の完全同値モデルでさえ探索速度は現行より約33.9%遅く、5%上限を通らなかった。つまりこの実験は「学習設定が悪かった」だけではなく、**このブラウザ探索へ追加した二視点・追加層の計算量が、得られた精度より重かった**。二候補とも静的評価のTorch→整数weight→WASM一致は64/64だったため、負けを変換バグのせいにはできない。この独自二視点系統は再学習せず閉じた。

### 11.12 公式BonaPiece意味論を自作しても大敗――勝敗データは壊れていなかった

次は「HalfKP風」ではなく、やねうら王の公開ソースで使われるBonaPieceの意味論（手駒slot、成駒の金への集約、玉を特徴から除外）を実装した。公開weightは使わず、**自分たちの80万教師局面だけ**で学習した。学習用JSONL全803,000行を別経路で監査すると、勝敗不一致0、不正行0、重複0、train/validation重複0だった。元CSA 15,539局への追跡でも欠落・改変は0。したがって、この失敗を「勝敗ラベルが逆だった」で説明することもできない。

現行から意味を保って初期化したseed 42は、10 epoch全体を108.12秒で学習し、最良はepoch 1だった。seed 43のepoch 1は検証MAE 376.3cp、pair一致71.39%で、三つのwarm候補中もっとも良かった。scratchはepoch 1でもMAE 439.3cp、pair一致61.5%と明確に劣り、その後も過学習したため、同じscratchをseed違いで増やさなかった。

最良のwarm seed 43を、固定時間・先後交換・局面fingerprint・weight/WASM SHA付きの新しいゲートで現行と直接対局させた。結果は42局で**候補8勝・現行34勝・0分**。16 half-pointsしかなく、残り14局を全部勝っても44で合格線62へ届かないため数学的に打ち切った。全着手は合法、序盤局面は重複0、異常終了0だった。独立96局と正式768局へ進める根拠はない。

速度にも問題があった。学習前の同値経路を現行WASMと同じ探索で比べると約62.9%遅かった。以前の短い速度試験は別の研究WASMとの差しか測っておらず、本番比の証拠にはならなかったため訂正した。**標準的な入力を真似ること、学習損失が下がること、変換が完全一致することの三つを満たしても、実戦で強くなるとは限らなかった。** 本番weightは引き続き変更していない。

次に残したのは、速度を守る単一視点だけである。一つは56局で合格まで1 half-pointだった保存済みepoch 2を、監査済み勝敗で低学習率微調整する案。もう一つはBonaPieceの駒意味論だけを残し、二視点と追加層を外す案である。どちらも短いscreenで現行へ勝てなければ、その系統を二週間回し続けない。

### 11.13 「勝敗を混ぜれば最後の1点が埋まる」も外れた

保存済みepoch 2は以前の56局で29勝24敗3分、61 half-pointsと、合格線62まで1点だった。そこで80万の監査済み教師に25%の実勝敗を混ぜ、元のcheckpointから1 epochだけ、学習率 `1e-5` と `3e-5` で微調整した。学習自体は各約41秒。WDL validationでは高い学習率ほどloss、MAE、pair一致が改善し、両候補ともTorch・TypeScript・WASMは64/64局面でbit-exactだった。

しかし実戦は逆だった。代理指標が良かった`3e-5`は**候補25勝・現行30勝・1分、51 half-points**。更新を3分の1へ抑えた`1e-5`は途中38局で20勝17敗1分まで先行したものの、完走すると**28勝26敗2分、58 half-points**だった。勝ち越しではあるが、事前合格線62を満たさない。どちらも全局面fingerprintが一意、全着手合法、障害0で、独立96局へは進めなかった。

これで分かったのは、勝敗ラベルの正しさと、勝敗を混ぜた学習の有効性は別だということだ。高い学習率はWDL近似を大きく改善しながら実戦を悪化させ、低い学習率は現行とほぼ互角に留まった。**「元候補があと1点だから勝敗を足せば越える」という推論には保証がなかった。** この二設定を長く回すことはせず、590万の強教師局面を使う単一視点BonaPieceへ計算を移した。本番weightは変更していない。

590万版の最初の読込は198.42秒、最大RSS約12.48GBで、既知の不正52行の一つ（銀が5枚ある不可能局面）に到達して学習前に停止した。これはデータ破損を黙って飲み込まない既定動作として正しい。そこで既定のfail-closedは変えず、明示指定時だけJSON/SFEN不正を分類・計数して除外し、CPや勝敗ラベルの不正は必ず停止する経路を追加した。停止したprocessのswapは0で、壊れた局面を使った更新も0だった。

ところが再読込は、過去の構文中心の監査値「除外52行」ではなく、**有効5,889,953行・SFEN除外2,239行**を報告した。新parserが駒の物理総数（銀は盤上と手駒を合わせて4枚まで等）も検査したため、旧監査が通した2,187行を追加で止めた可能性がある。期待値が違うまま学習を続けず、epoch 1のcheckpointができる前に手動停止した。

そこで二つの独立stream実装で全5,892,192行を再監査した。結論は一致し、2,239行はすべて不正、parserのfalse positiveは0だった。内訳は物理的に不可能な駒総数が2,099行、駒総数は範囲内だが一方の王が0枚または2枚の行が140行。JSONとCPは全行で正常だった。旧経路は手番側の王欠落52行しか止めず、2,187行を見逃していた。原因はparserでなく、元データ生成時の局面更新・make/unmake・捕獲・王管理のどこかにある。除外行を行SHA付きで隔離し、checkpoint/exportへ**採用5,889,953・隔離2,239**を記録する条件で研究学習を再開した。将来の教師生成は、局面serialize前後の駒総数と王数を強制するまで停止する。

監査後の2 epochは392.94秒、最大RSS約14.38GB、process swap 0で完了した。しかし多ければ良いという結果にはならなかった。80万warm最良は検証MAE 382.6cp、pair一致70.07%だったのに対し、590万版はepoch 1で551.8cp・60.10%、epoch 2で559.3cp・62.08%。epoch 2は訓練lossだけ0.009256から0.006230へ下がり、held-out側は悪化した。したがって590万版を優先せず、同じ単一BonaPieceでheld-outが明確に良い80万warmを先に直接screenする。

### 11.14 初めて短期ゲートを通過した候補――「学習を足す」のでなく、現行を半分残した

単視点BonaPieceの800,000局面warm候補も、直接対局では明確に負けた。検証pair精度が最良だったseed 43は、現行に対して**2勝26敗**。残りを全勝しても合格不能になった時点で停止した。全5,889,953正常局面を使った2 epoch学習も、80万版より検証MAE・順位一致率が大きく悪く、量子化と実行時の完全一致だけ確認して対局へは送らなかった。データを約7.4倍にしても、この経路は強くならなかった。

同時に、不正2,239局面の発生源も特定した。最初のMacが作った4,284,992行は全て物理的に正常で、不正は2台目Macの生成分だけにあった。2台目へ案内した時点では`--wasm`実装前だったのに、旧CLIが未知optionを黙って無視し、別のJS選択経路へ落ちていた。その経路はselectorの返した手を既生成の合法手集合と照合せず適用していた。未知optionの拒否、selector前後の局面hash、合法手のcanonical照合、毎手後の全駒・両王保存則を追加した。実在した不正局面を含む12回帰テストとランダム1,000局で再発は0だった。

ここで、追加学習とは別の候補を再検討した。HalfKP81のexact lift（現行と数学的に同一）と、全データ学習epoch 2のparameterを50%ずつ補間したモデルである。固定した二つの検証集合では、alpha=0.5がloss、MAE、pair精度をともにalpha=0より改善していた。ただし最初の事前規則は「量子化最大誤差175cp以下」で、基準alpha=0自身が207.6cpだった。そこで最初の失敗を後から合格にはせず、**基準比5%以内**という新しい規則、alpha=0.5の1本だけ、新しい対局seedを対局前に固定した。

結果、1手1.5秒・先後交換56局のscreenは**候補31勝、現行20勝、5分、67/112点（59.8%）**。合格線62点を初めて越えた。全着手合法、定跡重複0、技術障害0である。これは短期screenの通過であって、まだ「確実に強くなった」という結論ではない。

未使用の別seed・別定跡96局による独立確認は、最初の試行中に依存関係の再構築と衝突してtechnical faultが1件出たため、その試行全体から棋力結論を出さず、証拠を残して無効化した。環境を固定して同じ事前条件を最初から再実行した結果は、**候補53勝、現行37勝、6分、112/192点（58.33%）**。全着手合法、定跡重複0、技術障害0だった。先後交換2局を単位に10万回再標本化した片側95%下限は**98/192点（51.04%）**で、事前条件の「50%を厳密に超える」を満たした。

しかし正式768局では、**候補376勝、現行357勝、35分、787/1536点（51.236979%）**に収束した。全384先後交換pair、768局を完走し、全着手合法、定跡重複0、技術障害0だった。bootstrap seed `20260710`、10万回のpair再標本化による片側95%下限は**742/1536点（48.307292%）**、両側95%下限は**733/1536点（47.721354%）**。安全条件の45%超は満たしたが、「50%を厳密に超えて現行より強い」という正式条件は満たさず、判定は`rejected-complete`である。report SHA-256は`1f83896df8e55c631caa475494a4ba66a10f930068d2ec8ee236c9bf4abfa8ec`、manifest SHA-256は`6470c79b95ccf94fdd51fd017b05daab9e39b9ea98f7a22db4e8a7b72f0cc4e0`。独立96局を通っても、大標本では優位を証明できなかった。したがって外部校正と本番昇格へは進めず、ライブ重みは変更していない。

もう一つの本命として、合法候補手278,736行を使い、HalfKPをwarm startしてpairwise/listwise順位学習しながら、500,000局面の値を1:1でreplayする3候補も8 epoch完走した。値MAEは121〜161cp改善したが、独立集合のpair精度は0.53〜0.94ポイント、top-1は1.19〜1.81ポイント悪化し、採用checkpointは0だった。この系統は対局前に停止した。次回用には、現行ブラウザ探索とdepth-12教師が違う親局面だけを掘り、**全合法手の子局面**を独立採点する8-shard生成器を作った。3親239手で合法集合、子SFEN、視点符号が239/239一致し、同じ入力はbyte完全一致した。

今回の違いは、モデルを大きくしたことでも、データを増やしたことでもない。**現行の実戦的な順位付けを半分保持し、学習候補の過剰な移動を平均化した**ことで、短期56局と独立96局の二段階を越えた。しかし正式768局は、その早い有望信号を約1.24ポイントの小差へ縮め、統計的な優位を証明できなかった。独立確認は誤差を減らすが、少数標本を保証へ変えるものではない。次はbrowser-confusion教師を再生成し、現行探索が実際に迷う全合法手を順位学習してから、同じ直接ゲートを最初から通す。

## この章の教訓

- **「検証済みの定跡」と「十分な定跡」は別物**。1手ずつは正しくても、カバレッジが線だと穴から漏れる
- **修正の検証は「その局面」でなく「その筋の続き」まで**。1手直して満足すると、問題は1手先に逃げる（実体験）
- **評価関数の弱点は、終盤（飽和）と序盤（構想）の両端に出る**。中盤が強いのは、学習データが中盤に厚いから
- **公開資源を探すのを最初にやるべきだった**。車輪の再発明（手書き定跡）は、規模の壁に当たる
- **外部データの品質表示を盲信しない**。付属評価値だけでは1.5%の劣手が漏れた。自分のゲート（depth18全数検証）で測り直して初めて「悪手ゼロ」と言える
- **測定器の再現性まで疑う**。共有TTのままでは同じ局面のスコアが150cp揺れ、剪定基準そのものが崩れる。決定的に測れる状態を先に作る
- **フォールバックを最初に設計する**。定跡ファイルの取得失敗＝手書き定跡で従来動作、という退路があるから、大きな変更を安心して本番に出せる
- **「どこで効くか」が有意差を決める**。毎手働く評価関数の改善は自己対戦で素直に有意になり、条件が揃ったときだけ効く定跡は対人間で真価が出る。同じ「強くする」でも正しい測り方は変わる（第4サイクル）
- **変な手は、定跡でなく脳を疑う**。定跡を外れた瞬間の悪手は、序盤に厚い教師での追い焚きで根治する。近似指標（pair精度）は採否の根拠にせず、最後は192局の実対局で決めた
- **症状を殺すと真因が隠れる**。本番でだけ固まるバグは、機能を無効化して蓋をせず、本番同一環境で再現して真因（COEPヘッダ欠落）を暴く。無実の並列に濡れ衣を着せていた（第11章）
- **深い探索は狂った評価を救えない**。マルチスレッドの深さが価値になるのは評価が正しい時だけ。強豪の並列が強いのは土台の評価が良いから。順序は「評価→深さ」（第11章）
- **最大の欠陥は作者の実戦が当てた**。自己対戦A/Bも近似指標も見逃した中盤の評価バイアス（勝者の符号が9割方逆）を、二段の実戦一発で発見。実戦が最終審判、を再証明（第11章）
- **1局で結論を出すな──ただし短いA/Bの互角も安全証明ではない**。深いラベル再蒸留はgame4で中盤の較正を改善したが、後の実戦で`P*8f`回帰が見つかりrunOp1へ戻した。代理指標、少数局面、短いA/Bのどれか一つで採用を決めない（第11章）
- **安全基盤は棋力ではない**。強い棋譜と教師環境は資産だが、所有権・鍵・改ざん境界や非必須レビュー対応を増やしても評価関数は強くならない。最小限の安全ゲートを残し、直接A/Bを最優先する（第11章）
- **WDL近似の改善も棋力ではない**。勝敗ラベルを監査して正しくしても、それを混ぜた候補が現行より勝つとは限らない。低lossではなく、別seedの直接対局を昇格条件にする（第11章）
