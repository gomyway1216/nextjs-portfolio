# packed-key heapを実探索で測ったが、不採用にした——現行heap比+0.38%では次へ進めない

> 前回不採用にしたstable heapの残った安価な案として、比較キーをまとめたpacked-key heapを実探索で1回だけ測った。64 / 64局面で探索結果は完全一致したが、現行heapからの上積みは全体+0.3808%に留まり、事前基準+1.5%を下回った。候補はここで棄却し、v3、固定時間対局、本番変更へ進めない。ライブAIは今回も強くなっていない。

[English version](./blog-shogi-packed-heap-real-search-tuning.en.md)

---

## 結論

packed-key方式は本番の全ソート経路より全体**+6.8479%**速かった。しかし、すでに不採用となった現行heapとの差は全体**+0.3808%**、局面中央値**+0.2636%**だけだった。

| 比較                             |       実測 |   事前基準 | 判定   |
| -------------------------------- | ---------: | ---------: | ------ |
| packed対本番・全体throughput     |   +6.8479% |  +8.5%以上 | 不合格 |
| packed対現行heap・全体throughput |   +0.3808% |  +1.5%以上 | 不合格 |
| packed対本番・局面中央値         |   +5.8092% |  +5.5%以上 | 合格   |
| packed対現行heap・局面中央値     |   +0.2636% |     0%以上 | 合格   |
| packed対本番・wall time悪化のp90 |   +0.0367% |    +2%以下 | 合格   |
| 探索結果一致 / technical fault   | 64 / 64、0 | 64 / 64、0 | 合格   |

中央値などは通ったが、最重要の全体値2項目が不合格だった。結果を見た後に基準を緩めたり、同じデータで再実行したりはしない。

## 何を比較したのか

同一の64局面を固定深度5、quiescence depth 8、TT共有なしで、次の3方式に通した。

- P：本番の全ソート
- H：前回不採用にしたstable heap
- K：moveと比較用`u64 key`を持つpacked-key stable heap

計測順は`P,H,K,K,H,P,K,P,H,H,P,K`に固定し、各方式へ同じ42,582,768単位の仕事を与えた。閾値、候補、runner、停止規則は結果生成前にcommit `50c72dcc`としてGitHubへpushし、[PR #619](https://github.com/gomyway1216/nextjs-portfolio/pull/619)で外部時刻を固定した。

これは既に調整用と定義したv1の64局面を使う**tuning screen**であり、未使用の正式holdoutではない。正式v2 holdoutは再利用していない。

## 正確性

64 / 64局面でbest move、score、depth、nodes、leavesが3方式すべて一致し、相違0、technical fault 0だった。packed経路は次の回数だけ実際に発動した。

| 分類         | 発動回数 |
| ------------ | -------: |
| 序盤         |    5,411 |
| 中盤         |    2,923 |
| 打ち手が多い |  100,391 |
| 王手回避     |  168,931 |
| 合計         |  277,656 |

64局面中3局面では発動0だったが、事前条件は「4分類それぞれで発動すること」であり、全分類が満たした。機能が動かなかったために差が出なかった比較ではない。

## 速度結果

| 分類         | packed対本番 | packed対現行heap |
| ------------ | -----------: | ---------------: |
| 序盤         |     +2.6438% |         -0.0558% |
| 中盤         |     +2.6112% |         +0.3707% |
| 打ち手が多い |     +7.6680% |         +0.5236% |
| 王手回避     |     +6.8254% |         +0.3365% |

packed化による上積みは最大の分類でも現行heap比+0.53%ほどで、序盤ではわずかに遅かった。

packed-keyのkernelマイクロベンチでは条件によって大きな改善が見えたが、実探索全体ではmove picker以外の処理も多い。そのため、比較回数とswap項目を減らした効果は現行heap比+0.38%まで薄まった。

## なぜ不採用なのか

固定規則は「本番より明確に速い」と「現行heapにも意味のある上積みがある」の両方を要求した。全体集計ではどちらも不合格だった。

したがって停止規則どおり、次を行わない。

- 閾値変更や同じ試験のやり直し
- 新しいv3 holdoutの作成
- 固定時間対局
- 本番WASMやライブ重みの変更

固定時間対局をしていないため、勝率、Elo、段位が上がったという証拠はない。正しい主張は「同じ探索結果を安全に出せたが、上積みが小さすぎて止めた」までである。

## 所要時間と制約

Apple M4 Pro、14 logical CPUs、Node v22.13.0で、計測本体は**299,697ms、約4分59.7秒**だった。これはrun本体の値であり、実装・build・記事化を含む総工数は計測していない。

25msは各blockの校正目標で、実測の強制下限ではなかった。全768 block中142 blockが25ms未満、最短は20.31msだった。3方式を同一runで交互に測った集計と判定は独立再計算で一致したが、この点は短blockによるノイズ上の制約として残る。

また、これは単一Mac上のNode WASM測定であり、ブラウザの固定時間対局ではない。

## 次にやること

move-pickerの小幅調整はここで止める。次の計算資源は、指し手の質を変えられる新しい評価関数候補の教師生成・再学習へ戻す。

候補重みができてもholdout精度だけでは採用しない。現行ライブ重みとの事前固定した固定時間paired A/Bで勝率改善を確認し、外部校正を含む安全条件を通過した候補だけをライブへ進める。

今回の成果は高速化そのものではなく、約5分の実探索で「この枝にこれ以上計算資源を使わない」と決められたことである。
