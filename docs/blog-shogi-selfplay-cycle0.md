# 伸びない学習を止め、自作NNUEの自己対局サイクル0を始めた

> この一週間で、評価関数の形式、データの認証、再学習、静的指標、対局ゲートを多数調べた。しかし、ユーザーが求めていたのは「仕組みが安全になった」ことではなく、実戦で明確に強くなることだった。正式768局の候補は51.24%だったが、優越性を証明できず不採用。その後のbrowser-confusion学習もheld-out top-1を改善できなかった。そこで、同じ静的データを増やすレーンは打ち切り、自作エンジンの自己対局、深い事後評価、学習、候補対局を繰り返すサイクル0へ移った。この記事は、何が無駄だったか、何を残すか、いま何が動いているかを数字で記録する。

---

## 結論

- ライブAIが強くなったとはまだ言えない。`public/shogi-nnue-weights.bin`は変更していない
- HalfKP81 alpha-0.5候補の正式768局は **376勝357敗35分、51.236979%**。安全性条件は通ったが、強さの95%下限は47.72%で50%を超えず、`rejected-complete`になった
- browser-confusion batch 3では3つの8-epoch学習すべてでheld-out top-1が悪化した。最後の温度50診断も3案とも **65/643**で、基準66/643より1局面悪かった。このレーンは終了した
- 新しい自己対局パイプラインは実データで端から端まで動いた。ローカルテストはVitest 31件、Python 15件が通過し、82行の実データはtrain 75 / validation 7へ漏洩ゼロで分割され、2つの学習案が完走した。ただしこれは配線確認であり、強さの証拠ではない
- 採用した生成条件は、12並列、対局探索depth 2、終局後のラベル探索depth 6、4手ごと、1局最大24局面である。20局のdense pilotは62.48秒、247局面、故障0だった
- 24,000局の本生成は2026年7月21日23:27頃（PDT）に開始した。初期約3分では54局・612局面だったが、約12分では135局・1,592局面となり、単純外挿は約35時間へ伸びた。短いpilotだけの9〜11時間予測は楽観的だったため、現在は**1台で24〜48時間**を計画幅とする。完了時刻は断定しない
- 約12時間30分、6,219局・74,826局面で12 worker中4本が停止していることを検出した。保存済みprefixは破損0。原因はWASMの実効30-bit TT衝突で古いroot手を再利用したことだった。違法root手のときだけ同一局面を空TTで1回再探索する修正で停止局を越え、6,251局から12並列を再開した
- その後、完了済み **16,255 / 24,000局（67.73%）**だけを不変snapshotとして切り出した。元の本生成を破壊せず、198,391局面からtrain 186,634 / validation 6,818を作り、重複と漏洩を除去して2案を実学習・量子化した
- lambda-0.50とlambda-0.75はMPSで2 epochを完走した。validation lossとpair accuracyは小幅に改善したが、**これらの静的指標は棋力の証拠ではない**
- いまは両候補のscreen 56局を、各7 pair worker、1手1,500msで同時実行している。結果はまだ確定していない。通過候補だけを独立96局へ進め、そこも通過した候補から1つだけを正式768局へ進める。ライブ変更は自動化していない

## 1. 一週間の棚卸し：必要だったことと、棋力に直結しなかったこと

率直に言えば、これまでの作業の多くは、最終目的である棋力向上に直接つながらなかった。

データの所有元、改ざん検出、鍵、PR境界、再現可能なハッシュ、合法手検証は、誤った重みを本番へ出さないためには役に立つ。しかし、それら自体は1局も勝率を上げない。そこへ時間を使いすぎ、実際の学習と対局比較へ移るのが遅れた。この優先順位は間違っていた。

一方、完全に消えない実利もある。正式768局まで同じ候補を追い、51.24%という見た目のプラスを「強くなった」と誤認せず、信頼区間で不採用にできた。さらに、静的なpair/value指標が改善しても、実際の最善手一致が悪化する例を3 seedと追加診断で再現した。これにより、同じデータを増やして同じ損失で回す案を、追加の数日を使う前に終了できた。

教訓は単純である。

1. 完走した学習を成果と呼ばない
2. 静的指標だけで強さを主張しない
3. 同じ仮説が事前基準を繰り返し外したら止める
4. ライブ変更は、直接対局で優越性が確認できた候補だけにする

## 2. なぜ次は自己対局なのか

今回のサイクルは「既存の強い評価関数をコピーする」案ではない。自分たちのHalfKP81評価と自分たちのWASM探索を使って局面を作り、その局面を同じ固定済みモデルでより深く読み直し、探索値と最終勝敗を混ぜて次の候補を学習する。

```text
強豪棋譜由来の開始局面
        │
        ▼
自作WASM同士が固定depthで自己対局
        │
        ▼
終局後、採用局面を空のTTから深く再探索
        │
        ▼
探索値 + 対局結果でHalfKP81を微調整
        │
        ▼
ライブではなく不変の比較相手と直接対局
```

強豪棋譜由来の24,000開始局面を使うのは、弱い初期局面生成に偏らせないためである。対局中のランダム手、壁時計による探索打ち切り、フォールバック手は使わない。固定depthにすることで、別のMacでも同じ入力とseedから同じ処理を再現しやすくした。

ただし、この方法にも保証はない。depth 2の着手は浅く、depth 6のラベルはやねうら王級の教師ではない。同じモデルが自分の癖を再生産する危険もある。だから「データを大量に作ったから強い」とは判定せず、直接対局を唯一の昇格経路にする。

## 3. 速度pilotで高すぎるdepthを捨てた

最初から24,000局を高depthで開始すると、数日後に速度不足が判明する。その無駄を避けるため、同じ20局を12 workerで測った。

| 条件                     |              20分時点または完了結果 | 判断                         |
| ------------------------ | ----------------------------------: | ---------------------------- |
| play 4 / label 12        |                   20分22秒で完了0局 | 遅すぎるため中止             |
| play 3 / label 8         |                     約20分で10/20局 | 遅すぎるため中止             |
| play 2 / label 6、sparse |  24.89秒、82局面、17詰み・3最大手数 | 配線確認に採用、データ量不足 |
| play 2 / label 6、dense  | 62.48秒、247局面、19詰み・1最大手数 | 本生成に採用                 |

dense設定は12手目以降180手目まで、4手ごと、1局最大24局面を保存し、最大192手で打ち切る。20局ではゼロ局面の対局0、技術故障0、平均12.35局面/局だった。単純外挿は24,000局で296,400局面である。

ここで時間予測を二度修正した。62.48秒の短いpilotだけなら9〜11時間に見えた。本生成の初期約3分は54局、約18局/分だったが、約12分では135局・1,592局面、約11.5局/分となり、単純外挿は約35時間になった。長い対局と深いラベル探索の裾があるため、現時点の計画幅は24〜48時間とする。これは約束ではなく、定常区間の実測が増えたら更新する推定である。

## 4. 6,219局で見つかった停止と、データを捨てない復旧

約12時間30分の確認時点で、本生成は6,219 / 24,000局（25.91%）、74,826局面まで進んでいた。しかしworker 1、3、4、9が途中終了し、実際に動いていたのは8本だった。progressとpositionsを全shardで照合した結果、重複、途中行、局面数の不一致、game ID不一致は0で、各局の完了prefixは保存できていた。

停止局の一つgame 5193を再現すると、ply 111でWASMが`S*7g`（7七銀）を返した。7七には相手玉があり、明白な違法手だった。一方、JSとWASMの局面hash、手番、合法手数172は一致していた。同じ局面を空のTTから探索すると、毎回合法な`S*6h`を返した。

原因は局面同期ではなく、WASM探索が各手をまたいで保持する実効30-bitのtransposition tableだった。hash衝突した古いroot手を合法手集合と照合せず返していた。対策は、返却root手が現在のJS合法手集合にない場合だけTTを空にし、**同じ局面・同じdepthを1回だけ再探索する**ことである。JSの先頭合法手やランダム手へのfallbackは追加していない。再探索後も不正なら従来どおり停止する。

修正版はgame 5193を後手勝ち・140手・24サンプルで完走し、shard 9は432局から438局へ進んだ。既存の完了game 0も修正版で再生し、保存済み9,660 bytesとSHA-256が完全一致した。その後、全processを完了prefixで一度閉じ、6,251局・75,268局面から修正版coordinator 1本、12 workerで再開した。これは棋力向上の証拠ではなく、生成停止をデータ破棄なしで直した証拠である。

恒久対策はWASM側でroot TT手をroot合法手集合と照合し、さらに広いhash identityを持たせることである。ただしWASMを変えると固定済みSHAとrun fingerprintが変わるため、今回の途中runには混ぜず次cycleの課題とする。

## 5. 本生成の固定条件

| --------------------------- | -------------------------------------------- |
| 対局数 / worker             | 24,000局 / 12                                |

| quiescence                  | 10                                           |
| 採用間隔                    | 4手ごと                                      |
| 1局の最大採用数             | 24局面                                       |
| 最大採用手数 / 最大対局手数 | 180 / 192                                    |
| bootstrap weights           | `2b91060f…b47c`、81 buckets                  |
| research WASM               | `1b95659d…bdb`                               |
| 開始局面                    | 24,000行、1,000 source games、`c9ee90da…b62` |

出力先は`/Users/yudaiyaguchi/.codex/shogi-runs/selfplay-cycle0-full24k-depth2x6-dense-v1`である。完了済み局だけを読み取るsnapshotを16,255局で固定し、元runの途中書き込みには触れていない。snapshotのshard別完了局数は`[1906, 761, 2000, 670, 794, 2000, 829, 2000, 1545, 1711, 1794, 245]`で、合計16,255局である。

screen 56局の実行中は、同じMacのCPUを実戦判定へ集中するため、本生成workerをメモリ上で一時停止している。両screenが終われば自動的に再開し、通過候補があれば次の実戦ゲート中だけ再び一時停止する。これは24,000局を完了扱いしたという意味ではない。16,255局のsnapshot候補を先に直接対局へ出し、残りの生成も保存するための計算資源の切り替えである。

## 6. 16,255局snapshotの分割と実学習

本生成の完了prefixから、不変のsnapshotを作った。入力は16,255局、198,391局面である。

- train 186,634行 / 15,499局、validation 6,818行 / 610局
- source game、生成game、opening、positionのtrain/validation重複はすべて0
- current側の重複局面4,771行、validation内の重複局面151行を除去した
- cycle 0のholdout seedは`selfplay-cycle0-fixed-holdout-20260722`で固定
- 次サイクル以降は、現在の採用データ75%と過去の採用データ25%を混ぜる。cycle 0には過去採用データがないため実効比率は100/0

学習計画を先に固定し、alpha-0.5のcheckpoint `ea36d0b9…a8c4`からMPSで2 epoch、batch 256、学習率3e-6を実行した。比較するのは次の2案だけである。

| arm         | 深い探索値の割合 | 終局結果の割合 | trainer `wdl_mix` |
| ----------- | ---------------: | -------------: | ----------------: |
| lambda-0.50 |              50% |            50% |              0.50 |
| lambda-0.75 |              75% |            25% |              0.25 |

ここは表記を間違えやすい。ローカルtrainerの`wdl_mix`は「探索値」ではなく「終局結果」の割合なので、lambda 0.75では`wdl_mix=0.25`になる。

結果は次のとおりで、両方を94,656,708 bytesのHalfKP81 int16重みに変換した。

| arm         | initializer val loss | epoch 2 val loss | initializer pair acc | epoch 2 pair acc | best checkpoint SHA |
| ----------- | -------------------: | ---------------: | -------------------: | ---------------: | ------------------- |
| lambda-0.50 |             0.078309 |         0.076182 |               0.8743 |           0.8750 | `785ff6ea…cc9`      |
| lambda-0.75 |             0.045156 |         0.043336 |               0.8743 |           0.8757 | `bd964ea0…f8e`      |

この表は、学習損失が下がりpair accuracyが小幅に上がったことしか示さない。以前の失敗で、静的指標の改善と実戦棋力は一致しないことを確認済みである。したがって、この時点で「強くなった」とは主張しない。

監査チェックも維持した。snapshotは完了局だけ、run fingerprintは1つ、4種類のtrain/validation overlapは0、入力・計画・checkpoint・exportはSHA-256で固定、データmanifestと学習結果の`live_weight_write_authorized`はfalseである。これは誤昇格を防ぐ境界であり、棋力そのものではない。

## 7. 強くなったと呼ぶ条件

本生成完了後も、すぐライブへ置かない。

1. 16,255局snapshotと全shardを再検証する — 完了
2. 固定holdoutでtrain/validationを公開し、2 armを学習する — 完了
3. 候補を量子化し、実行時の一致を確認する — 完了
4. **screen 56局**で不変の比較相手と直接対局する — 両候補を同時実行中
5. 通過した候補だけを、screenと異なるseedの**独立96局**へ自動で進める
6. 独立96局を通過した候補から事前固定規則で1つだけ選び、**正式768局**へ進める
7. 正式優越性と外部校正の両方を確認してから、別途ライブ変更を判断する

screen 56は両候補とも各7 pair worker、1手1,500ms、28 pairで実行する。独立96局と正式768局は別seedで、故障なしの完全通過だけが先へ進む。両候補が独立96局を通過しても正式768局は1候補だけである。最初に落ちたゲートでその候補を止める。最大3 cycle、2 cycle連続不採用なら、この方式も停止して設計を見直す。学習回数を増やし続けて「いつか良くなる」とは扱わない。

## 8. 現在地

いま確認できる成果は、「AIが強くなった」ことではなく、16,255局の実データで2候補を作り、静的指標から直接対局へ移れたことである。ライブ重みは不変である。

lambda-0.50とlambda-0.75のscreen 56局は同時に動いているが、この記事の更新時点では勝敗結果をまだ確定していない。結果を先取りせず、完了receipt、合法手、技術故障、事前固定thresholdを満たしたreportだけを採用する。通過時は自動で独立96局、さらに選抜された1候補だけが正式768局へ進む。正式通過後もライブへ自動反映しない。目標は「学習した」ではなく、**同じ条件の対局で不変の比較相手を統計的に上回った**ことである。

設計の背景資料として、[Stockfish NNUEの学習ドキュメント](https://github.com/official-stockfish/nnue-pytorch/blob/master/docs/nnue.md)と[やねうら王のNNUE学習解説](https://yaneuraou.yaneu.com/2018/12/30/nnue%E8%A9%95%E4%BE%A1%E9%96%A2%E6%95%B0%E3%81%AE%E5%AD%A6%E7%BF%92%E6%96%B9%E6%B3%95%E3%81%AB%E3%81%A4%E3%81%84%E3%81%A6/)を参照した。ただし、一般的な成功例は今回の候補が強くなる保証ではない。今回の結論は、保存した実データと直接対局だけから出す。
