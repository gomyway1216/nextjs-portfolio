# 将棋AIの手順選択をheap化したが、本番には入れなかった——正式64局面で+6.79%、事前基準には未達

> ブラウザ将棋AIの探索結果を変えず、同じ仕事を速く終わらせるために、指し手の取り出し方だけを変更した。固定深度では全64局面で最善手・評価値・探索量が完全一致し、全体処理速度は6.79%上がった。しかし、事前に決めた「全体+8%、局面中央値+5%」には届かなかった。したがって固定時間対局へ進めず、本番WASMもライブ重みも変更していない。これは「強くなった」記事ではなく、有望に見えた高速化を正式に不採用にした記録である。

[English version](./blog-shogi-stable-heap-move-picker-formal-v2.en.md)

追跡結果：残ったpacked-key案も実探索で現行heap比+0.38%に留まり、[事前基準どおり不採用にした](./blog-shogi-packed-heap-real-search-tuning.md)。

---

## TL;DR

- 全指し手を最初に並べ替える代わりに、次に調べる手だけを順に取り出す`stable max-heap`を研究用WASMへ実装した
- 単純なselection scanは、試した5条件すべてで**0.96〜6.55%遅く**なり、早い段階で不採用にした
- 調整用データでは最終heap候補が全体**+6.87%**、局面中央値**+5.67%**だったため、未使用の正式64局面へ1回だけ進めた
- 正式結果は、探索結果が**64 / 64局面で完全一致**、technical fault 0、全体**+6.7915%**、中央値**+2.9145%**
- p90の遅化、4分類すべて非負、全分類で機能が実際に発動、technical fault 0は合格した
- ただし事前基準の全体**+8%**と中央値**+5%**の両方に不合格だった
- 予定していた固定時間56局の対局は実施していない。本番ソース、本番WASM、埋め込みbase64、ライブNNUE重みはすべて未変更
- さらに試したindex-only heapも、8条件すべてで遅く、正式実験へ進めず不採用にした
- その後のpacked-key heapは、Node 22・各block 100ms以上・ABBA/BAABの追跡可能な再測定で、同じ仕事のthroughput差が全条件**+0.52〜+19.14%**だった。しかし実候補に近い64手以上・8手だけ取り出す条件では**+0.52〜+3.65%**に留まり、明確な次候補とは判定しなかった
- 所有権・改ざん・鍵・PR境界の整備は誤投入防止には役立ったが、**棋力への直接寄与は0**だった。今後は安価な実測を先に行い、形式作業は安全な本番反映に必要な最小限へ絞る

## 何を変えようとしたのか

αβ探索は、良い手を先に調べるほど早く枝を切れる。現行エンジンは各局面で候補手に点数を付け、全候補を安定ソートしてから順に探索する。この方式は分かりやすい一方、途中の数手で枝刈りできる局面でも、最初に全候補を並べ替える費用を払う。

今回の狙いは、評価関数や探索規則を変更せず、**同じ順番の手を必要になった分だけ取り出す**ことだった。成功すれば、同じ思考時間でより多くの探索を行える可能性がある。ただし、固定深度で速くなることは棋力向上そのものではない。固定時間対局で勝率が上がって初めて、棋力への効果を主張できる。

候補は次の条件に限定した。

- 対象は内部のmain searchだけ。root searchとquiescence searchは変更しない
- 擬似合法手が64手以上あるノードだけで有効化する
- 全候補の点数は従来と同じ時点で計算する
- 優先順位は「点数の降順、同点なら元の生成順」で固定する
- 候補をOFFにすれば従来経路へ戻る研究用exportとし、本番経路には接続しない

実装差分は[研究用patch](../wasm-spike/assembly/lazy-move-picker-research.patch)、隔離された候補は[研究用WASM](../wasm-spike/artifacts/shogi-lazy-move-picker-research.wasm)に固定した。

## 最初の案：selection scanは素直に遅かった

最初に試したのは、未探索の候補を毎回走査して最高点の手を1つ選ぶ方法だった。数手しか調べない局面なら全ソートを避けられるため有利に見える。しかし、候補を多く取り出すと同じ配列を繰り返し走査する。

実測では、有効化する最低手数を2、16、32、48、64と変えても、速度差は順に**-0.96%、-6.55%、-1.03%、-2.35%、-1.94%**だった。すべて従来より遅い。理屈を追加して救済せず、この方式はここで止めた。

この5値は初期の短い探索ログから丸めた概算で、生reportは追跡していない。正式な効果量としてではなく、「全条件で遅く、次へ進めなかった」という早期打ち切り記録として残す。

この失敗から、完全ソートを避けるだけでは足りず、**次の最大要素を取り出す費用自体が十分小さくなければならない**と分かった。

## stable heapへ切り替えた

次に、同じ安定順序を保つmax-heapを試した。heapの構築と取り出しは対数時間で、枝刈りまでに必要な手だけを取り出せる。コピーを持つ版、in-place版、zero-window限定、全windowへ適用する版を順に比較した。

ここで使った64局面は調整専用であり、正式な証拠には使っていない。

| 調整候補                         |    全体NPS差 |   局面中央値 | 判断                              |
| -------------------------------- | -----------: | -----------: | --------------------------------- |
| copy heap、zero-window、64手以上 |     +5.6780% |     +4.8736% | 元の全体+8%基準に未達             |
| in-place、zero-window、32手以上  |     +6.3861% |     +4.0020% | 中央値とtailが弱く不採用          |
| in-place、zero-window、48手以上  |     +4.5873% |     +4.2335% | 不採用                            |
| in-place、zero-window、64手以上  |       +6.25% |       +4.78% | 閾値だけ維持                      |
| in-place、全内部window、64手以上 | **+6.8684%** | **+5.6723%** | 未使用の正式データへ1回だけ進める |

途中、結果を見たあとに基準を全体+3%、中央値+2%へ緩めれば「合格」に見える確認もあった。しかし、それは事後的な基準変更であり、正式合格としては使えない。最終判断では当初の厳しい基準へ戻した。

## 正式v2を結果を見る前に固定した

正式実験では、実装や閾値調整に使っていない64局面を用意した。内訳は序盤、中盤、持駒の打ち手が多い局面、王手回避局面を各16局面。調整用v1とはcanonical SFENを分離し、ブラウザ由来データは元対局も重ならないようにした。局面選抜には候補エンジンの結果を使っていない。

実験前に[正式計画](../ml/protocols/stable-heap-move-picker-formal-v2-plan.json)へ、候補・ベースライン・ライブ重み・局面・生成器・計測器のbytesとSHA-256、計測順、合格基準、失敗時の停止条件を固定した。[正式fixture](../wasm-spike/lazy-move-picker-fixture-v2.json)は[fixture生成器](../wasm-spike/build-lazy-move-picker-fixtures.ts)から再生成でき、判定は[正式gate](../wasm-spike/lazy-move-picker-gate.ts)で行った。

ただし、この計画と結果は今回同じPRで初めてcommitする。ローカルでは結果ファイル生成前に計画を固定し、そのSHA-256を結果証拠へ残したが、第三者のtimestampや先行commitはない。したがって、ここでいう「事前固定」は**ローカルの実行順序と固定identity**を指し、外部から時刻まで独立証明された事前登録を意味しない。今回の結果は不合格なので昇格判断を有利にする方向の問題は生じていないが、次のv3では計画だけを先にcommitしてから未使用holdoutを開く。

主な合格基準は次のとおりだった。

| 判定項目                   |                  事前基準 |
| -------------------------- | ------------------------: |
| 固定深度の探索一致         |            64 / 64、相違0 |
| 全体の固定仕事量NPS        |                   +8%以上 |
| 局面ごとのNPS差の中央値    |                   +5%以上 |
| 局面ごとのwall time悪化p90 |                   +2%以下 |
| 4分類の集計                |              すべて0%以上 |
| 機能の発動                 | 全体および各分類で1回以上 |
| technical fault            |                         0 |

計測は固定深度5、quiescence depth 8、TT共有なし、各探索前にTTを消去して行った。順序バイアスを抑えるため、baseline / candidateをABBAとBAABの組み合わせで同じ回数だけ走らせた。

## 正式結果：速くはなったが、合格ではない

正式結果は次のとおりだった。

| 項目             |           実測 |         基準 | 判定       |
| ---------------- | -------------: | -----------: | ---------- |
| 探索一致         | 64 / 64、相違0 |        相違0 | 合格       |
| 全体NPS差        |   **+6.7915%** |      +8%以上 | **不合格** |
| 局面中央値       |   **+2.9145%** |      +5%以上 | **不合格** |
| wall time悪化p90 |       +1.4342% |      +2%以下 | 合格       |
| 4分類の集計      |     すべて非負 | すべて0%以上 | 合格       |
| 各分類での発動   |           あり |         あり | 合格       |
| technical fault  |              0 |            0 | 合格       |

「探索一致」は、64局面すべてでbest move key、score、completed depth、nodes、leavesが一致したという意味である。候補経路は固定深度確認で421,752ノード発動しており、たまたま機能が動かなかった比較でもない。

分類別には差が大きかった。

| 局面分類         | 全体NPS差 |
| ---------------- | --------: |
| 序盤             |  +0.0150% |
| 中盤             |  +0.8008% |
| 打ち手が多い局面 |  +6.1496% |
| 王手回避局面     |  +8.5061% |

候補手の多い難しい局面では効いた一方、序盤と通常の中盤ではほぼ変わらなかった。そのため、重い一部局面に引っ張られる全体値は+6.79%でも、典型局面を表す中央値は+2.91%に留まった。

正式結果の元ファイルは184,725 bytes、SHA-256は`6ce667e41bcc0f8464c6fbfae47660de48f2050e868675f260e9c877ae2f1b72`である。全fixed-depth行と全timing行を保持し、絶対pathだけrepo-relativeへ変換した[追跡可能なraw report](./data/shogi-stable-heap-move-picker-formal-v2-raw-2026-07-25.json)と、公開用の要約・identityを収録した[機械可読証拠](./data/shogi-stable-heap-move-picker-formal-v2-2026-07-25.json)をrepo内で再監査できる。

## なぜ+6.79%でも本番へ入れなかったのか

6.79%は誤差として無視する値ではなく、実際の高速化signalである。しかし、次の理由で「AIが強くなった」とは言えない。

1. **事前基準に届いていない。** 結果を見て+8%を+6%へ下げれば、今後の実験でも都合のよい判定ができてしまう。
2. **固定深度の速度実験である。** 同じ仕事が速く終わったことは確認したが、固定時間で深く読めたか、勝率が上がったかは測っていない。
3. **利得が局面に偏っている。** 序盤は+0.015%、中盤は+0.80%で、中央値も+2.91%に留まった。
4. **本番差分には保守費用がある。** 研究用分岐と追加メモリを恒久的に持つなら、利得が明確でなければ割に合わない。

事前計画では、正式gate合格時だけ「候補ON対OFF、同じライブ重み」の固定時間56局screenへ進むことにしていた。今回はgate不合格なので、この対局を走らせていない。勝敗、Elo、段位について新しい証拠はない。

## index-only heapは不採用、packed keyも強い次候補とは言えなかった

full moveをheap内で交換する費用を減らすため、`u16`の元候補indexだけをheap化し、点数と指し手は元配列を参照する案も試した。理論上は交換するデータが小さくなる。

しかし、partial popとfull popを含むマイクロベンチでは、8条件すべてで現行heapより遅かった。間接参照の費用が、交換量削減の利点を上回ったと考えられる。探索用の生scriptとreportを保存しなかったため、ここでは正確な割合を主張しない。全条件で劣ったという打ち切り判断だけを残し、新しいformal holdoutや固定時間対局は作らず不採用にした。

そこで、間接参照を増やさず比較回数と交換量を減らす案として、heapの1要素を「moveの`i32`と比較用の`u64 key`」にまとめるpacked-key方式を試した。keyは上位32 bitにsigned score、下位32 bitに元の生成順を反転した`~ordinal`を持つ。これにより「score降順、同点なら元の生成順」という従来の安定順序を、1個のkey比較で表現する。

最初の短いNode 20計測は大きな利得に見えたが、現在のNode 22で再現すると数字が大幅に縮んだ。そのため最初の値を採用せず、[benchmark source](../wasm-spike/packed-heap-microbench/bench.ts)、[runner](../wasm-spike/packed-heap-microbench/run.mjs)、[生結果](../wasm-spike/packed-heap-microbench/result.json)を追跡し、AssemblyScript 0.28.19とbuild flag、Node 22、各block 100ms以上、同一仕事量、ABBA / BAAB順、3周を固定して取り直した。

同点を多く含む18,000 vectorsに加え、`INT32_MIN` / `INT32_MAX`を含む12,288 vectorsで取り出し順を検証した。現行heapとpacked-key heapは、どちらも基準のstable sortに対して不一致0で、arm別checksumも一致かつ非0だった。性能は候補数48 / 64 / 96 / 128と、先頭8手だけ、25%だけ、全手を取り出す3条件を組み合わせた。

| 長block小ベンチ                  |                           結果 |
| -------------------------------- | -----------------------------: |
| 比較した条件                     | 4候補数 × 3取り出し量 = 12条件 |
| 通常 / signed境界の順序不一致    |           current 0 / packed 0 |
| 最短の実測block                  |                       151.58ms |
| 全12条件のwall time短縮          |               **0.51〜16.06%** |
| 全12条件の同一仕事量throughput差 |             **+0.52〜+19.14%** |
| 64手以上・先頭8手のthroughput差  |              **+0.52〜+3.65%** |

全手を取り出す条件では約13〜19%のthroughput差がある一方、αβ探索の狙いである早いcutoffに近い「64手以上から8手だけ」のkernel利得は約0.5〜3.7%だった。move pickerは探索全体の一部なので、正式v2で不足した全体1.21ポイント・中央値2.09ポイントを埋める保証は薄い。固定深度の実探索、正式gate、固定時間対局、棋力向上はどれも未確認である。

したがってpacked-key方式の次手は、やるとしても隔離candidateでの安価な実探索tuningまでに限定する。そこでend-to-endの利得が正式v2候補を明確に超えない限り、新しいv3 holdoutは作らない。結果をすでに見たv2 fixtureを正式判定へ再利用することもしない。

## 正直な棚卸し：形式作業は棋力を上げなかった

この一連の作業より前に、所有権、改ざん検知、鍵、PR境界、安全な本番gateを細かく整備した。それらは、間違った重みや未検証candidateをライブへ入れないためには意味がある。しかし、**その作業自体が探索を深くしたり、評価関数を賢くしたり、勝率を上げたりしたわけではない。棋力への直接寄与は0だった。**

問題は、安全対策が存在したことではなく、棋力signalを安く測る前に形式を増やしすぎたことだった。結果として、計算資源と時間の一部を、強さへ直結しない境界整理や文書化へ使った。予定が大きく遅れた理由の一つであり、「後で役立つかもしれない」を棋力向上と同じ進捗として扱ったのは誤りだった。

今回のmove-picker研究では、その反省から次の順序へ改めた。

1. 最小の実装とマイクロベンチで、弱い案をすぐ落とす
2. 調整用データで効果量を測り、有望な候補だけを1つ選ぶ
3. 結果を見る前に基準を固定し、未使用データで1回だけ判定する
4. 不合格なら対局、本番統合、デプロイを行わない
5. 所有権・署名・PR境界は、本番反映が見える段階で必要最小限だけ追加する

安全gateを捨てるのではない。**「強くなる可能性の検証」と「安全に配るための形式」を順番どおりに行う**という教訓である。

## 結論

stable heapは、固定仕事量では全体6.79%の実在する高速化を示した。特に打ち手の多い局面と王手回避局面では効果があった。一方で、事前に決めた全体+8%、中央値+5%には届かず、通常局面の利得も小さかった。

したがって、この正式v2 candidateは研究結果として保存するが、本番には採用しない。index-only派生も不採用である。固定時間対局を行っていない以上、現在のAIがこの作業で強くなったという主張はしない。

packed-key heapは全手を取り出すkernelでは速かったが、実候補に近いpartial workloadの利得は小さかった。隔離candidateと実探索tuningを低コストで1回試す余地はあるものの、現時点で次の本命や棋力向上候補とは扱わない。v2の不合格をpacked方式の合格へ読み替えたり、開封済みのv2を正式証拠へ再利用したりはしない。

packed方式が安価な実探索でも弱ければそこで止め、その後の計算資源を自己対局・再学習・候補対現行の固定時間対局のように、最終的な勝率へ直接つながる実験へ戻す。ライブを置き換えるのは、候補が事前固定した強度gateを通過した後だけである。
