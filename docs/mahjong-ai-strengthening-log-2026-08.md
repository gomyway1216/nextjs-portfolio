## 1. なぜ M5 のランダム打ちベースラインでは守備を測れないのか

M5 の `scripts/mahjong-ai-baseline.ts` は「AI 1席 + ランダム打ち3席」で東風戦を回す。
300局・seed 1 での実測(本ラウンドで再取得):

| difficulty | 平均順位 | 1位/2位/3位/4位 | 和了率 | **放銃率** |
|---|---|---|---|---|
| easy(守備無効) | **1.0100** | 297/3/0/0 | 44.7% | 0.1% |
| medium(守備あり) | **1.0333** | 291/8/1/0 | 48.2% | 0.0% |
| hard(R1のEV押し引き) | 1.0133 | 297/2/1/0 | 52.4% | 0.1% |

**放銃率が 0.0〜0.1%** ——これが全てである。ランダム打ちの3人は狙ってテンパイを組まないので、
こちらがどれだけ無筋を押しても放銃しない。守備は「効かない保険」であり、
オリた分だけ和了機会を失う**純損**になる。結果として守備を切った easy が medium より
「強い」という、麻雀としては明らかに誤った順序が出る。しかも上限は平均順位 1.0 に張り付いており
(300局中297局が1位)、**天井効果で解像度そのものが無い**。

つまりランダムベースラインは「AI が壊れていないこと」を確認する健全性バーであって、
押し引きのチューニングには原理的に使えない。M5 のドキュメントもそう書いてあるが、
数字で示しておく価値がある。**守備を測れるのは AI 同士の対戦だけ**であり、M7 のハーネスはそのために存在する。

同じ2つのアームを複製壁の AI 同士対戦にかけると、順序は即座に逆転する
(`mahjong-duplicate-ab-v1-defence-check.json`、500セット / 2000局):

| | easy | medium |
|---|---|---|
| 平均順位 | **2.8410** | **2.3863** |
| 放銃率 | 22.26% | 12.84% |
| 和了率 | 17.94% | 23.45% |

ペア差 **+0.4547 ± 0.0298**(easy が悪い方向)、`t(499) = 15.24`、`p = 2.6e-43`。
ランダム相手では 0.1% だった放銃率が、AI 相手では 22% になる。守備が仕事を始める場所は、
そもそも相手がテンパイする卓だけである。

## 2. 複製壁(duplicate wall)とペアリングで何が買えるのか

### 2.1 設計

1セット = **同一シードの壁(同一の山・配牌・ツモ順)で4局**。被験アーム A の座席を 0→1→2→3 と
ローテーションし、残り3席は常に対照アーム B。したがって

- 配られた4つの手牌は、セットの中で **A が1回ずつ、B が3回ずつ** 打つ
- A が親を引くのは4局のうちちょうど1局
- A/B は完全に同じシード集合を見る

実装上の肝は**乱数ストリームの分離**である。壁用 RNG は `startGame`/`advanceHand` にしか渡さない
ので、「ゲーム内 k 局目の壁」はシードだけの純関数になり、打ち回しがどれだけ分岐しても
k 局目の山は4ローテーションで同一になる。決定用 RNG は壁ストリームから引かず、
`(seed, 局番号, 手番番号, 座席, salt)` から都度生成する ——
つまり **common random numbers**。テストで実際に「4ローテーションの山136枚の並びが完全一致」を
検証している(`tests/unit/components/game/Mahjong/match.test.ts`)。

### 2.2 検定

観測単位はセット。セット `i` について

```
d_i = (A の4局の平均順位) − (B の12席局の平均順位)
```

を作り、`d` に対する両側1標本(=対応のある)t検定を行う。順位は小さいほど良いので、
ゲートは「`mean(d) < 0` かつ `p < 0.05`」。t分布の裾は不完全ベータ関数で厳密に計算しており
(正規近似ではない)、依存パッケージは追加していない。閉形式で答えが分かる df=1(コーシー)と
df=2 のケースでユニットテストしている。

### 2.3 ブロッキングで実際にどれだけ分散が減ったか

同じ推定量・同じ局数のまま**ブロッキングだけを捨てた**場合の標準誤差(1局を1観測とした
`perGameContrast`)と比較する。1局の4順位は必ず和が10なので、A の順位が決まれば B 3席の平均も
決まり、局単位の対比は `(順位 − 2.5) × 4/3`。点推定はブロック版と厳密に一致し、**標準誤差だけが違う**。

| 対戦 | セット数 | ペア差 | ブロックSE | 非ブロックSE | SE比 | 実効サンプル倍率 |
|---|---|---|---|---|---|---|
| medium vs medium(決定的) | 3 | **厳密に 0** | 0 | 0.44947 | ∞ | ∞ |
| **hard-ev vs medium(R1)** | 2000 | −0.0622 | **0.01052** | 0.01619 | **1.539×** | **2.37×** |
| easy vs easy(saltあり) | 500 | +0.0127 | 0.03123 | 0.03333 | 1.067× | 1.14× |
| easy vs medium | 500 | +0.4547 | 0.02984 | 0.03292 | 1.103× | 1.22× |

**R1 の 8,000局は、ブロッキングなしなら約 19,000局に相当する。** p値で言うと
ブロック版 `3.98e-9` に対し非ブロック版は `1.24e-4` ——同じデータ、同じ点推定、
4桁以上違う確信度である。

ここから読み取れる法則が1つある。**ブロッキングの効きは「アームの近さ」ではなく
「4ローテーションが同じ軌道に留まる長さ」に比例する。**

- 決定的な同一ポリシー同士なら、4局は座席のラベルを付け替えただけの同じ局になるので
  A の順位は必ず `{1,2,3,4}`、ペア差は**厳密にゼロ**(§2.4)。
- R1 のように押し引き判断だけが違うアームは、判断が分かれる局面まで軌道が一致するので **2.37×** 残る。
- easy は毎巡上位3候補から乱択するので、salt を変えた瞬間に軌道が割れる。だから
  「同じポリシー同士」でも **1.07×** しか残らない。easy vs medium も同様に **1.10×**。

**したがって複製壁は「小さな改良を測るとき」に最も効く。** これは都合が良い。
大きな改良は元々どんな測り方でも見えるし、強化ループが後半で扱うのは常に小さな改良だからである。

### 2.4 AA対照(アームが自分自身と打つ)

2種類やっている。

**(a) 決定的AA — 厳密ゼロ。** medium vs medium は、上記の理由でセットごとのペア差が
**厳密に 0**(有意差なしより強い主張)。ユニットテストで3セット分、
「A の順位が `{1,2,3,4}` に一致」「`diff === 0`」「A の和了数×3 == B の和了数」まで検証している。
これは統計的な検定ではなく**配線の検証**である ——座席ローテーションと集計の紐付けを1本でも
間違えれば、この等式は壊れる。

**(b) 確率的AA — 本物の帰無実験。** それだけでは「統計側」が検証できないので、
`--aa-salt` で A アームの決定ストリームだけを別種にし、乱択を使う easy 同士で打たせた。
**500セット / 2,000局**(seed 4242、`mahjong-duplicate-ab-v1-aa-control.json`):

```
ペア差 +0.01267,  SE 0.03123,  95%CI [-0.04855, 0.07388]
t(499) = 0.406,   p = 0.685    → 有意差なし(期待どおり)
```

500セットは R1 の検出効果量(0.062)なら `t ≈ 2.0` 相当を出せる規模なので、
「差が無い」ではなく「**この規模で見えるはずの差は無かった**」と言える。

## 3. EVテーブルの推定(R1の材料)

§M7 が名指しした2つのテーブルを、AI自身の自己対戦ログから推定した。

```
node -r tsx/cjs scripts/mahjong-ai-match.ts --a=medium --sets=500 --seed=99 \
  --ev-log=docs/data/mahjong-ev-tables-v1-source.json
```

**11,179局 / 528,124回の打牌判断**(独立2,000ゲーム、seed 99、東風)。
`--ev-log` は複製セットではなく**独立ゲーム**を回す ——決定的ポリシーの自己対戦では
1セットの4局は同じ局なので、複製すると同じ手牌を4回数えて行数だけ4倍に見えてしまう。

推定したのは4つ。すべて「打牌の瞬間にポリシーが見えている特徴量」で条件付け、局の決着で解決している。

1. **和了率**`[自分の打牌数][打牌後のシャンテン]`(18×7)。テンパイ×0巡目で 68.3%、
   テンパイ×17巡目で 5.0%、3シャンテン×8巡目で 1.1%。
2. **放銃率**`[危険度バンド]`(13)。バンドは `safety.ts` の `weightedDanger` の整数部。
   現物相当のバンド0で **0.13%**、無筋中張牌のバンド9+で **17.0%** —— **130倍**。
   これが危険度読みを実装している理由そのもの。
3. **残り打牌数**`[巡目]`:押しが約束する枚数。3巡目なら約8枚、14巡目なら約2枚。
4. **和了打点**`[estimateHan]` と **放銃打点**`[脅威の種類]`。リーチへの放銃は 6,000点、
   役牌仕掛けへの放銃は 3,291点 —— **オリの価値は相手によって2倍違う**。v1の閾値ルールには
   この区別を表現する手段が無かった。

平滑化は3ルールのみ(観測30未満のセルは1巡前を継承 / 和了率は巡目・シャンテンに関して単調化 /
放銃率と打点は PAVA で単調かつ十分な観測数になるまで併合)。詳細と既知のバイアスは
`evTables.ts` の冒頭コメントに書いた。

### 3.1 最初に失敗したモデル(記録)

素直に

```
押しEV = P(和了) × E[打点]
オリEV = 残り打牌数 × P(放銃 | この牌の危険度) × E[放銃打点]
```

と書くと、**ほぼ全てのテンパイがオリになる**。6巡目・テンパイ・2翻・危険度バンド8 で
押し 3,081点 vs オリ 4,690点。原因は明白で、「これから10枚切る牌が全部いま切ろうとしている
無筋と同じ危険度」という仮定が現実的でないから。修正は測定値で行った ——
いま切る1枚だけを自分のバンドで、それ以降は**脅威がある状況での全打牌の平均放銃率
(5,469/174,366 = 3.137%)**で課金する。同じ局面が押し 3,081 vs オリ 1,700 になる。
この係数も推定値であって手で決めた定数ではない。

## 4. R1: EV押し引き vs 閾値押し引き(2026-08-26、**hard 昇格**)

### 4.1 事前登録

`docs/data/mahjong-duplicate-ab-v1-plan.json` を**実験の実行前にコミット**した
(コミット `43c9941b`、結果JSONより前)。固定したもの: アーム定義、シード範囲、
セット数、主指標、検定、ゲート、退行を許さない診断指標、そして禁止事項
(結果を見てからアームを変えない・シードをつまみ食いしない・EVテーブルをR1のシードで
再推定しない・medium の挙動を変えない)。

検出力の見積もりには **別シード(777)の30セットのパイロット**を使い、その事実と数値
(`sd(d) = 0.3238`、2000セットでの最小検出効果量 0.0203)もプラン内に開示してある。

プラン JSON は登録後**一切書き換えていない** ——`currentState` は登録時点の状態
(`experimentExecuted: false`)のまま残してある。結果は結果JSONとこのログに書く、という分担。

### 4.2 実行

```
node -r tsx/cjs scripts/mahjong-ai-match.ts --a=hard-ev --b=medium \
  --sets=2000 --seed=20260826 --length=tonpuu --jobs=7
```

**2,000セット = 8,000局 = 44,743ハンド**、268万回の判断、1判断 **0.329ms**、
7シャード並列で **144秒**(55.5局/秒)。シャード分割は純関数シードなので単一プロセスと
バイト一致することを確認済み。

### 4.3 結果

| 指標 | A: hard-ev | B: medium | 判定 |
|---|---|---|---|
| **平均順位** | **2.4534** | **2.5155** | 主指標 |
| 平均素点 | 25,524 | 24,783 | ガード通過 |
| 和了率 | 21.02% | 21.73% | −0.71pt(上限3.0pt) |
| **放銃率** | **10.74%** | **14.58%** | −3.84pt |
| 立直率 | 28.21% | 31.06% | 参考 |
| 副露率 | 18.02% | 18.54% | 参考 |
| 平均和了打点 | 5,765 | 5,779 | 参考 |
| 平均放銃打点 | 5,034 | 5,420 | 参考 |
| 順位分布 1/2/3/4 | 1990/2128/2147/1735 | 6010/5872/5853/6265 | 参考 |

```
ペア差(A − B) = -0.06217
SE            =  0.01052
95%CI         = [-0.08278, -0.04155]
t(1999)       = -5.9114
p(両側)       =  3.98e-9        → ゲート達成
```

**ゲート達成 → `HARD_POLICY.useEvPushFold = true` に昇格**(`hard`/`expert`/`master` が同時に動く)。
事前登録のガード指標(放銃率の悪化 ≤1.0pt、和了率の低下 ≤3.0pt、平均素点が B 以上、
1判断 ≤1.0ms)はすべて通過。

### 4.4 何が起きたのか

数字の形が非常に素直である。**放銃率が 3.84pt(相対26%)下がり、和了率は 0.71pt しか下がらなかった。**
つまりEV比較は「和了をほとんど諦めずに放銃だけを減らす」交換に成功している。
v1の閾値ルールは「1シャンテンなら押す」を**切る牌の危険度と無関係に**適用していたので、
現物で押せる1シャンテンも、無筋ドラで押すしかない1シャンテンも同じ扱いだった。
その2つは放銃率が 130倍 違う。R1 が買ったのは主にこの区別である。

立直率が 2.85pt 下がっているのは副作用で、押し引きでオリに回った局はリーチまで辿り着かないため。
平均和了打点がほぼ同じ(5,765 vs 5,779)なのは、「安手だけ降りている」わけではないことの傍証。
平均放銃打点が下がっている(5,034 vs 5,420)のは、リーチ(放銃打点6,000)に対して
より強く降りるようになった結果として整合的。

## 5. 測り方の教訓(次のラウンドに引き継ぐこと)

1. **強さの測定器は、測りたい性質が働く環境でなければならない。** 守備を測るのに
   守備が無意味な相手を使ってはいけない。M5 の easy > medium はバグではなく、
   測定器の適用範囲外の値だった。
2. **ブロッキングは「軌道が一致する長さ」に比例して効く。** 小さな改良ほど効くので、
   強化ループの後半ほど価値が上がる。効果量は仮定せず毎回測って結果と並べて出す
   (ハーネスが自動で出す)。
3. **A/B の順位を素朴な2標本検定にかけてはいけない。** 同一局内の A と B の順位は
   和が10で機械的に従属しており、Welch は標準誤差を過小評価する
   (R1 では 0.01416 と出る。正しい値は 0.01052)。ハーネスは `naiveTwoSample` として
   併記はするが**ゲートには使わない**。
4. **決定的な自己対戦のAAは厳密ゼロになる。** これは検定ではなく配線テストとして使い、
   統計側の帰無検証は乱択ポリシー + salt で別途回す。
5. **モデルの係数は測る。** §3.1 の「将来の危険度」係数は、手で決めていたらそのまま
   チューニングの自由度=言い訳になっていた。

## 6. R2 の候補(優先順)

1. **押し引きラベル付きのEVログ。** いまの `DEAL_IN_PROBABILITY_BY_DANGER` と
   `BASELINE_DEAL_IN_PROBABILITY` は「すでにオリを知っているポリシー」の打牌で条件付いており、
   最後まで押し切る席が実際に浴びる危険を過小評価している。ログに押し/オリのラベルを足し、
   押し継続時のみで再推定する。R1 の効果がバイアスの上に乗って**さらに**伸びる可能性が高い。
2. **鳴きの押し引き。** `chooseCall` はまだ `FOLD_MIN_SHANTEN` の閾値でパスを決めている。
   R1 は「1実験1変数」を守るために打牌側だけを差し替えた。次はここを同じEV比較にする。
3. **リーチ/ダマの判断のEV化。** `shouldDeclareRiichi` は3条件の閾値ルールのまま。
   立直率が R1 で 2.85pt 動いた以上、押し引きと相互作用している。
4. **待ち取り・手替わりの選択**(§M7の強化ループ3本目)。
5. **半荘での再現確認。** R1 は東風のみ。順位期待値の構造は半荘で変わる(親の価値・
   オーラスの条件戦)ので、昇格済みポリシーを `--length=hanchan` で追試する。
   これは新しい昇格ではなく既存昇格の外挿検証として回す。

## 付録: ハーネスの使い方

```bash
# A/B(既定の出力先は docs/data/ 配下に自動命名)
node -r tsx/cjs scripts/mahjong-ai-match.ts --a=hard --b=medium --sets=2000 --seed=1 --jobs=7

# 帰無対照(乱択ポリシーの決定ストリームだけずらす)
node -r tsx/cjs scripts/mahjong-ai-match.ts --a=easy --b=easy --sets=500 --seed=1 --aa-salt=aa

# EVテーブル用の自己対戦ログ
node -r tsx/cjs scripts/mahjong-ai-match.ts --a=medium --sets=500 --seed=99 \
  --ev-log=docs/data/mahjong-ev-tables-v1-source.json
```

アームは組み込み名(`easy`/`medium`/`hard`/`expert`/`master`/`hard-ev`)か、
`AiPolicy` を書いた JSON ファイルのパス。恒久的なアームは `NAMED_ARMS` に足す。
`package.json` はバイトシールされているので npm script は追加しない。
