# 麻雀（リーチ麻雀）ソフト開発プラン — 2026-08

将棋 (`src/components/game/ShogiImproved/`) と同じ規律で、ブラウザで遊べる 4 人打ちリーチ麻雀
（人間 1 + AI 3）を作り、将棋と同様にブログで経緯を公開するための実行プラン。
**各マイルストーン（M1〜M8）はサブエージェントに 1 つずつ割り当てられる粒度**で書いてある。

- 対象リポジトリ: `nextjs-portfolio`（このリポジトリ）
- 公開 URL: `/games/mahjong`
- 参考にする既存資産: 将棋の worker 分離・自己対戦ハーネス・`docs/data/` エビデンス JSON・
  `docs/blog-*.md`（日英ペア）のブログ運用

---

## 0. 実現可能性の整理（結論: 作れる。ただし将棋と設計思想が違う）

| 観点 | 将棋 | 麻雀 |
|---|---|---|
| 情報 | 完全情報 | **不完全情報**（他家の手牌・山が見えない） |
| プレイヤー | 2 人ゼロサム | 4 人・確率的（ツモ順） |
| 強さの源泉 | 深い探索（αβ+NNUE） | **正確な局面評価 + 期待値判断**（探索はほぼ不要） |
| 実装の重心 | 探索の速度 → WASM 必須 | **ルール実装とシャンテン/点数計算の正確さ** → TS で十分速い |
| 強さ検証 | 自己対戦 80〜200 局で有意 | 分散が非常に大きい → **複製壁（duplicate wall）+ 1000 戦単位**が必要 |

つまり「αβ探索を移植する」のではなく、

1. **ルールエンジンを完璧にする**（テストベクタで担保）
2. **シャンテン数・受け入れ（ukeire）計算**を高速に持つ
3. その上に **押し引き（EV）ヒューリスティック AI** を載せる
4. 将棋と同じ **ペア対戦 A/B ハーネス**で強化ループを回す

という順序になる。世界最強級（Suphx / Mortal）は深層 RL だが、ヒューリスティック +
EV テーブルだけでも「天鳳の中級者を安定して倒す」レベルには到達でき、ブラウザ内で
1 手 1ms 未満で動く。NN 化は将棋の NNUE 強化ログと同じく「公開後の強化フェーズ」に回す
（§M9）。WASM / SharedArrayBuffer / COOP ヘッダは**初期リリースでは不要**
（将棋で必要だったのは探索速度のためであり、麻雀 v1 の AI は軽い）。

## 1. ルール仕様（M0 で確定させるデフォルト）

v1 で実装するルール。迷ったらここに従う。**このセクションが仕様の単一情報源**。

- 4 人打ち、東風戦（ハンチャンは設定で選択可。AI ハーネスは東風で回す）
- 25000 点持ち 30000 点返し、ウマは v1 では無し（順位のみ表示）
- 赤ドラ 3 枚（5m/5p/5s 各 1）、一発・裏ドラあり、カンドラ・カン裏あり（即めくり）
- 喰いタンあり・後付けあり（アリアリ）
- ダブロンあり（供託・本場は放銃者払い、親流れ判定は頭ハネしない）
- 途中流局は**九種九牌のみ**（四風連打・四家立直・四槓散了は v1 では無し）
- 流し満貫なし、切り上げ満貫なし、人和なし
- パオ（大三元・大四喜の責任払い）は v1 では無し（M9 候補）
- 三槓子（2 翻）あり。ダブル役満なし（国士13面・四暗刻単騎・純正九蓮も単倍）
- 連風牌の雀頭は 4 符（場風・自風を別々に数える）
- ロンで完成した刻子は明刻扱い（符・三暗刻/四暗刻の判定とも）
- 役満同士は複合する（大三元＋字一色＝ダブル役満）。通常役は役満と複合しない
- ダブロンの本場・供託は頭ハネ順で上家（`wins[0]`）が総取り、親の連荘は頭ハネしない
- トビ終了あり（0 点未満で終局）
- 役・点数は標準（符計算含む完全実装。青天井なし、数え役満あり）

### 牌の内部表現（全モジュール共通の契約 — 最初に固定し、以後変更禁止）

- **牌種 (kind)**: `0..33`。`0..8`=萬子1-9, `9..17`=筒子1-9, `18..26`=索子1-9,
  `27..30`=東南西北, `31..33`=白發中。
- **牌 ID (tileId)**: `0..135`。`kind = tileId >> 2`。赤 5 は
  `tileId === 16(5m0), 52(5p0), 88(5s0)`（各 kind の 0 番目コピー）を赤とする。
- 手牌は `Uint8Array(34)` のカウント表現 + 赤保有フラグ、河・副露は tileId 列。
- 乱数は **`seedrandom` 等を使わず自前の xorshift/PCG をシード付きで実装**
  （ハーネスの複製壁再現に必須。将棋ハーネスのペア開局と同じ思想）。

### エンジン規約（将棋から引き継ぐ規律）

- `engine/` と `ai/` は **DOM・React に一切依存しない**（`scripts/` から tsx で直接 import
  して回すため。将棋 V20 と `shogi-ai-match.ts` の関係と同じ）。
- すべての状態遷移は「合法アクション列挙 → 1 つ適用」の純関数スタイル。
  `applyAction(state, action) -> state`。非合法アクションは throw。
- 不変条件: **どの時点でも 136 枚が山+王牌+手牌+河+副露+和了牌に過不足なく存在**。
  テストで常時検証する（将棋 perft に相当する健全性検査）。

### M2: シャンテン数・受け入れ計算（1〜2 日）★正確さが最重要

**成果物**: `shanten.ts`, `ukeire.ts`（+ テスト）
- 一般形: スーツごとの (面子, 面子候補) 分解を DP/メモ化で計算する標準アルゴリズム。
  七対子・国士無双は別式で計算し min を取る。副露数を考慮。
- `ukeire(hand)`: 34 種それぞれを 1 枚加えたときシャンテンが下がる牌種と残り枚数
  （見えている牌を差し引く）を返す。
- 性能目標: シャンテン 1 手 <0.05ms、ukeire 全走査 <2ms（TS で十分達成可能）。

**ゲート（テスト）**
- 公開されているシャンテン数テストケース集（例: 天鳳系の 10000 手牌ベクタ。
  `tests/unit/components/game/Mahjong/fixtures/shanten-cases.txt` としてリポジトリに
  同梱できるライセンスのものを選ぶ。なければランダム手牌に対する**素朴な全探索実装
  （遅いが確実な参照実装）との突き合わせ 10000 件**で代替。参照実装は
  `tests/.../shantenReference.ts` に置く）
- 和了形 0 面子〜4 副露の境界ケース、国士 13 面待ち、七対子と一般形の交差ケース

### M3: 役判定・点数計算（2 日）★テストベクタ勝負

**成果物**: `yaku.ts`, `score.ts`（+ テスト）
- 全標準役（1 翻〜役満、食い下がり、複合、役満複合）、ドラ/赤/裏は役ではなく加算翻
- 符計算（副底 20、面子符、待ち符、雀頭符、**門前ロン +10 符**、ツモ +2 符、
  七対子 25 固定、平和ツモ 20、**最後に 10 符単位へ切り上げ**。
  ※§1 の「切り上げ満貫なし」とは別物）
- 支払い計算（親子、ツモ/ロン、本場、供託、ダブロン、トビ）
- 和了形分解は複数分解を全列挙して**最高点を採用**（高点法）

**ゲート（テスト）**
- 符×翻 → 点数の全テーブル一致（20 符〜110 符 × 1〜4 翻、満貫〜役満）
- 高点法が要るケース（例: 平和ツモ 20 符 vs 別分解 30 符、一盃口を含む分解選択）
- 役判定スナップショット 100 ケース以上を fixtures に列挙
  （国士/九蓮/四暗刻単騎などのダブル役満は §1 に従い**シングル役満**として扱う。
  ※ここも v1 仕様として rules.ts に明記）

### M4: 局進行の状態機械（2〜3 日）

**成果物**: `gameState.ts`, `actions.ts`, `furiten.ts`（+ テスト）

**ゲート（テスト）**

### M5: ヒューリスティック AI v1 + worker（2〜3 日）

**成果物**: `ai/heuristicAI.ts`, `ai/safety.ts`, `mahjong-ai.worker.ts`,
`mahjongAiWorkerClient.ts`（+ テスト）

**攻め（打牌選択）**
1. シャンテン数を上げない打牌集合を列挙
2. その中で ukeire 最大を基本とし、同率は牌価値（ドラ近接・良形残り・安全度）で順序付け
3. リーチ判定: テンパイ・門前・待ち 4 枚以上 or 打点十分なら宣言（愚形×安手のみダマ検討）
4. 鳴き判定: 役牌ポン、タンヤオ/染め手が 2 シャンテン以内で加速する場合のみ。
   役消滅する鳴きは禁止

**守り**
- 他家リーチ/明らかな染め手に対し、自手が (2 シャンテン以上 or 安手) ならベタオリ:
  現物 > スジ > 字牌(枚数) > 壁 > 無スジの序列で安全牌選択
- 押し引きは v1 は閾値ルール（テンパイ+打点あり=押し、それ以外=引き）。
  v2 (M7) で EV テーブル化

**難易度マッピング**（`common/DifficultySelector` の 3 段階を使用）
- easy: 守り無効 + 打牌を上位 3 候補からランダム
- medium: v1 フル
- hard: v1 フル + EV 押し引き（M7 成果を接続。それまでは medium と同一で出す）

**worker**: 将棋と同じく `mahjongAiWorkerClient.ts` に `new Worker(new URL(...))` を集約。
AI 1 手は同期 1ms 未満なので SMP/ponder は不要。メッセージは
`{requestId, state, seat} -> {requestId, action}` の単純 RPC。

**ゲート**
- `mahjong-ai-match.ts`（M7 の簡易版で可）で **AI v1 vs ランダム打ち 3 席**: 平均順位 < 1.8
- 具体的な局面ユニットテスト 20 本（「リーチに現物を切る」「役なし鳴きをしない」等）

### M7: A/B 自己対戦ハーネスと強化ループ（2 日 + 継続）

**成果物**: `scripts/mahjong-ai-match.ts`（`node -r tsx/cjs scripts/mahjong-ai-match.ts` で直接起動）、
`docs/data/mahjong-*.json` への結果出力

**分散対策（麻雀 A/B の核心。将棋のペア開局に相当）**
- **複製壁**: 同一シード（=同一の山・配牌・ツモ順）で、被験 AI の座席を 4 席ローテーション
  した 4 ゲームを 1 セットとする。アーム A/B は同じシード集合を使う
- 指標: 平均順位（主指標）、素点 EV、和了率/放銃率/立直率/副露率（診断用）
- 判定: セット単位のペア差に対する検定。**東風 × 2000 セット規模**を基本とし、
  ハーネスは Node で数分で回る速度を維持する（AI 1 手 <1ms を守る）
- 将棋と同じく **プランを JSON で事前登録**（`ml/` 方式は重いので簡易版:
  `docs/data/mahjong-<exp>-plan.json` に gate・シード範囲・禁止事項を書いてから実行）

**強化ループの最初の 3 本（v2 候補）**
1. EV 押し引き: 自己対戦ログから「巡目×シャンテン→和了率」「無スジ放銃率」テーブルを推定し
   `ai/evTables.ts` に焼き込み → 押し引きを閾値から EV 比較に置換
2. 鳴き判断の精緻化（打点×速度のトレードオフ評価）
3. 手替わり・待ち取り選択（テンパイ時の待ち比較: 枚数×打点×安全度）

**ゲート**: v2 が v1 に対して平均順位で有意に勝つ（p<0.05, 事前登録した効果量）まで
本番 difficulty=hard に昇格させない（将棋の昇格規律と同じ）。

### M9a: サンマ（三人麻雀）— v1 公開後の独立マイルストーン

サンマは「設定フラグ」ではなくルール亜種であり、**四麻 v1 を出し切ってから**着手する。
M4〜M7 の実装中に着手すると型と状態機械が二重に不安定になるため、順序は厳守。

**ルール差分（v1 サンマの仕様）**

| 項目 | 四麻 | サンマ |
|---|---|---|
| 牌 | 136 枚 | **108 枚**（2m〜8m の 28 枚を除去。1m と 9m は残す） |
| 席 | 4（東南西北） | **3（東南西）** |
| 配牌 | 13×4 = 52 | 13×3 = 39 |
| 王牌 | 14 枚、生牌は index 0..121 | 14 枚、**生牌は index 0..93**（ツモ可能 55 枚） |
| チー | あり | **なし**（ポン・カンのみ） |
| 北 | 客風牌 | **抜きドラ**。手牌から抜いて副露領域に置き嶺上牌をツモる。1 枚 = ドラ 1 |
| ツモ支払い | 子 3 人で分割 | **2 人で分割**（ツモ損ルールは v1 では採用しない） |
| 順位 | 4 位まで | 3 位まで |

自然に消える役: 萬子は 1・9 のみなので**萬子の清一色・純チャンの萬子染めは実質不可**
（国士は 1m/9m が残るので成立）。四風連打は元から v1 未実装。

**必要なリファクタ（ここが工数の実体）**

1. `types.ts` の `TILE_COUNT` / `DEAD_WALL_START` を定数からルール由来に変える。
   `Rules` に `tileSet: 'yonma' | 'sanma'` を足し、`wallLayout(rules)` が
   `{ tileCount, deadWallStart, doraIndicatorIndex, replacementIndex }` を返す形にする。
2. `Seat = 0 | 1 | 2 | 3` と `[number, number, number, number]` の 4 要素タプルが
   `PlayerState` / `RoundResult.scoreDeltas` / `GameState.scores` に焼き込まれている。
   **可変長（`number[]` + `seatCount`）へ広げる**のがこのマイルストーンの主作業。
3. `wall.ts`: 牌種 1..7 を除いた 108 枚生成。`buildWall(rng, rules)` にシグネチャ変更。
4. `actions.ts`: チーを列挙しない。**`nuki`（北抜き）アクションを追加**（嶺上ツモを伴う）。
   v1 では抜きドラは搶槓の対象にしない（国士のみロン可とするルールは採用しない）。
5. `score.ts`: 抜きドラをドラ数に加算。ツモ支払いを 2 人割りに。順位判定を 3 席に。
6. `ai/`: 3 席前提の安全牌評価（現物の母数が減るので押し引き閾値は再チューニング必須）。
   **M7 の A/B は四麻とは別の実験として回す**（複製壁は 3 席ローテになる）。

**ゲート**: 四麻の全テストが緑のまま、サンマでも `mahjong-sim-smoke` の不変条件
（牌の保存・点数総和・合法手が空にならない）が 5000 局でゼロ違反。

## 4. サブエージェント運用メモ

- **`package.json` は変更禁止**（バイトシール: 将棋 ML のエビデンステストが sha256 を固定しており、
  npm script を 1 行足すだけで `Test and build` が落ちる）。新しいハーネスは
  `node -r tsx/cjs scripts/<name>.ts` で直接起動する。
- **テストは必ず `tests/unit/**` 配下**に置く（vitest の include グロブ。コンポーネント dir に
  colocate すると CI で実行されない）。
- 実装ブランチは `main` から切り、M 単位で PR を分ける（M1+M2、M3、M4、M5、M6、M7 の
  5〜6 本想定）。フロントの必須チェック + gemini/copilot レビューボット
  （conversation-resolution 必須）が通ることがマージ条件。
- 並列化: M2 と M3 は別エージェントで同時進行可（M0 の型が契約）。M6 は M4 完了後に
  M5 と並列可。
- 各エージェントへの指示テンプレ: 「本ドキュメント §該当M を読み、成果物ファイルのみを
  変更し、ゲートのテストを `npm run test`（vitest）に追加して green にすること。
  `engine/` に React/DOM 依存を持ち込まないこと。牌表現の契約(§2)を変更しないこと。」
- ゲートを満たせない場合は仕様を勝手に変えず、本ドキュメントに Issue 追記して停止する。
