# サイト性能・モバイル全ページ監査レポート

監査日: 2026-09-02
対象: `https://www.meetyudai.com` と、この作業ツリーの最適化済み production build

## 結論

公開サイトの「クリックしてから待たされる」感覚は、単一の画像だけではなく、次の要因が重なっていた。

1. ルートレイアウトで `cookies()` と `headers()` を読むため、ほぼ全ページがリクエストごとの動的SSRになっている。
2. 記事一覧・記事詳細でクライアントへ渡すデータが大きく、遷移先RSCの取得・解析・hydrationが重い。
3. 一覧画像が2.19 MBの原寸PNGのまま配信されるケースがあり、画面外画像も早期に読み込まれていた。
4. ホームの複数データ取得がクライアント開始かつ直列寄りで、初期表示後も通信と再描画が集中していた。
5. i18nインスタンスの共有により、公開環境ではReact hydration error #418が複数ページで発生していた。
6. analytics・認証初期化・全ページ共通アニメーションなどが、最初の操作可能時間と競合していた。

今回、表示内容を削らずに改善できる範囲は実装済み。最終のローカルproduction buildでは、87の具体的ルートを320pxで再巡回し、実行エラー0件、ページ全体の横はみ出し0件だった。1280px巡回も実行エラー0件、横はみ出し0件だった。

Medium級の安定した即時レスポンスにさらに近づける最大の次手は、全ページを動的SSRにしている言語・認証判定をルート設計から分離し、公開ページをCDNキャッシュ可能にすること。ただしURL、SEO、言語切替の設計判断を伴うため、今回は勝手に変更していない。

## 監査範囲と方法

### 公開環境

- `sitemap.xml` から重複を除いた130 URLを取得。
- 130 URLすべてのHTTP応答を確認し、すべて200を確認。
- 130 URLすべてを320px幅の実ブラウザで巡回。
- 初期描画が認証・データ取得待ちになる79ページは、待機後に再評価。
- 記事一覧、記事詳細、ホーム、メニュー、長い表・コードブロックを個別に操作確認。

公開環境の単発観測では、ホーム初回表示が約3.4秒、記事カードから詳細への遷移が約3.3秒だった。ウォーム時TTFBは多くのページで約0.7〜1.7秒。ネットワーク、リージョン、キャッシュ状態で変動するため、これらは傾向把握用の値である。

### 最適化済みローカルproduction build

- Next.js manifestから取得した、動的パラメータを必要としない87ページを対象にした。
- 1280px幅と320px幅で全ページ巡回。
- 各ページで描画成立、Next.jsエラー画面、`scrollWidth`、本文表示を確認。
- 300ms時点で認証待ちだった14ページは、1.5秒待機後に再確認。
- 認証必須の管理画面・ユーザー固有データの作成/更新/削除は、資格情報なしで状態を変更しない範囲までを対象にした。
- 動的な記事・プロジェクトの実データページは公開環境側で確認した。

## 反復監査で見つけて直した内容

### 1巡目: 初期表示と記事遷移

- ホームのプロフィール、記事、プロジェクト、職歴、学歴、ゲーム設定などをサーバー側で並列取得し、初期値として渡すようにした。
- 同一リクエスト内・短時間の重複取得をキャッシュした。
- 匿名訪問者では不要な認証トークンAPI呼び出しを省略した。
- route-level loading UIを追加し、遷移直後の無反応感を減らした。
- page-view記録をmain threadのidle時へ遅らせた。
- AOSのCSSと初期化を、必要なホームだけに限定した。

### 2巡目: 記事ペイロード、画像、hydration

- 記事レイアウトの重複slug解決をなくし、middlewareとサーバー取得へ集約した。
- 記事取得をReact cacheで共有した。
- 記事一覧のクライアントペイロードを全文から要約中心へ変更した。サンプル5記事のシリアライズ量は約257 KBから約5.3 KBへ縮小した。
- 記事詳細は表示中の言語だけをクライアントへ渡した。サンプルでは約305 KBから約164 KBへ縮小した。
- 上位記事カードと関連記事をprefetch対象にし、クリック前に遷移先を準備するようにした。
- i18nをリクエスト/Provider単位のインスタンスに変更し、ローカル最終確認でhydration errorを解消した。
- 記事一覧の画像をNext.js Image Optimizationへ戻し、レスポンシブな`srcset`を利用した。
- 画面外の一覧画像、ゲームスライド、Markdown/legacy HTML本文画像へlazy loadingを適用した。LCP候補のヒーロー画像はeager/priorityのまま維持した。

実画像で、原寸2,193,208 bytesのPNGは、640px WebPで23,438 bytesになった。約98.9%削減。ローカルの最初の変換は約1.6秒だったが、キャッシュ済み応答は約0.002秒だった。

### 3巡目: 320pxモバイル崩れ

初回の87ページモバイル巡回で、次の3ページに横はみ出しを検出した。

- `/games/roulette`: 320px viewportに対して397px
- `/tools/kuizu/custom/new`: 363px
- `/tools/settli/new`: 322px

Rouletteの盤面をレスポンシブ化し、狭い画面ではベット面だけを内部スクロール可能にした。KuizuとSettliは操作ボタンをモバイルで縦積みにした。修正後の全87ページ再巡回では横はみ出し0件になった。

### 4巡目: 遅延表示・認証状態

認証初期化後まで待って再確認したところ、`/study/learning/flashcards`だけが未ログインでもAPIを呼び、認証エラー文を表示し、351pxまで横にはみ出していた。

- AuthProviderの初期化完了を待ってから表示を分岐。
- 未ログイン時は正しいredirect付きSign Inリンクを表示。
- 未ログイン時はflashcard/deck APIを呼ばないようhookに`enabled`制御を追加。
- ログイン時ヘッダーのボタンも320pxで折り返すよう調整。
- ページ側に重複していたflashcard/deck取得を削除。

最新ビルドで全87ページをもう一度巡回し、さらに認証待ち14ページを1.5秒後に再確認した。実行エラー0件、横はみ出し0件、空表示0件、`Unauthorized`露出0件だった。

## 犠牲・トレードオフ

- 表示内容や画質を意図的に削ってはいない。画像は端末幅に合うサイズ・形式へ変換される。
- lazy loading対象は画面外画像。LCP候補は先読みを維持しているため、ファーストビューを犠牲にしていない。
- Image Optimizationは、初めて使う幅・形式の変換時にサーバー処理とホスティング側の画像最適化使用量が増える。以後はキャッシュが効き、転送量削減効果が大きい。
- 320pxのRouletteでは、ページ全体ではなくベット盤面内を横スクロールする。盤面を判読不能なほど縮小しないための選択。
- 記事詳細では別言語の全文を同時に埋め込まない。言語切替時は対応ルートへ遷移して取得する代わりに、通常閲覧の転送・解析量を減らした。
- analyticsをidleまで遅らせたため、ロード直後に離脱したごく短い訪問は記録されない可能性がある。

## 残る改善候補

### 優先度1: 公開ページをCDNキャッシュ可能にする

`src/app/layout.tsx`が言語とセッション判定のために`cookies()`と`headers()`を読むので、build結果ではほぼすべてがdynamic SSR (`ƒ`) になっている。これがMediumとの差として最も大きい。

候補は、言語を`/en/...`・`/ja/...`のURLへ完全に寄せ、公開ページの認証状態をクライアント境界の内側へ移すこと。公開記事と一覧をstatic/ISR化できれば、HTML/RSCをCDN edgeから返しやすくなる。URL移行、canonical/hreflang、既存リンクredirectが関係するため、別変更として設計・計測して進めるべき。

### 優先度2: 共通client bundleを分割する

Theme、Auth、i18n、toolbar、ゲーム用Provider、global animation系の一部が全ルートに載っている。公開記事、ゲーム、認証ツールでlayout境界を分ければ、記事閲覧だけのユーザーへ不要なJavaScriptを送らずに済む。

### 優先度3: 認証必須hook全体のfetch抑制

今回Flashcardsでは未ログイン時のfetchを止めた。他のLearningページはUI上は正常なSign In表示だが、いくつかの共通hookはページの認証分岐より前にfetchを開始する構造が残る。hook全体に`enabled`契約を広げると、未ログイン遷移時の無駄な401とmain-thread workをさらに減らせる。

### 優先度4: 実ユーザー計測

本番へ反映後、Web VitalsのLCP・INP・TTFBと、`/blog`から記事詳細へのroute transition時間をp50/p75で計測する。今回のbrowser観測は改善箇所の発見には有効だが、実ユーザーの端末・回線・地域差はRUMで確認する必要がある。

## 環境上の制約

ローカル環境にはFirebase Admin資格情報がないため、データ依存ページは既定値・クライアントfallbackで検証した。公開データを伴う130 URLは本番側で別途確認済み。認証済み管理操作やユーザーデータ変更は、監査で本番状態を変更しないため対象外とした。
