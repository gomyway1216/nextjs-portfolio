# NNUE 蒸留 第3サイクル レポート — 縮約KP特徴量 (自玉バケット): 否定的結果

日付: 2026-07-05
作業: 特徴量を現行の盤面 one-hot (2268) から **縮約 King-Piece (自玉位置バケット×盤面/持ち駒)**
へ拡張し、玉の文脈を第1層に取り込む試み。学習・量子化・TS/WASM 推論 (差分アキュムレータ
+ 玉バケット越え refresh) まで全パイプラインを実装し、パリティ/3-way はすべて通過したが、
**共通ホールドアウトで現行 run1m-base を上回れず (pair_acc −0.5pt / 互角圏 同等)、
参考の新旧直接対決でも勝ち越せなかったため、本番重みは run1m-base のまま変更しない**。
インフラ (KP 対応の学習・エクスポート・推論・検証・対戦ハーネス) は本 PR で整備済みで、
教師データの質・量が改善した後に再挑戦できる。

前サイクル: `ml/data/training-report-2.md` (run1m-base, holdout MAE 458.7cp / 対V3 77.1%)。

## 1. 設計 — 縮約KP (KP6)

フル HalfKP (玉81×駒種×マス) は重み表が数十MBになり配信不可 (現行 1.19MB, 上限目安 8MB)。
自玉位置を **6バケット** に量子化し、盤面/持ち駒テーブルをバケット毎に複製する縮約案を採った:

- 特徴: `bucket(自玉) × (28駒種プレーン × 81マス)` = 6×2268 = 13,608 + 持ち駒 6×14 = 84
- 手番側視点は現行と同一 (後手番は180°回転+色反転)。**両視点それぞれ「その視点の自玉」**
  のバケットを使う (本家 HalfKP と同じ構図)。
- バケット定義 (手番側視点の自玉 (筋s, 段d)) — 教師データ20万局面の実測分布でマスを粗く等分:

  | bucket | 領域 | 出現率 |
  |---|---|---|
  | 0 | d9, s5 (玉未移動) | 47.8% |
  | 1 | d9, s1-4 | 6.0% |
  | 2 | d9, s6-9 | 9.7% |
  | 3 | d8, s1-4 | 11.7% |
  | 4 | d8, s5-9 | 18.5% |
  | 5 | d1-7 | 6.1% |

- サイズ: weights.bin **7,027,908 B (6.70MB)** — int16 のまま 8MB 上限内 (現行の6.07倍)。
- 差分更新: 玉がバケット境界を越える指し手はその視点の全特徴が変わるため
  **アキュムレータをその視点だけ盤面から全再計算 (refresh)**。バケット内の玉移動・
  他の駒の指し手は従来通りの行加減算。lazy 適用スタックとの整合は「折り込み中に
  境界越えを検出→現局面から再構築」「折り込み済み境界越えの unmake→dirty フラグ→
  次回評価時に再構築」で厳密に保つ (パリティで検証済み)。

## 2. 学習 (teacher-1m-train 1,004,878 局面, run1m-base と同一ハイパラ)

40 epoch, MPS, batch 256, AdamW lr 1e-3 cosine, K=600, cp±3000, seed 42, val 10% (同一split)。

| run | 特徴量 | best epoch | best val_loss | val MAE | val pair_acc | 学習時間 |
|---|---|---|---|---|---|---|
| run1m-base (第2サイクル) | board (2282) | 8 | **0.020732** | 437.1cp | 0.8961 | 387s |
| run1m-kp6 | kp 直接 (13692) | 27 | 0.020995 | 395.3cp | 0.8959 | 676s |
| run1m-kpf | **kp-factor** (分解学習) | 23 | 0.021037 | 399.7cp | 0.8965 | 857s |

- kp 直接: 第1層パラメータ6倍で train_loss は 1/3 に下がるが val_loss は base 未満に届かず
  — **明確な過学習**。
- 再挑戦 (設計変更1回): **factorized KP** (`--features kp-factor`)。第1層を
  `w1[b][f] = w_shared[f] + w_delta[b][f]` (デルタはゼロ初期化) に分解して学習し、
  共通構造を共有テーブルに載せてバケット別テーブルの過学習を抑える
  (本家 NNUE 学習器の factorizer の定石)。エクスポート時に合成するので推論形式は同一。

## 3. 共通ホールドアウト (holdout-1m-4k, 4,000局面, 全モデル未見, ペア189,333)

| モデル | MAE | median | pair_acc | 互角圏(0-300) | 300-1000 | 1000-3000 | 3000+ |
|---|---|---|---|---|---|---|---|
| run1m-base | 458.7 | 292.1 | **0.8725** | 258 | **392** | 608 | 1104 |
| run1m-kp6 | 463.9 | 261.7 | 0.8629 | 280 | 445 | 580 | 903 |
| run1m-kpf | **455.4** | **259.5** | 0.8678 | 259 | 452 | **571** | **847** |

(単位cp。バケット n: 1,138 / 1,188 / 1,555 / 119。base 行は第2サイクルレポートの値を
新規実装の `ml/eval-holdout.py` で再現一致確認済み)

**判定: 改善なし。**

- factorizer で kp 直接比は全指標改善したが、base 比では **pair_acc −0.5pt (0.8725→0.8678)**、
  **互角圏 MAE 同等 (258→259)**、300-1000 帯 **+15% 悪化 (392→452)**。全体 MAE −0.7% と
  median −11% の改善は **|cp|≥1000 の sigmoid 飽和域に集中**しており、探索の着手順位に
  効く領域 (互角圏・pair_acc) では勝っていない。
- 解釈: 教師 1M 局面のうち玉が動いた局面は約半分で、バケット別テーブルは実効データが
  1/6〜1/2 に薄まる。現在のデータ量・質では「玉文脈の追加表現力 < データ希釈による損失」。
  第2サイクルで 300k→1M のスケーリングがまだ逓減しつつ効いていたこととも整合する。

## 4. 量子化・パリティ・3-way 検証 (すべて通過 — インフラは完成)

- `export-weights.py`: kp/kp-factor 対応 (factor は shared+delta を合成して量子化)。
  run1m-kpf: float vs int16 誤差 mean 17.5cp / max 130cp (200局面) — base 系と同水準。
- WASM (`wasm-spike/assembly/index.ts`): `setNnueBuckets(1|6)` でレイアウト切替
  (デフォルト1=現行と完全互換)。KP 用に両視点バケット byte offset キャッシュ +
  境界越え検出 + 視点別 refresh + dirty フラグを実装。重み領域は 7MB 静的確保
  (`memory.data` は data segment を出さないため .wasm バイナリは約35KBのまま)。
  作業中に main へ入った SIMD128 化 (PR #309) ともマージ済みで、SIMD 経路 +
  KP の組み合わせでもパリティ全通過。
- `nnue-parity.ts`: 全スイートを **buckets=1 / buckets=6 の両フォーマットで実行**。
  1000 recompute + 1200 differential 局面、玉移動126回 (うち**バケット越え87回 =
  refresh 経路**)、全6バケット出現、探索同値性 (fast==full, ノード数まで一致) — 全部
  ビット一致で通過。既存フォーマットも回帰なし。
- 3-way (`nnue-verify-reference.ts`, ファイルサイズからフォーマット自動判別):
  run1m-kpf 200局面 **torch == TS == WASM ビット一致**。run1m-base (旧フォーマット) も
  再検証しビット一致 (回帰なし)。
- `match-nnue-vs-v3.ts` に `--vs <weights.bin>` を追加: **新旧 NNUE 直接対決**が可能に
  (両側とも任意フォーマット、サイズ自動判別)。
- tsc / eslint / vitest (292) / next build / parity.ts (V3経路回帰) すべて通過。

## 5. 参考: 新旧 NNUE 直接対決 (情報提供のみ、採用ゲートではない)

ホールドアウトで改善が出なかったため本採用 A/B (3シード×16局) は実施しない。
ただし「MAE/pair_acc は対局強度の予測子として不十分」という第1サイクルの教訓を踏まえ、
参考として 1 シードのみ直接対決を実施した (`--vs` ハーネスの実証を兼ねる):

- 条件: run1m-kpf (KP6) vs run1m-base、1000ms/手 × 16局、seed 11、book/詰みソルバなし
  (`match-nnue-vs-v3.ts <kpf> --vs <base>`)。
- 結果: **KP6 側 6勝 10敗 0分 = 6/16 (37.5%)**。全 1,596 手の合法性チェック通過、exit 0。
- ホールドアウトの示唆 (改善なし) と整合。KP6 が base に勝ち越す証拠は得られず、
  むしろ明確な劣勢。不採用の結論を補強する。

## 6. 結論と次への示唆

1. **本番は run1m-base のまま** (public/shogi-nnue-weights.bin 変更なし、ローダ変更なし。
   なお PR #310 のホットフィックス以降、NNUE は medium 難易度のみで有効)。
2. 縮約 KP6 は現在の教師データ (1M, depth8, 自己対戦由来で玉未移動局面が半分) では
   **過学習/データ希釈が支配的で純増にならない**。factorizer でも埋まらなかった。
3. 再挑戦の条件 (優先度順):
   - **教師データを 3〜10M へ増強** (バケット毎の実効サンプルを確保)。特に玉が
     移動した局面 (囲い完成形) の比率を上げる生成制御が有効なはず。
   - 教師 depth を 8→10-12 に上げて玉安全度がラベルに反映される局面を増やす。
   - バケットを 6→3 (未移動/右/左 等) に減らして希釈を抑える案、または
     持ち駒テーブルのみ共有化する折衷案。
   - WDL ブレンド等で大差域の教師ノイズを抑え、互角圏の学習効率を上げる。
4. インフラは全て main に入る: `--features kp|kp-factor` 学習、KP 量子化エクスポート、
   `setNnueBuckets` 付き WASM 推論 (デフォルト経路はビット互換)、両フォーマット
   パリティ/3-way、新旧直接対決ハーネス。再挑戦時はデータ生成からやり直すだけでよい。
